# pi-web-simple

一个基于 [pi](https://github.com/earendil-works/pi-coding-agent) 的本地项目管理 / 对话 Web UI。

项目管理模型与界面风格参考 [deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)：**一个本地目录 = 一个项目**，项目下挂该目录的会话。agent 内核是 pi 本身，通过 `pi --mode rpc` 子进程接入。

```
浏览器 (React + Vite)
   │  POST /api/*            上行命令
   │  GET  /api/events (SSE) 下行事件
   ▼
Node 服务端 (单进程)
   ├─ 项目记录   ~/.pi-web-simple/store.json
   ├─ 界面偏好   同一份 store.json（外观 / 字号 / 对话显示 / 发送行为）
   ├─ 模型提供方 ~/.pi/agent/models.json + auth.json（pi 没有对应 RPC）
   ├─ 会话列表   从 pi 自己的存储实时派生
   └─ 进程注册表 每个会话一个 pi RPC 子进程（懒启动 + 空闲回收）
   ▼
node <pi>/dist/cli.js --mode rpc --session <file>   (cwd = 项目目录)
```

## 快速开始

需要 Node.js `>= 22.19`。

```sh
pnpm install
pnpm dev
```

然后打开 <http://127.0.0.1:5319>。

- 前端 dev server：`127.0.0.1:5319`（Vite，`/api` 反向代理到后端）
- 后端 API：`127.0.0.1:4319`

首次使用：点击左侧栏的 **+**，在弹出的目录选择器里逐级进入目标目录（顶部快捷位置可直达主目录 / 桌面 / 文稿 / 下载 / 根目录，地址栏也可直接粘贴路径），点 **选择此目录** 添加项目；再点项目下的 **+** 新建会话开始对话。

其他命令：

```sh
pnpm build       # 构建前端
pnpm typecheck   # 前后端类型检查
pnpm test        # 前后端测试（vitest）
```

## 环境变量

| 变量 | 默认值 | 说明 |
|---|---|---|
| `PI_WEB_SIMPLE_HOME` | `~/.pi-web-simple` | 项目记录（`store.json`）的存放目录 |
| `PI_WEB_SIMPLE_PORT` | `4319` | 后端 API 端口 |
| `PI_WEB_SIMPLE_SESSION_DIR` | pi 的默认目录 | 覆盖会话存储根目录；同时作用于会话查找与派生的 pi 子进程（`--session-dir`） |
| `PI_WEB_SIMPLE_IDLE_MS` | `600000` | 会话空闲多久后回收其 pi 进程（预热进程同样适用） |
| `PI_WEB_SIMPLE_MAX_SESSIONS` | `8` | 同时存活的 pi 进程上限 |

前端 dev server 的代理目标端口读取 `PI_WEB_SIMPLE_PORT`，两处要保持一致。

## 目录选择器为什么要走服务端

浏览器拿不到本地目录的绝对路径：`<input webkitdirectory>` 只给出相对路径，File System Access API 出于安全考虑刻意不暴露真实位置。所以目录浏览由服务端提供（`/api/fs/list`、`/api/fs/locations`），只列出子目录名，**从不读取文件内容**。

因为无鉴权的服务端能枚举文件系统，所有 `/api/*` 请求都会校验 `Host`（以及存在时的 `Origin`）必须是回环地址。这样即使恶意页面通过 DNS rebinding 把自己的域名解析到 `127.0.0.1`，也会因携带非回环的 `Host` 头而被拒。

## 与 pi CLI 并存

这是这个工具的核心约束，也是几个设计取舍的来源。

**项目记录与会话是分开的。** `store.json` 只保存项目（路径、标题、顺序）和少量 UI 偏好（重命名、隐藏）。会话列表每次都从 pi 自己的会话目录实时派生，会话正文永远只有 pi 一份。因此终端和 Web 看到的会话始终一致，也不存在同步问题。

**同一时刻只有一个写者。** 服务端保证一个会话文件最多对应一个 pi 子进程。如果终端里的 `pi` 正在写一个 Web 也开着的会话，文件监听会发现这次写入发生在 Web 自身活动窗口之外，于是：

- 侧栏对应行出现一个圆点；
- 对话区顶部出现「这个会话被其他进程修改过」的提示条；
- 点击 **重新载入** 会结束 Web 侧的进程、重新读取文件，之后由 Web 接管。

Web 不会静默合并两边的写入 —— 那样会互相覆盖 leaf 指针。

**新建会话是即时的。** 启动一个 pi 子进程要花 1.3–3.2 秒（冷启动实测 3220ms，从磁盘重开 1492ms；已驻留的会话只要 2–3ms）。所以点 **+** 不会等它，有两层保障：

1. **预热**：选中项目时就后台先起一个 pi 进程（`POST /api/sessions/prewarm`，请求本身立即返回，不阻塞任何 UI）。点 **+** 时直接接管它，实测 **2–3ms**；接管后立即在后台预热下一个，所以连续新建也一样快。
2. **draft 兑底**：如果预热还未就绪（刚切到项目、或上一轮已被回收），界面立刻切到一个纯前端的 draft（`draft:<random>`），pi 进程在后台启动，完成后把真实路径换进来（侧栏显示为「新会话 · 准备中」，对话区标题旁转圈）。这期间可以直接输入，发送时会等进程就绪再投递。

预热的进程从未被认领时不会产生任何文件（pi 只在收到第一条 assistant 回复后才写入 JSONL），并且：同一项目最多一个未认领预热（预热新项目会释放旧的），空闲 10 分钟后同样被回收。

**未落盘的会话是临时的。** pi 在收到第一条 assistant 回复之前不会创建 JSONL 文件。所以新会话在发出第一条消息并收到回复之前：

- 不会出现在会话列表里（只显示为侧栏顶部的「新会话」行）；
- 如果此时服务端的进程被回收（空闲超时、重启），它的上下文会丢失。

一旦有了回复，文件落盘，侧栏列表会自动把它收录进来。

**删除项目不等于删除数据。** 移除项目只删掉那条记录，目录和全部会话历史都留在磁盘上。

**重命名不写 pi 的文件。** 在 Web 里改会话名只写入 `store.json` 的覆盖项，pi 的 `/name` 和 JSONL 内容都不动。

## 实现要点

**pi 的接入用的是官方 `RpcClient`**（`@earendil-works/pi-coding-agent` 已导出），但它有一个坑：`start()` 内部的 `cliPath` 默认是相对路径 `dist/cli.js`，而子进程的 `cwd` 是项目目录，所以必须显式传入 `getPackageDir()` 拼出的绝对路径。

**消息列表也来自 pi**：`SessionManager.list(cwd, sessionDir)` 直接给出标题、时间、消息数，`SessionManager.list` 的第二个参数是**该项目的会话目录**（`<root>/--<编码后的 cwd>--`），不是会话根目录；这个编码规则 pi 没有导出，在 `session-path.ts` 里复刻了一份。

**流式渲染没有累积快照**：`message_update` 只带增量，客户端必须按 `contentIndex` 自行拼装，并以 `message_end.message` 为准。

**延迟都被推到了有预期的地方**：界面从不等 pi。选中项目时后台预热一个空会话（点 **+** 实测 2–3ms，对比冷启动 3220ms），预热未就绪时退化到纯前端 draft，点已有会话则直接从磁盘读转录（见下）。进程启动的开销要么提前付掉，要么发生在用户已经在“等待回复”的心理预期里。待发消息通过 `pendingPrompt` 交接给真实会话，切换会话时会丢弃，不会误投。

**侧栏跟随 dsh 的信息层级**：顶部是全宽「新会话」按钮，下方是「工作区」分区，每个工作区展开后把它的会话嵌在下一层（会话行不重复文件夹图标，右侧只给紧凑的 `7天`）。工作区支持按目录祖先关系嵌套（`/a` 包的 `/a/b` 收在它下面，没有注册父目录的保持平铺）；每个工作区默认只列 5 条会话，其余折叠为「展开其余 N 个会话」。选中项用浅底 + 文字加粗，而不是只换背景色。

**整行都是切换目标，而不只是标题文字**。会话行的标题按钮用一个拉伸的伪元素（`.sessionTitle::after` + `inset: 0`）铺满整行：仍是**一个**真实控件（键盘焦点和读屏不会看到多余东西），但行的内边距、时间戳、以及短标题旁边的空白都算在内 —— 实测非悬停状态下 225px 行宽的采样 76/76 全部命中。两个容易踩的坑：`inset: 0` 必须相对已定位的 `.sessionRow` 解析（否则只铺开标题自己那么宽）；`.rowActions` 的渐变背景从透明开始，命中测试走的是 padding 盒，不给它 `pointer-events: none` 就会默默吞掉右侧约三分之一的点击 —— 只把指针留给真正的按钮。

**新会话页是一个独立的空状态**：未选中会话时不再是一个「请选择会话」的占位，而是 dsh 风格的居中页 —— 品牌标记 + 标题 + 「预览版」标签、工作区选择器、大圆角输入框。在这里输入第一句话会同时完成两件事：立即切到 draft，并把这句话排队交给即将就绪的会话。

**内置命令必须由 Web 端自己实现**。pi 把 `compact` / `export` / `session` / `name` 这类命令放在独立的 `BUILTIN_SLASH_COMMANDS` 里，**永远不会出现在 `get_commands` 的返回中** —— 因为在 TUI 里它们是 TUI 自己实现的（打开设置菜单、读剪贴板、导航会话树）。`RpcSlashCommand.source` 的类型就是 `"extension" | "prompt" | "skill"`，没有 builtin。

所以 Web 端要同时提供清单和行为：只列出**有对应 RPC 方法**的命令，`/tree`、`/settings`、`/copy` 这些需要专门 UI 的不列 —— 菜单里点了没反应的选项比不列出更糟。执行时走 `POST /api/sessions/:id/command`，文本不会进入模型。

**输入框里的 `/` 补全**：命令列表来自运行中的 pi 进程（`get_commands` RPC），所以服务端优先复用该项目的活跃会话，没有就走预热进程，结果按项目缓存 60 秒。补全覆盖三类：扩展命令、prompt 模板，以及注册为 `/skill:name` 的技能。pi 在投递 prompt 前会自己展开 skill 与模板命令，所以前端只负责补全文本，不做任何替换。候选按「名字前缀 → 名字子串 → 描述」排序，上下键选择，Enter/Tab 补全（此时不会发送消息），Esc 关闭。对话输入框和新会话页共用同一套逻辑。

**扩展 UI 请求**：pi 的自有工具不会弹确认框，但已安装的扩展可以通过 `ctx.ui.confirm/select/input/editor` 阻塞运行。这类请求会被转成弹窗；`notify` 变成页面提示；`setTitle` / `setStatus` 等终端专用请求在服务端就被丢弃（一次普通对话会产生 50 多次 `setTitle`）。

**切换会话不启动进程**。`GET /api/sessions/:id/messages` 原本走 `openSession` → spawn pi，而冷启动要 1.2–3.3 秒 —— 这就是「正在载入会话…」等待的**全部**来源，尽管转录一直躺在磁盘上。现在只有**已驻留**的会话才走 RPC（它的内存视图是权威的，可能含有尚未落盘的轮次），其余直接从 JSONL 读：`SessionManager.open(path).buildSessionContext()`，也就是 pi 自己重建会话时用的那套（compaction-aware、从当前 leaf 走树）。35 个真实会话实测中位 **4ms**、p95 23ms、最大 28ms，且**零进程启动**；7 个会话与 RPC 结果逐条比对**完全一致**（覆盖 352 条消息 / 189 次工具调用，到 3 条消息的空会话）。浏览器里实测点击到内容可见 19–160ms。

顺带一提，payload 的大头是工具输出，不是 `system` 消息（实测只占 0.3% 字节），所以没做服务端瘦身。

切换耗时降到 ~100ms 后，「正在载入会话…」自己变成了两帧的闪烁。提示文案因此延迟 250ms 才出现（`useDelayedFlag`）：快的时候什么都不显示，真的慢了再解释原因。

**思考与工具调用是同一个原语的两种形态**。两者都走 `DisclosureRow.tsx`（移植自 dsh 的 `DisclosureRow`）：折叠时是一行 24px 高——图标、名称、一个 2×2 的圆点、然后是摘要。**没有单独的 chevron 列**：悬停时图标在**原地**淡出、chevron 在原地淡入（`.iconIdle` / `.chevronHover` 占同一个 16px 盒子），这正是让一列工具调用能像段落一样紧凑的原因。展开后 leading 位固定显示 chevron、不再做悬停预览，而 `collapsedContent` 默认会被丢掉（工具行传了 `keepContentWhenOpen`，因为它展开的是输入输出而不是摘要）。行高、图标盒 16px、字形 14px、圆点 2×2、各处间距都照抄 dsh 的值。

**行距是 dsh 的 flow gap，不是一个 `gap`。** 24px 是一行的高度，行与行的距离是另一回事：dsh 的 `ChatView.column` 从不设 `gap`，而是用相邻兄弟选择器给每个 flow item 加 `margin-top: var(--dsh-chat-flow-gap, 16px)`，只把**紧跟在紧凑过程窗口之后**的那个答案项改成 8px——它是那个窗口的结尾，不是新的一步。这里照搬同一套机制（`MessageList.module.css` 的 `.assistantTurn > * + *`，答案项上的 `data-turn-process-answer`），紧凑组展开后的行列表（`TurnProcessGroup.module.css`）也统一到 16px。改之前用的是 2px：行距 26px，比行本身高不了多少，一轮下来的思考与工具调用会被压成一整块；dsh 里它们各自是 40px 一座。

**`/skill:` 命令在转录里是展开态，显示时必须折回去。** pi 在投递前就把 `/skill:<name> [args]` 解成一条用户消息：`<skill name="git-commit" location="…">`、整份 SKILL.md、`</skill>`。于是「发一条 skill 命令」在这个 UI 里曾经是**两三千字的文件倾倒**，会话标题也跟着变成 `<skill name="git-commit" location="/Users/…`（pi 的标题取首条消息）。dsh 没有这个问题——它存的就是字面 `/git-commit`，`projectUserText` 把 `/` 开头的 token 渲染成蓝字等宽的 chip。这里做同一件事：`skill-block.ts` 用 **pi 自己的正则**（`parseSkillBlock`，`dist/core/agent-session.js`）解析，气泡里只画 `/skill:<name>`（外加用户写在命令后面的参数），复制按钮复制同一串命令，服务端派生标题时也先折叠（`foldSkillCommand`，同时容错 pi 已经截断的形态——标题只有 80 字，完整块多半只剩个开头）。chip 与气泡都照 dsh：chip 是 `refChip` + `slashChip`（品牌蓝、500 字重、代码字体、无自己的底色），气泡从灰底描边方块换成 `--dsw-specific-bubble` 的浅蓝胶囊（22px 圆角、10/16 内边距、22px 行高）。

**空思考块不渲染**。模型返回的思考常常以空行开头，直接取第一行会渲染出孤零零的「思考 ·」；pi 还会产生**完全空的** reasoning 块（思考被打断）。dsh 的 `ReasoningRow` 取字面第一行，但它另一个 helper 明确用 `find(c => c !== "")`，这里跟随后者。在一个真实会话上，这消灭了 39 行里的 11 行噪音。

**流式思考跟随末尾**：正在输出时摘要取**最后一个非空行**并右对齐（`data-follow-end`），文本从左侧溢出而不是整行重新省略号——否则每来一个 token 整行都会跳一下。输出结束后回到第一行。

**执行中有一处专门的指示**。`TurnStatus.tsx` 是消息列表末尾那行「深度求索中...」——字符串本身被渐变填充（`background-clip: text` + 透明文字色），渐变以 1.8s 平移，于是那道光扫过文字而完全不参与布局。它**不随首个 token 出现而消失**：dsh 的注释写得很明白，这个标签要跨越「首字之前、工具执行、流式输出」三个阶段，而这正好是 pi 的 `agent_start` → `agent_settled`，所以窗口直接用 `isStreaming`。超过 15 秒才会追加一个 `tabular-nums` 计时——大多数轮次在那之前就结束了，闪一下反而像故障。

**重试有独立的一行**。pi 在模型请求失败后会自己退避重试，这段时间界面本该是「卡住」的——而 `auto_retry_start` 带着 `attempt` / `maxAttempts` / `delayMs` / `errorMessage`，所以可以有带倒计时的「等待重试模型请求（1/3） · 8s」，倒计时归零后切成 shimmer 的「正在重试模型请求（2/3）」，展开能看到延迟和失败原因（照 dsh 的 `<details>` 结构）。这里有一处刻意的偏离：dsh 在重试进行中也显示秒数，但它的取值恒为 `1s`（helper 有 `Math.max(1, …)` 下限，而 deadline 已经过去了），显示一个永不变化的数字比不显示更糟，所以进行中的状态去掉了时钟、只留尝试次数。

**运行中的指示是扫光而不是转圈**：一条 300px 的高光以 2.6s 穿过整行，工具行和思考行各一份 keyframes，与 dsh 同一套动画。失败时图标换成 dsh 的 `StateDot`（外圈 10% 同色 + 内点 80%），摘要转成错误色。

**任务清单有两副面孔，因为 pi 的 `todo` 和 dsh 的 `todo_write` 根本不是一个东西。** dsh 是全量写：每次调用带整份列表，plan 在下一轮开始时清空，所以它的面板永远只描述当前这一轮。pi 的 `todo`（由 rpiv-todo 扩展提供）是增量操作——`create` / `update` / `list` / `get` / `delete` / `clear` 六种动作、四态状态（多一个 `deleted` 墓碑）、`blockedBy` 依赖、给进行中任务用的 `activeForm`，而且**清单是会话级的**，被显式清空之前一直在。能照搬的是形状与字形，不能照搬的是「这份列表属于谁」。

**让这件事成立的是两者共有的一个字段**：每次成功调用都在 `details.tasks` 里带回改动后的**完整清单**。于是当前清单是转录的一个投影（`projectTodos`：反向扫描，取最后一份读得懂的快照），而不是这个 UI 要自己维护的状态；终端面板在 `/reload` 与 compaction 之后也是这么重建自己的，两个界面读的是同一份东西。解析是**全有或全无**：一条任务读不懂就丢掉整份、再往前找一份，因为「少一行的列表」不是一个更小的列表，而是一份从来没存在过的清单。

**面板在输入框上方，默认折叠，空清单不渲染。** header 是清单图标 +「任务」+ `2 已完成 · 1 进行中 · 3 待处理`（用 U+2002 分隔——ASCII 空格会被 HTML 折叠成一格），展开是 `max-height: 180px` 的清单。卡片宽度是输入卡的 `780px − 32px`（dsh 的 dock 比 composer 每侧内缩 16px），与输入卡的间距就是 composer 自己的 8px 上边距。三个状态字形（绿圈勾 / 蓝色渐变环旋转 / 虚线空环）与 dsh 逐字节相同；`deleted` 不画——墓碑的意义是让 `blockedBy` 的 id 还能解析，不是给人看的，终端面板也从不渲染它。

**转录里那一行的摘要说的是「这次调用之后」的清单**：`3/7 已完成 · <正在进行的任务>`，并行进行的其余任务进一个不收缩的 `+1`（拼进摘要就会被窄行先截掉，而那恰好是它唯一要说的事）。dsh 的摘要只能描述整个列表，因为它的工具只写整个列表；pi 每次只动一个任务，所以「update #3」这一行不查快照就说不出发生了什么。参数读得到、快照读不到时（进行中）退回 `update #3` 这样的参数摘要。展开是这份快照本身——dsh 展开的是原始参数，对它来说那就是全部信息；pi 的参数只有一个 id 和一个状态，展开成 JSON 恰好把有用的东西藏起来。

**面板会裁掉过期的完成项，转录里的展开体不裁。** 实测那份真实会话里有 40 条完成压着 1 条待处理，展开面板先要滚过三屏历史才看得到「还剩什么」。所以面板只留**最近完成的 3 条**（`PANEL_COMPLETED_LIMIT`），其余折成末行 `+37 项已完成`；未完成的永远不裁。留最近而不是最旧，是因为任务按创建顺序编号，最近完成的正好挨着还在进行的工作——可见窗口因此是连续的，而不是中间被挖一个洞（同一份数据裁完是 `[38, 39, 40, 41]`，前三条完成、最后一条是唯一未完成）。转录里的展开体不裁：那是一份历史记录，裁剪它就是撒谎。

**没做「完成项下一轮隐藏」，虽然终端面板有这条规则。** 它靠的是一份运行时的「已经显示过」记账（`/reload` 或 compaction 会重置这份账），而这个 UI 每次切会话都从磁盘重建转录，没有那份账。按轮次硬推会在重新打开会话时把终端仍会显示的旧完成项藏起来——一个看起来一样、实际不同的模仿。同理没做每行的 `#id` 前缀：终端面板在至少一行带 `blockedBy` 时给每行标 `#N`，是为了让 `⛓ #1,#2` 的引用可解析；这里同样显示依赖，但 `#N` 从不被点击，只在一处被引用，前缀于是只是噪音。

**设置分两层，因为它们真的属于两层。** 侧栏底部的「设置」进入一个全屏设置页（左栏导航 + 右栏内容，照 dsh 重建）。导航有两项——**通用设置**和**模型**——它们各自的内容来自不同的地方：

- **外观 / 字号大小 / 对话显示 / 繁忙时的发送行为** 存在本项目的 `store.json` 里。pi 没有对应物，改它们不该影响终端里跑着的 `pi`。
- **自动压缩** 属于 pi，所以是从一个活的 pi 进程 `get_state` 读回来的，写也走 `set_auto_compaction`。一个项目进程都起不来时这一行显示为禁用——**宁可禁用，也不要显示一个我们猜的值**，否则用户会把它「改成」它看起来已经是的样子。
- **模型提供方** 既不在我们的 store 里，也没有 RPC，所以直接改 pi 的两个配置文件（下一节）。

**外观：深色主题是 dsh 的原件，不是调出来的。** dsh 的主题包里有四个 `body[data-ds-dark-theme]` 块，重新指向整套 static 色阶再由 semantic alias 引用它。它们本来就在 `design-platform.css` 里（当初是逐字移植的），只是**从来没生效过**——dsh 的运行时写的是 `data-ds-dark-theme`，而本项目写 `data-appearance`。把选择器改成 `html[data-appearance="dark"] body` 之后，深色立刻是对的：`--dsw-alias-bg-base` → `rgb(21,21,23)`，`--dsh-scrollbar-thumb` → `rgb(60,60,61)`，连思考行的渐隐带都从白换成 `#151517`。

**选择器写成 `html[…] body` 而不是 `body[…]` 是有原因的**：浅色 token 就声明在 `body` 上，深色块必须**在同一元素上比它更具体**，而不是去命中它的后代。三个 token 表（`design-platform` / `gradient-shadow-text` / `shiki`）都是这个形状。

**字号只写一个变量，其余靠 CSS 派生。** dsh 的字号是 12–17 的整数（`Schema.number().step(1).min(12).max(17).default(14)`）。`--dsh-content-font-size` 由设置页写成 `documentElement` 上的内联属性，而 `--dsh-content-font-delta` / `-secondary` / `-delta-secondary` 在 `gradient-shadow-text.css` 的 `body` 块里用 `calc` / `min` / `max` 从它派生——那份是 dsh 原件，本项目一直就有。

**真正断掉的是消费端。** `Markdown.module.css` 把正文字号硬编码成 13.5px、标题 19/17/15/14px，`MessageList.module.css` 把用户气泡写成 13.5px——全都不读那几个 token。后果是：改字号时只有工具行和思考行会动（它们读 `--dsh-content-font-size-secondary`），而读者停留最久的**正文一动不动**。接上 dsh 的 `--dsw-font-markdown-*` 尺寸后，正文 14→17px 时行高跟着 24→27px，标题按同一像素增量保持层级。顺带把基准从 13.5px 拉回 14px：dsh 的 `--dsw-font-markdown-base-font-size` 就是 `--dsh-content-font-size`，13.5px 是当初手写时滑掉的。code 与行内 code 保持固定，dsh 把它们归为密集次级文本。

**字号越界是拒绝，不是夹取。** 服务端校验 `Number.isInteger` 且 12 ≤ n ≤ 17，不合法直接 400。stepper 的按钮在边界上禁用，所以 UI 根本产生不出一个会被拒的值——一个悄悄存成别的数字的设置项比一个报错的设置项更难查。

**「对话显示 = 紧凑」是按轮次折叠，不是按消息。** 已完成轮次的思考与工具调用收进一行「执行过程 · N 项」，答案保持在原位；进行中的轮次永远不折，否则折掉的正是用户在等的东西。这里踩了一个真坑：分区最初放在渲染单条 assistant 消息的组件里，于是一轮里每次工具往返都产出一个「执行过程」行——一个真实会话上量到 **23 个组**，而正确的数字是 **3**。改成在轮次层先把 assistant 内容拍平再分区后，3 个组分别是 27 / 16 / 12 项，加起来 55 = 32 个工具 + 23 个思考，**数量精确对上**。

**「繁忙时的发送行为」是本项目的设置，不是 pi 的。** pi 有 `set_steering_mode` / `set_follow_up_mode`，但它们管的是**已经排队的多条消息怎么投递**（`all` 还是一条一条），而 dsh 这一项问的是**Enter 键用哪种投递**——那是客户端选 `prompt`/`steer`/`followUp` 时决定的。所以它进 `store.json`，控制 Composer 的默认投递方式；输入框上的「引导 / 追问」开关是本次会话内的临时覆盖，而 **Cmd/Ctrl+Enter 永远走另一个**（dsh 的说明里明确写了这一点，本项目此前没有实现）。

**改 pi 的全局设置会让其他驻留进程过期。** `set_auto_compaction` 写的是 pi 自己的配置文件，而只有**新启动**的进程会重新读它——已经跑着的进程继续用它启动时那份。所以写入成功后除了当前 handle 之外全部关闭（`closeAllExcept`），代价是下次切到那些会话要付一次冷启动。改设置是低频操作，用一次稍慢的切换换「另一个开着的会话不会显示旧值」，值。

**没有「权限」也没有「语言」，因为做不出真的。** dsh 的权限是三档「仅可查看 / 工作区内修改 / 完全权限」，pi 侧对应的是 `trust`——而那是**「是否信任这个项目的动态配置（`.pi` / `.agents/skills`）」**，项目级、没有 RPC、语义也不是工具执行级别，放进「通用」里是错位的。语言则是单语言项目：列表里只有一个选项，等于摆了一个不会变的下拉。两项都留空，而不是放个占位。

### 消息操作行 / fork / 话题树

**每条消息下面有一行操作（复制、分支、用量、用时、时间），其中只有「复制」是纯前端的。** 其余三项都需要 pi 里真实存在的数据，而它们确实存在，只是藏得比较深：

- **用量**在每条 assistant message 自带的 `usage` 里（`{input, output, cacheRead, cacheWrite, totalTokens, cost}`）。一轮的用量是该轮所有 assistant message 的 `totalTokens` 之和——所以它是「本轮所有模型调用累加的 token 数，含缓存读取」，而不是可见答案的长度。一个 400 token 的回复坐在 30k 的上下文上会报 ~30k，这是对的。
- **用时**由时间戳算：本轮最后一条 message 的 `timestamp` 减去第一条的。**它是墙上时间，不是模型时间**——包含工具执行、排队、重试。别处没有更好的数据源；pi 的 TUI 有自己的计时器，但那是终端渲染层的东西，没有 RPC 能拿到。
- **分支**需要 `entryId`，而 `get_messages()` 返回的 message **不带 id**，只有 JSONL 里的 entry 带。

**entryId 是按位置配对、用文本二次校验的。** 一开始想用时间戳配对，实测发现不行：entry 的 `timestamp` 是**写入时刻**，message 的 `timestamp` 是**生成时刻**，同一条助手消息相差 4 秒（`toolResult` 两者相等，`user` 差 0.35 秒)。能依赖的是**顺序**：`buildContextEntries()`（pi 自己重建上下文用的函数）里筛出 `type === "message" && role === "user"`，其顺序与转录里的用户消息严格一致——在一个 13 轮会话上验过，**13/13 对齐、文本 0 处不符**。文本一并下发，客户端逐条比对，**不符就不显示分支按钮**：与其在错误的位罟分叉，不如不给这个按钮。

**pi 的 `fork` 是「从这条消息重新开始」，不是「截断当前会话」。** 实测（先备份、测完逐字节还原）：

```
原会话   210 行 → 211 行，且新增的那条是 plannotator 插件写的 custom entry
             0 个 entry 被移除，11 个用户消息 id 全部保留
新会话   另建一个 .jsonl（93 条 entry / 87 条 message / 2 条用户消息）
```

fork 到第 3 条用户消息时，新会话里只有 **2** 条用户消息——因为被点的那条是「要重新提的问题」，不在历史里。这一点和直觉相左，所以界面在分叉后**直接切到新会话**、刷新侧栏，并用一句通知说清楚原会话还在。（第一版把 `sessionPath` 当成新会话读回去，看上去像什么都没发生：`sessionPath` 始终是原路径，新分支在 `sessionFile` 里。）

**没有赞/踩。** 参考截图里助手消息下还有一对拇指，但 dsh 把反馈存在自己的 message 字段上，pi 没有对应字段也没有 RPC。那个按钮要么什么都不做，要么写到没人读的地方——**一个做不到事的控件比一个不存在的控件更糟**。

**话题树能看，不能“切过去”。** pi 的 TUI `/tree` 可以把叶子指针移到任意节点，但**没有任何 RPC 能移叶子**：分支相关的方法只有 `fork`，而且它只接受用户消息。所以这一页展示树、标出当前所在位置、在能分叉的节点上标「可分叉」，而不提供一个看起来能切换分支、实际什么都不做的按钮。节点标签是本项目自拟的（pi 的 TUI 文案是英文终端文本，没有可以照搬的 zh 词典），默认展开当前叶子那条路径。

**设置页的导航只有两项，但轨道形状是对的。** dsh 的面板有模型 / 插件 / Agent 预设 等一节节，本项目做的是通用设置和模型。搜索框没做——它只能搜到几个结果，加一个搜索框是为了显得完整，不是为了好用。

### 模型配置为什么在改文件

**pi 的 RPC 覆盖的是「一个正在跑的会话」，不是它的配置。** `set_model` / `get_available_models` 这些操作的是进程状态，而 provider 定义和它们的凭据是**启动时读一次**——那时还没有任何会话。所以这一节直接编辑 `~/.pi/agent/models.json` 和 `auth.json`：

```
models.json  { providers: { <id>: { name, baseUrl, api, apiKey?, models: [...] } } }
auth.json    { <id>: { type: "api_key", key: "..." } }
```

两个文件都读，凭据**只写 `auth.json`**：pi 自己的登录流程就存在那里，而且把秘密集中在一个 0600 文件里，比散在一个用户很可能粘进聊天窗口的定义文件里好推理。pi 支持把 `apiKey` 内联写在 provider 里，这种情况也会被认出来（`keySource: "inline"`），但不由本页管理——编辑器看不到它的值，没法让用户决定要不要覆盖它。

**「自定义」徽章的判据是 pi 的 `KnownProvider`（41 个 id）。** id 不在那张表里，就是用户自己造的 provider，只有用户知道它的地址和协议。拿截图核对过：dsh 那边 `DeepSeek` 没有徽章（内置），`cz` 和 `CommandCode` 有（自建）——本项目里 `cz` 和 `commandcode` 同样带徽章，**判据一致**。那张表在 `models.ts` 里是字面量而不是 import 的，因为 `@earendil-works/pi-ai` 是 pi 启动器的传递依赖，pnpm 的严格布局不暴露它。代价是 pi 新增内置 provider 时它会被标成自定义——一个外观上的小误差，不是一次错误的写入。

**API 密钥是只写的。** 页面从服务端拿不到当前 key，所以没法显示或是回显；没动过输入框的保存**不发送 apiKey 字段**，服务端把「字段缺席」解释为「保持原值」，密钥因此活下来。占位文字就是 dsh 的那句「已配置——输入新值可替换」。这条不只是隐私：如果 key 能读回来，它就会出现在 DOM 里、出现在浏览器缓存里、出现在任何一次截图里。

**保存时按 id 合并模型列表，不重建。** 编辑器只渲染每个模型的 `id` 和 `name`，但一个模型条目还带着 `contextWindow` / `maxTokens` / `cost` / `reasoning` / `input` / `thinkingLevelMap` / `compat`。**这里踩了一个真坑**：第一版把列表整个替换成渲染出来的两个字段，结果浏览器里改一个 provider 的名字，它下面所有模型都被削成 `{id, name}`——一个声明了 `contextWindow: 1000000` 的模型回来时上下文窗口为空，pi 会退回一个对那个端点而言错误的默认值。文件里那段注释当时写的就是「要保留不理解的字段」，然后服务端在模型数组上正好没做到。改成按 id 合并、只覆盖 `name` 之后，改名操作对 `models` 是**逐字节无差**的（有测试守着）。删除仍然有效：编辑器列表里没有的 id 会被移除。

**状态点只说明配置文件里有没有凭据，措辞也跟着收敛。** 判断看 `auth.json` 的条目和 `models.json` 的内联 `apiKey` 两处，但**环境变量提供的密钥看不到**——所以 tooltip 写的是「配置文件里没有 API 密钥」，而不是「未配置」。用户用环境变量时这行不会误导他去重新输入一个已经生效的 key。

**写之前备份，写的时候原子替换。** 每个被改动的文件先落一份 `*.bak.pi-web-simple-<时间戳>`（沿用 pi 自己 `.bak.<后缀>` 的习惯），再用临时文件 + rename 落盘，权限 0600。改配置文件是一个崩溃就可能毁掉用户全部模型配置的操作，这两步都很便宜。

**改完关掉所有驻留的 pi 进程。** provider 列表是进程启动时读的，所以一个比这次编辑更早启动的进程会继续用它那份：刚加的 provider 在任何地方都看不见，刚删的还会应答。会话本体在磁盘上，所以代价只是下次切换付一次冷启动。

**「打开配置文件」在本项目里叫「复制配置路径」。** dsh 是桌面应用，能把路径交给操作系统去打开；浏览器不行。按钮名字改成它真正做的事，路径放在 `title` 里，点击即复制——一个承诺「打开」然后什么都不发生的按钮比一个范围更窄的按钮更糟。

**不列出未配置的内置 provider，虽然 dsh 会列。** 截图里 `DeepSeek` 带着红点出现在列表里，因为 dsh 知道它的端点与协议。pi 的 provider 必须在 `models.json` 里显式定义（含模型列表），所以我们不知道一个没配置的 provider 该长什么样——列出来点开也没有可填的东西。入口交给「添加提供方」：它从那 41 个 id 里选一个。

### 获取可用模型

**「获取可用模型」这件事 pi 做不了。** `get_available_models` 报的是**已经配好**的模型，而 pi-ai 里的 `refreshModels` 是**每个 provider 自己的方法**（各 provider 自建 `models-store.json` 条目，比如 `opencode-go`），而且 `@earendil-works/pi-ai` 不在依赖树里。所以这个请求由服务端自己发。

**地址与认证头按协议选。** Anthropic 的列表端点在版本前缀下面（`https://api.anthropic.com/v1/models`），而它的消息端点是 `{baseUrl}/v1/messages`，所以 `anthropic-messages` 拼 `/v1/models`，其余拼 `/models`——**但如果用户已经写了 `/v1` 就不再接一次**。把 `https://host/v1` 拼成 `/v1/v1/models` 不是一个任何 provider 会服务的路径，而粘贴一个带 `/v1` 的 base URL 很常见。认证头同样分两种：Anthropic 用 `x-api-key` + `anthropic-version`，其余用 Bearer。

**响应形状宽容一点没代价。** OpenAI 和 Anthropic 都答 `{ data: [{ id, … }] }`（Anthropic 把显示名叫 `display_name`），而自建网关也常见 `{ models: [...] }` 和裸字符串数组。三种都收，代价是一个分支。

**参数是「表单里当前的值」，不是已保存的 provider。** 这个功能最有用的时刻就是**建一个 provider 的时候**——那时还没有 id、也没有文件可读。所以接口收的是未保存的 `baseUrl` / `api` / `apiKey`，密钥未填时服务端回退到 `auth.json` 里存的那个（**回传的只有模型列表，密钥永远不回前端**）。没有任何写入，所以不会清掉驻留进程。

**已在目录中的模型会列出但不可选。** 列出是因为一个用户找得到的模型在列表里看不到，读起来像拉取失败；不可选是因为重加一个会重写它的条目，把手工改过的 `contextWindow` / `cost` 覆盖掉。

**「全选」作用于筛选后的行，不是全部。** 搜索框里打着字的时候，「全选」如果连被你筛掉的也选上，这个意外会在保存之后才发现。

**这个功能真的有价值，不只是对齐截图。** 实测：用户的 `cz` 提供 **11 个**模型，而 `models.json` 里只配了 **5 个**——发现这个差别正是这一节存在的理由。

**删除的确认文案分两种，因为后果真的不同。** 凭据在 `auth.json` 里时，提示是「会移除其配置和存储的 API 密钥」；否则是「其使用的凭证（如有）由其他位置管理，将会保留」——环境变量给的 key 从来不是我们写的，删除 provider 也不该去碰它。两句都是 dsh 原文。

**图标从 dsh 的产物里取出来，逐字节相同。** 这一次新增了四个 glyph：侧栏齿轮、外观三个方块（`IconLightOutline16` / `IconDarkOutline16` / `IconFollowsystemOutline16`）。字号 stepper 的上下箭头共用一套 chevron，向上的那个是 `rotate(180deg)`，而不是第二份 path。

**图标是从 dsh 的产物里取出来的**。dsh 的工具图标表是 Figma 导出的（bash→终端方框、read→浏览、edit→铅笔、search→放大镜、其余→星芒），`dsh-icons.tsx` 里是逐字节相同的 path。它们是纯填充（`fill: currentColor`）而不是描边，所以没和 `icons.tsx` 那套描边图标混在一起。

**右侧导轨是会话的索引，不是会话的地图**。`TurnNavigator.tsx` 在每个轮次旁边放一条 12×2px 的圆角短线：悬停显示该轮的内容卡片，点击滚过去，键盘 Tab 也能逐个预览。轨道全长只有几条线，但每个标记承担的是「用户提的一个要求」而不是「一条消息」——分组在 `turn-rail.ts`，遇到 user 消息开新一轮，助手回复和它触发的所有工具往返都留在同一轮里。

**标记是等间距的**（10px 一档，`TURN_SPACING_PX`），这正是它能用一次除法反推指针落在哪个标记上的原因（`itemAtPointer`）；如果按内容高度摆放，它就不再是索引而是缩略图了。首尾各留 6px（`RAIL_INSET_PX`），整条轨道的高度就是 `(轮数-1) × 10 + 12`——实测 3 轮时 32px、标记中心整齐地落在 433/443/453。轮次多时封顶 420px 并在内部滚动，上下各用 `mask-image` 渐隐一段 24px 的带子，这样「被裁掉的轨道」和「就这么长的轨道」一眼能区分开。窄于 900px 时整个导轨隐藏（容器查询）——再窄它就要压在它本意要索引的文字上了。

**当前轮次是数出来的，不是猜出来的**：在滚动区顶部往下 `min(96px, 高度的 20%)` 处拉一条探针线，取最后一个起点在线上方的轮次（`turnAtLine`）。跳转用 `scrollTop += rowTop - 24` 而不是 `scrollIntoView`——后者没法在目标行上方留出固定空白，会把标题贴在面板边缘。跳转后若没落到底部就关掉自动跟随，否则下一个流式增量会把读者拽回去。

**三处与 dsh 的偏离，都是因为它有分页而我没有**：dsh 的轨道由「已加载窗口 + 未加载的 outline 投影」拼接而成，所以有 `markUnloaded`（8px、60% 透明）、「加载并跳转到第 N 轮」文案，以及点击后等待 `loadThrough(seq)` 的忙态；pi 一次读回整个转录，每个标记都是已加载的，这些状态没有对应物。另外 dsh 用 `100dvh - composer-height (152px)` 估算轨道所在带子的高度，我改成用 `ResizeObserver` 量滚动容器的实际高度——顶部多一条横幅或错误条时不会失准。

**一个真 bug 值得记下**。`syncActiveTurn` 用 `requestAnimationFrame` 节流，标志位是 `frameRef`；cleanup 里 `cancelAnimationFrame` 了却没把这个 ref 复位。于是 StrictMode 的双挂载在**第一次渲染**就踩中：effect 排队一帧 → 卸载时被取消 → ref 仍是非空 → 之后每次调度都认为「已经有一帧在排队」而直接返回，轨道永远停在初始状态（安安静静，不报错）。修复是 cleanup 里无条件把 ref 置回 `null`。

**卡片预算是 50 / 120 字符**（`PROMPT_PREVIEW_LIMIT` / `RESPONSE_PREVIEW_LIMIT`），对应卡片的一行标题加最多三行摘要，连同 `preview()` 里那个 `limit * 2` 的预读上限一起照搬 dsh——不设上限的话，轨道的工作量会随每一个回答的长度增长。截断是**按字符**切的（`word word w…`），不向词边界回退：卡片宽度已经由 CSS 的行数钳制决定，从这里再回退一次只会让它和真实文本差得更远。

**没有的东西是有意没有的**。dsh 的编辑行还带 `+18 -18` 的 diff 统计、把路径做成虚线下划线可点开的文件链接，并有一个悬停才出现的「查看」药丸。pi 的结果只给 `Successfully replaced 2 block(s)`，没有行级 diff；文件也打不开。这三样因此都没做——用参数行数近似出来的 `+N -M` 会是个看起来精确、实际错误的数字。

**路径做了一次缩短**：摘要若是工作区内的绝对路径就先转相对，再对 home 下的路径显示成 `~/…`（`shortenPath`，照 dsh 的 `relativizeToCwd` + `abbreviateHomePath`）。两者都只在整个字符串以根开头时才生效，所以 `cd /long/path && …` 这样的命令不会被改写。本机 5716 次文件类调用里 95% 是 home 下的绝对路径。

**目录选择器**：`/api/fs/list` 只返回子目录（符号链接指向目录时也会返回），以 `.` 开头的目录排在最后而不是隐藏（`~/.config` 这类目标依然可选）；路径经 `fs.realpath` 规范化，因此软链会被解析到真实位置。

## 已知限制

- 只在浏览器本地单机单人使用，没有账号体系；兜底的 Host/Origin 校验只挡浏览器发起的跨源请求，**不要把它暴露到公网**。
- 目录选择器浏览的是**服务端所在机器**的文件系统（本工具里就是本机）。
- 只有两栏；没有右侧面板、文件树、终端、diff 视图（轮次导轨是浮在对话流旁的一条窄轨，不算第三栏）。
- 工具调用以「参数 + 折叠输出」的通用卡片呈现，没有针对 edit 的 diff 高亮。
- **任务清单面板只显示最近完成的 3 条**完成项（其余折成 `+N 项已完成`），展开后的高度上限是 180px——长清单要靠滚动。转录里那次调用的展开体显示完整快照（不裁），但也有 260px 的滚动上限。
- **话题树只能看，不能把叶子移过去**：pi 没有移动 leaf 的 RPC，只有 `fork`（且仅限用户消息）。树里能分叉的节点有标记，点它走的就是分叉。
- **fork 创建的是新会话**，不是把当前会话截断；原会话一个 entry 都不会丢（已实测）。分叉后会自动切到新会话。
- 助手消息下的「赞/踩」**没有做**：pi 没有对应字段，也没有 RPC，做了也写不进任何会被读的地方。
- 「用时」是墙上时间（含工具执行），不是模型生成时间——pi 没有暴露后者。
- compaction 的可视化还没接。
- 设置页有「通用设置」和「模型」两节；插件 / Agent 预设 等还没有。
- 模型一节不列举未配置的内置 provider（pi 需要显式的模型列表，列出来也没有可填的东西），但可以**向提供方询问它有哪些模型**。这需要 provider 有一个 API 地址：内置 provider 的默认地址不归我们管，新建的 known provider 又还没保存，所以这两种情况下要先填上地址。dsh 的限制完全一样（`fetchNeedsBaseUrl: "请先填写 API 地址，再获取。"`）。
- 模型写入只对真实 pi 做过**读**的验证；写入用临时栈验证过（包括中途发现并修掉的字段丢失），但用户全局 `~/.pi/agent/*.json` 的写入每次都会先备份再原子替换。
- 模型状态点只反映两个配置文件，**环境变量提供的密钥看不到**（`@earendil-works/pi-ai` 不在依赖树里，拿不到它的 `findEnvKeys`）。措辞已经收敛成「配置文件里没有 API 密钥」，不会断言成「未配置」使环境变量用户去做多余操作。
- 没有「权限」和「语言」两项：前者在 pi 侧没有对应概念（`trust` 管的是项目动态配置的信任，不是工具执行级别），后者在单语言项目里只有一个选项。
- 设置页的下拉用原生 `<select>`：外壳是自绘的，展开的菜单是系统的。换取的是键盘、读屏、首字跳转全部由平台提供，不必重新发明一遍。
- 代码高亮固定浅色主题。
- `web/src/features/dev/TokenPreview.tsx` 是设计系统的自检页，不在路由里；需要时把 `App.tsx` 临时指向它即可。

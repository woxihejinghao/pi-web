# 设计说明

内部结构与设计取舍——**为什么**是这样，而不只是**是什么**。面向想读源码、改动行为或评估移植成本的读者；只想装来用，看 [README](./README.zh-CN.md) 就够了。

## 架构

浏览器不与 pi 直接说话，中间只有一个 Node 进程：上行命令走 `POST /api/*`，下行事件走一条 SSE。会话列表每次都从 pi 自己的存储实时派生，进程池按需拉起 `pi --mode rpc` 子进程、空闲回收。

```
浏览器 (React + Vite)
   │  POST /api/*            上行命令
   │  GET  /api/events (SSE) 下行事件
   ▼
Node 服务端 (单进程)
   ├─ 项目记录   ~/.pi-web-simple/store.json
   ├─ 界面偏好   同一份 store.json（外观 / 字号 / 对话显示 / 发送行为）
   ├─ 模型提供方 ~/.pi/agent/models.json + auth.json（pi 没有对应 RPC）
   ├─ 会话列表   从 pi 自己的存储实时派生
   └─ 进程注册表 每个会话一个 pi RPC 子进程（懒启动 + 空闲回收）
   ▼
node <pi>/dist/cli.js --mode rpc --session <file>   (cwd = 项目目录)
```

## 与 pi CLI 并存

这是这个工具的核心约束，也是几个设计取舍的来源。

**项目记录与会话是分开的。** `store.json` 只保存项目（路径、标题、顺序）和一条 UI 偏好（隐藏）。会话列表每次都从 pi 自己的会话目录实时派生，会话正文永远只有 pi 一份。因此终端和 Web 看到的会话始终一致，也不存在同步问题。

**`ask_user_question`、`todo` 与计划模式都只在 Web 侧加载。** 包的 `pi.extensions` 清单只剩 `/web` 一个入口，所以终端会话一样都不注册：工具清单里没有它们，系统提示里也没有问答那三条 Guidelines 与计划模式那一段——Web 启动的 pi 由 `server/src/presets.ts` 显式 `--extension` 带入 `extensions/ask-user.ts`、`extensions/todo.ts` 与 `extensions/plan-mode.ts`（与 `/web` 在极简 preset 里的处理同一条路数）。问答的理由不是「终端用不上」，而是批量问题被编码进 `select` 标题的那份格式只有认得的客户端解得开，而终端里最好的下落也只是把一批拆成一串原生对话框；把手写前缀喂给终端用户，比问他三遍更糟。任务清单的理由是它的载荷本身就是 Web 的投影（整份列表写在 `details.todos` 里，面板与转录行读的就是这个形状），而清单能带给终端会话的只有多一行工具。计划模式的理由介于两者之间：它的状态是日志里的一条 entry（谁都能读，见[计划模式为什么落在日志上](#计划模式为什么落在日志上)），但进入与退出的 chip、退出时那张审批卡、读全文的侧栏标签页、轮次尾部的计划卡片，以及侧栏的状态点，都是这个界面的东西。代价写在明处：pi 自己不带 todo，所以普通终端会话既没有这个工具也没有 `/todos` 覆盖层，想用得手工 `pi -e extensions/todo.ts`；另外两个同理。另一个代价是包清单不再用 glob，以后新增扩展也要在 `package.json` 里显式加一行。

**会话列表是按页取的，文件没动就不重读。** 派生一份列表的代价是整个工作区的历史：pi 要流式读完目录里每个 JSONL，才能数出消息条数、取出首条用户消息（标题与预览都来自它）——而侧栏只画 5 行。所以侧栏只问它正在显示的那一页（`limit`，默认是 dsh 的 5 条）加一个总数（`total`），「展开其余 N 个会话」的 N 就是两者的差；`focus` 让选中的那个会话即使排在页外也随这一页回来，对话区因此不会因为分页而丢掉标题。服务端把解析结果**按文件**缓存，凭据是那个文件的**大小与 mtime**：只要没变，重新解析不可能得到不同答案，而 stat 一遍比流式读一遍便宜几个数量级（102 个会话、178 MB 的工作区：整目录 672 ms，stat 一遍 1.2 ms）。这道检查每次请求都做，而不是信任文件监听——漏掉一个事件就会让列表一直陈旧下去。真正变的文件才重解析，而解析仍然交给 pi：把变化的文件**符号链接**进一个临时目录再喂给 `SessionManager.list`，拿到的就是同一份权威答案，不必去复刻 pi 私有的 `buildSessionInfo`。代价是 pi 对非默认目录会按 header 里的 cwd 过滤：凡是它不肯回答的文件（旧会话的 `cwd` 是空串、链接失败、读不动），就退回真目录整读一次，并把这个答案按文件记下——所以这种文件不会每次请求都触发回退。目录的现况同时充当删除对账：缓存里已经不在目录里的条目直接丢掉，侧栏删掉的会话不会因为缓存还挂着一行。同一目录的并发请求也不各读一遍：后来的等前一次读完再排进队列。实测同一工作区：全冷 672 ms，什么都不动 1 ms，动一个会话后 67 ms。前端相应地不再重复取：手里的行已经够这次视图画（`min(页大小, 总数)`）时就什么都不发，`sessions_changed`、重连、隐藏/删除这些真会变的路径才带 `force`。

**同一时刻只有一个写者。** 服务端保证一个会话文件最多对应一个 pi 子进程。如果终端里的 `pi` 正在写一个 Web 也开着的会话，文件监听会发现这次写入发生在 Web 自身活动窗口之外，于是：

- 侧栏对应行出现一个圆点；
- 对话区顶部出现「这个会话被其他进程修改过」的提示条；
- 点击 **重新载入** 会结束 Web 侧的进程、重新读取文件，之后由 Web 接管。

Web 不会静默合并两边的写入 —— 那样会互相覆盖 leaf 指针。

**新建会话是即时的。** 启动一个 pi 子进程要花 1.3–3.2 秒（冷启动实测 3220ms，从磁盘重开 1492ms；已驻留的会话只要 2–3ms）。所以点 **+** 不会等它，有两层保障：

1. **预热**：选中项目时就后台先起一个 pi 进程（`POST /api/sessions/prewarm`，请求本身立即返回，不阻塞任何 UI）。点 **+** 时直接接管它，实测 **2–3ms**；接管后立即在后台预热下一个，所以连续新建也一样快。
2. **draft 兑底**：如果预热还未就绪（刚切到项目、或上一轮已被回收），界面立刻切到一个纯前端的 draft（`draft:<random>`），pi 进程在后台启动，完成后把真实路径换进来（侧栏显示为「新会话 · 准备中」，对话区标题旁转圈）。这期间可以直接输入，发送时会等进程就绪再投递。

预热的进程从未被认领时不会产生任何文件（pi 只在收到第一条 assistant 回复后才写入 JSONL），并且：同一项目最多一个未认领预热（预热新项目会释放旧的），空闲 10 分钟后同样被回收。

**未落盘的会话是临时的。** pi 在收到第一条 assistant 回复之前不会创建 JSONL 文件。所以新会话在发出第一条消息并收到回复之前：

- 不会出现在服务端按磁盘推导的会话列表里；Web 端自己在 `unsavedSessions`（按项目记录，值是最新在前的路径列表）里跟踪它们，侧栏就按这份记录在对应项目下渲染「新会话」行；
- 因为这份记录属于会话而不是「当前选中的那个会话」，切换会话、切到别的项目、或再新建一个，都不会让正在运行的会话从侧栏消失（同项目下多个未落盘会话会并排显示）；
- 如果此时服务端的进程被回收（空闲超时、重启），它的上下文会丢失，`session_closed` 会同时删掉这一行。

一旦有了回复，文件落盘，`refreshSessions` 会把该路径从 `unsavedSessions` 里剔除，侧栏列表自动接手这一行。

**删除项目不等于删除数据。** 移除项目只删掉那条记录，目录和全部会话历史都留在磁盘上。

**重命名写进 pi 自己的文件。** 会话名只有一个落点：pi 自己 JSONL 里的 `session_info` 条目（`/name` 写的也是它，pi 读**最后一条**）。所以 Web 改名与终端改名是同一个动作，`pi --resume` 和侧栏不会对同一个会话给出两个名字。写入分两条路：有驻留进程时走 RPC（与流式写入在同一进程里串行），没有时用 `SessionManager.open()` 直接追加——不必为了改个名字冷启动一个 1.5–3.2 秒的进程。空名会把名字清掉，那就是「回到自动」：标题回落到首条用户消息。此前 Web 侧那份 `store.json` 覆盖项因此废除，只剩 `hidden`（dsh 没有「隐藏会话」这个概念，它用归档，所以这条不假装是同一个动作）。升级时启动阶段会把旧名字一次性搬进会话文件（在文件监听开始之前，幂等且失败不阻断启动）；会话在 pi 里已经有名字的，以 pi 的名字为准——两边都可能是用户写的，而日志里的那个才是现在唯一那个答案。

**模型起名是可选的，且默认不开。** 会话名只有一个落点（上一条），所以自动命名不是另一套机制，而是同一个写入路径的另一个调用者：第一条用户消息到达时问一次配置好的模型，拿到标题就写 `session_info`，拿不到就什么都不做（首条消息派生的标题已经在屏幕上）。默认关闭是因为这一页里只有它花钱——每命名一个会话就是一次额外的请求；开了之后也只问一次、只发首条消息的前 2000 字节、最多 32 个输出 token，而且用户改过的名字永远赢（调用前与写回前各查一次，late answer 盖不掉 pause 期间的手动改名）。只支持 OpenAI 与 Anthropic 两种线上协议，其余直接拒绝。

**删除会话是先关进程，再交给系统废纸篓。** 这是本项目里唯一会丢数据的操作，所以每一步都按“删错了能不能退”来定：先结束该会话的驻留 pi 进程（否则它继续握着文件句柄，下一次点击还会对着一个已经不存在的文件重启）；文件优先交给 `trash` 命令，与 pi 自己在 `/resume` 里的删除路径保持一致，删错了还能从废纸篓捞回来；系统没有这个命令（它不是 pi-web-simple 的依赖）时回退到 `unlink` 永久删除，两种结果在侧栏的提示里分开说。Web 端的隐藏覆盖项一并清掉——它按会话路径索引，留着只会永远指向一个不存在的文件，并在该路径被复用时突然复活。文件已经不在时接口返回 404，不谎报成功。

## 目录选择器为什么要走服务端

浏览器拿不到本地目录的绝对路径：`<input webkitdirectory>` 只给出相对路径，File System Access API 出于安全考虑刻意不暴露真实位置。所以目录浏览由服务端提供（`/api/fs/list`、`/api/fs/locations`），只列出子目录名，**从不读取文件内容**。

**拖放是同一道墙的另一个面。** 把文件夹拖到弹窗上时，桌面版由 preload 的 `getPathForFile` 拿到绝对路径（`webUtils` 在 preload 进程里读一次、只回传一个字符串，页面依旧不碰 `ipcRenderer` 与 Node），填进地址栏并打开那一层；浏览器里没有这条路，就退到“拖进来的文件夹名命中当前列表就进入同名项”——两边都不猜路径：够得着的就进入，够不着的就说明白。拖的是普通文件时什么都不做，否则那会变成一条把文件当目录递给服务端的路径，错误也在服务端才现形。

**地址栏当草稿来读，这一半照 dsh。** dsh 的选择器是 Miller 双列加一个路径编辑区：草稿的最后一段前缀过滤它命名的那一列，目录部分变了就防抖扫描把两列挪过去，所以“输入路径”与“走列表”是一个手势。这里只有一列，但读数留住：`path-draft.ts` 把“草稿命名哪个目录”与“哪一个尾段缩窄它”分开算，再交给一个 250ms 的防抖跟随。两条规矩是 dsh 的，也是能避免“一次按键视图动两次”的写法：过滤只打在草稿点名的那一层，以及没有任何行匹配时不缩窄（没人匹配的尾段是一个正在拼写的名字）。第三条不同类：地址栏停在当前目录时（导航之后的字面状态）必须读成“这一层就是答案”，不能读成“末段是该目录自己的名字”，否则每次导航都会把视图拉回父层再过滤一遍。另外服务端会 `resolve` + `realpath`，所以文本与落到的层未必同名（`~`、相对路径、macOS 上 `/tmp` 落到 `/private/tmp`），把“刚发出的目录文本”与“它落到的路径”成对记住就能让缩窄也认得。Miller 那一半（双列、选中列、两栏在窄窗口里的横向滚动）不搬：那是为“两列之间不来回动”服务的，一列没有这个问题。

因为无鉴权的服务端能枚举文件系统，所有 `/api/*` 请求都会校验 `Host`（以及存在时的 `Origin`）必须是回环地址。这样即使恶意页面通过 DNS rebinding 把自己的域名解析到 `127.0.0.1`，也会因携带非回环的 `Host` 头而被拒。

## 实现要点

**pi 的接入用的是官方 `RpcClient`**（`@earendil-works/pi-coding-agent` 已导出），但它有一个坑：`start()` 内部的 `cliPath` 默认是相对路径 `dist/cli.js`，而子进程的 `cwd` 是项目目录，所以必须显式传入 `getPackageDir()` 拼出的绝对路径。

**消息列表也来自 pi**：`SessionManager.list(cwd, sessionDir)` 直接给出标题、时间、消息数，`SessionManager.list` 的第二个参数是**该项目的会话目录**（`<root>/--<编码后的 cwd>--`），不是会话根目录；这个编码规则 pi 没有导出，在 `session-path.ts` 里复刻了一份。

**流式渲染没有累积快照**：`message_update` 只带增量，客户端必须按 `contentIndex` 自行拼装，并以 `message_end.message` 为准。

**SSE 只把「你正在看的那个会话」的 token 流发给你。** 一个 pi 进程的事件会广播给所有连接，但 `message_update` 是每 token 一条、而且带的是**增量**：四个标签页各自复制全部会话的全部事件时，扇出倍率就是 `会话数 × 客户端数`，实测 8 会话 × 4 客户端能把服务端写队列顶到 688MB、P50 延迟 1.2 秒（见 [bench](../bench/README.md)）。所以 `bus.ts` 的 `wantsFrame` 丢掉「不是这条连接订阅的会话」的 `message_update` / `tool_execution_update` —— 用黑名单而不是白名单：`agent_start` / `agent_settled`（侧栏状态点）、`extension_ui_request`（被阻塞的扩展对话框）、项目与会话列表照常发给每个客户端，pi 以后新增事件类型也不会被漏掉。客户端在 `hello` 里拿到 connection id，切会话时 `POST /api/events/subscription` 声明订阅；**声明之前服务端照发全部**，所以一次切换不会因为竞态丢帧，旧客户端也只是退化成原来的行为。

**连接自带背压，慢客户端会被断开而不是无限缓冲。** `res.write` 返回 false 意味着 Node 自己的写缓冲满了；忽略它继续写，就是上面那 688MB 的来路。现在返回 false 就暂停投递、把后续帧排队等 `drain`，队列超过 `SSE_MAX_BUFFERED_BYTES`（默认 4MB）就断开这条连接 —— `message_update` 带的是增量，丢弃会把转录写坏，断开反而让 `EventSource` 在一秒内重连（服务端发 `retry: 1000`）并重读一份权威快照。重连时前端会重新读一次当前会话（`streamRestored` 信号），因为断线期间漏掉的增量不可能被下一条补上。

**流式渲染有一个 50ms 的发布地板。** `message_update` 只按帧合并（`requestAnimationFrame`）在短回复里够用，但回复越长越不够：每个 delta 都要把**整段** partial 重新交给 react-markdown 解析，而帧率是固定的，于是成本随回复长度线性增长。压测（[bench 场景 C](../bench/README.md)，17.6 秒的长流式）里无节流时当前会话占到主线程 58%、8 会话并发直接打满；把发布下限提到 50ms（`STREAM_REPAINT_MS`）后两项都减半以上，观感仍是连续吐字。节流只作用于 token 流：`message_end`、`agent_settled`、工具结果这些事件仍然立即发布——它们是不能迟到的到达。

**延迟都被推到了有预期的地方**：界面从不等 pi。选中项目时后台预热一个空会话（点 **+** 实测 2–3ms，对比冷启动 3220ms），预热未就绪时退化到纯前端 draft，点已有会话则直接从磁盘读转录（见下）。进程启动的开销要么提前付掉，要么发生在用户已经在“等待回复”的心理预期里。待发消息通过 `pendingPrompt` 交接给真实会话，切换会话时会丢弃，不会误投。

**侧栏跟随 dsh 的信息层级**：顶部是全宽「新会话」按钮，下方是「工作区」分区，每个工作区展开后把它的会话嵌在下一层（会话行不重复文件夹图标，右侧只给紧凑的 `7天`）。工作区支持按目录祖先关系嵌套（`/a` 包的 `/a/b` 收在它下面，没有注册父目录的保持平铺）；每个工作区默认只列 5 条会话，其余折叠为「展开其余 N 个会话」。**还没列过的工作区不能读成空的**：侧栏只从 `sessions[projectId]` 画行，所以「请求还在飞」与「真的一条都没有」同形，而首次列出要服务端把整个工作区的历史读一遍（实测冷读 672ms，见上）。这种工作区现在先显示「正在载入会话列表…」，并由 `useDelayedFlag`（250ms，与转录那枚提示共用同一枚钩子）压住头几帧 —— 热工作区毫秒级返回，出现又消失的提示只会闪两帧，比不显示更差。标记只在「从未列过」时打：已经有行的重载继续画旧行、不退回空态也不闪提示，而读失败或请求被顶替都不会把提示留在屏幕上（只有最新那次请求能清它）。选中项照 dsh 只换底色（`--dsw-alias-interactive-bg-hover`，与悬停同一层），不加粗、也不换文字颜色。

**会话行那枚状态点是 dsh 的 `SessionStatusDots`，三档按 dsh 的优先级排：等待回答 > 进行中 > 已完成。** 有扩展正阻塞在这个会话上（`pendingUiRequests` 按会话路径命中）时先亮 warning 橙点，读屏文案「等待回答」—— dsh 的 `sessionStatuses` 也是先看待回答、再看活动；运行中共用 dsh 的 `StateDot`，但 `ongoing` 不是圆点，而是 10×10 视口里 8 个 2×2 方格绕成一圈、中间空着，逐格点亮（`dsh-state-dot-chase`，每格 125ms、1s 一循环，8 × 125ms 刚好一圈），颜色恒为品牌蓝 `--dsw-static-deepseek-450` —— dsh 把「工作中」排除在状态色之外，它不该读成告警；运行结束落成普通圆点（success 绿）。后两档按会话路径记：`agent_start` 点亮，`agent_settled` 时若用户没打开这个会话就留一枚「已完成」，打开会话即清除（运行中的标记不清），`session_closed`（进程被关）也清掉，否则点阵会一直转下去。流断了又回来时（`hello` 带着服务端当前全部的进程句柄）还会拿这份列表对一次账：运行中的会话必然有句柄，标记是 `ongoing` 却没有句柄，说明进程是在流断开期间没的（多半是服务端重启），此时收不到 `session_closed`，不清掉的话「进行中」就会永远转下去。三档都没有的空闲会话不显示标记，但**槽位本身保留**：dsh 的 `.slot` 是每行恒在的 16×20 格，只有里面的标记有无之分，所以空闲会话的标题和有状态会话的标题落在同一个 x，列表不会随状态出现或消失而整体左右移。

**「已完成」还有一枚浏览器级的对应物，但它只对应「完成」这半边。** 通用设置里的「浏览器通知」（`browserNotifications`，默认关闭）打开后，`agent_settled` 且用户没在看该会话时发一条系统通知：标题是**应用名**（`APP_NAME`），正文是「会话名 · 会话任务已完成」，列表里还查不到这个会话时只剩后半句；`icon` 传 `PI_MARK_URL`，也就是标签页上那枚 mark。这三项都是同一件事逼出来的：**通知上只有标题、正文、图标这三行是页面自己的**，最上面那行来源由地址决定（本机跑的就是 `127.0.0.1`，改不了），所以应用名只能写在标题里，会话名挪到正文；不给图标，横幅就退回浏览器自己的默认图。点击跳回该会话。**不通知开始**：任务是自己派出去的，开始不是一个需要把用户叫回来的消息；会走到通知这一步的只有「跑完了，可以来看结果」。默认关闭是因为权限提示只能由用户手势触发——页面加载时弹权限会被所有现代浏览器直接忽略——所以开关本身就是权限的申请入口：打开即 `requestPermission()`，拿不到 `granted` 就把开关弹回去并给一句提示，**绝不把偏好写进 store**，否则刷新之后开关会替一个永远不会出现的通知做担保。反过来说，权限被用户在浏览器设置里事后撤销时，这里不去自动改写偏好，`showNotification` 自己按 `permission` 静默跳过：用户没改变过选择，替他改是另一种撒谎。**「没在看」是两个条件的合取**：会话在阅读位上（`selectedSessionPath`），**并且**那个页面真的在用户眼前（`pageIsAttended()`：`visibilityState === "visible"` 且 `document.hasFocus()`）。这两半会各自失效——切到别的标签页、最小化都算隐藏（浏览器只看标签页在不在前台，不判断窗口有没有被挡住），而焦点在别的应用上则会让 `hasFocus()` 为假，哪怕窗口就摊在屏幕别处——而只按「选中了没有」判断，恰好把所有真需要的场合都吞掉：会话开着、人已经去干别的，跑完一声不响。侧栏那枚 done 点仍然只问「打开没打开」（打开就是清除它的动作），所以一个人在后台跑完、回来接着读的会话不会留一枚没人会去点的点——两者看的是同一批完成，只在「用户在不在」这一步分叉。也**不再要求本标签页看见过这次开始**：`agent_settled` 是实时帧、这条流不重放历史（`wantsFrame` 只按订阅过滤 token 增量），收到它就等于刚刚跑完；按「见过 start」判，会把刷新页面时正在跑的那次一并吞掉——而那正是最需要提醒的一次。没有 `document` 的宿主（单测）一律算「在眼前」：观察不到用户时，那帧仍然是一次真的完成，宁可多弹一条一秒就能划掉的横幅，也不吞掉这条路径存在的理由。`tag` 用会话路径，同一会话的第二次完成替换掉第一条，而不是把同一份消息叠成一摞。

**顶部那枚「新会话」是 dsh 的 pill，不是自绘的方块。** 度量逐项照 `SidebarRoot.module.css` 的 `.newSession`：`--dsw-radius-md`（12px）圆角、38px 盒高、`8px 12px` 内边距、14px/22px 文字、6px 图标间距，以及按钮自己那侧向 2px、下边 12px 的外边距；填充用 `--dsw-alias-button-elevated-fill`（浅色下就是白，深色下是 `neutral-bluish-750`），悬停才换成 `--dsw-alias-button-floating-hover`。那根 `0.5px solid var(--dsw-alias-border-l3)` 是 dsh 原件写在 border 上的，不是 elevation 阴影里的发丝，所以这里也留成真 border。**这一条曾经偏离过**：早先把 12px 圆角改成了 14px，理由是想与下方的输入卡呼应；而 dsh 给的是 12px，且它周围的每一行都是 12px，一个 38px 的盒子跟着邻居走比跟着一个它并不相连的输入卡走更对。

**左侧栏的几何是 dsh 的，来自两张表。** 列本身（`6px 12px` 内边距、60px 品牌行、38px 新会话条、36px 分组头、42px 设置项、l3 的列分隔线）照 `ui-sidebar/SidebarRoot.module.css`；行（工作区 34px、会话 32px、14px/20px 标题、10px/16px 时间戳、标题与时间戳分别是 `label-primary` / `label-tertiary`、`--dsw-radius-md` 圆角、悬停与选中同用 `--dsw-alias-interactive-bg-hover`）照 `ui-workspace/rows/Rows.module.css`。这两张表也是 `--dsw-radius-*` 四档 token 的来源，它们随这次一起补进了设计 token 表。列宽从 268px 提到 dsh 的 `SIDEBAR_DEFAULT` 280px；dsh 的 264/420 拖拽上下限这里用不上——这个壳没有侧栏拖拽把手，宽度就是那个默认值。滚动条照 dsh 贴到列自己的右边缘：负外边距抵消列内边距，再用 `edge − 滚动条 − 2` 把行放回原位；公式读的是本项目自己的 `--dsh-scrollbar-width`，不跟 dsh 的 5px——要跟的是行的落点，不是滚动条本身的粗细。

**侧栏的底色不是一块平涂，而是两道光晕叠在填充上；macOS 上填充本身再让位给窗口毛玻璃。** dsh 的 `AppFrame.module.css` 给 `.sidebarCol` 的是一条 `to bottom` 的渐变：顶部一道蓝、到三分之一处化没、底部三分之一再抬起一点蓝灰紫 —— 这就是侧栏那道从顶到底的柔光。这里逐值照抄（浅色 / 深色两套），而且**光晕在所有平台都留着**：压在不透明填充上读到的就是同一层柔光，没有理由只给一个平台。**填充的半透明则只在 macOS 生效**，因为那正是 dsh 为 `vibrancy` 材质留的透光口。透明链共三节：`desktop/src/main.cts` 在 darwin 上开 `vibrancy: 'sidebar'` 并给窗口透明背景；`theme/index.css` 把 `html`/`body` 的底色收掉（`design-platform.css` 画在 `body` 上的页面底色必须让开，否则毛玻璃被它盖死）；`AppLayout.module.css` 的列把不透明填充换成 dsh 那份 40%（浅）/ 50%（深）的着色，列分隔线也跟着从这条半透明列挪到不透明的中间栏 —— 留在半透明列上会和壁纸混成一道深缝（dsh 把分隔线画在 `.centerCol` 就是同一个理由）。系统「减少透明度」打开时照 dsh 退回 90% 不透明的同色填充。`html[data-platform]` 这个开关属性由 web 侧从壳的 bridge 上转印（`lib/desktop.ts` 的 `markDocumentPlatform`；dsh 是它的 preload 直接写，这里的 preload 有意不碰 DOM），纯浏览器没有这个属性，于是侧栏保持不透明、不进任何桌面分支。

**macOS 的窗口顶部是 `hiddenInset`，拖拽改由页面自己标的行提供。** 半透明底色要一直跑到窗口顶边，就不能留一条不透明的标题栏横在那里：窗口因此用 `hiddenInset`（保留系统红绿灯，只把那条带子画成透明），红绿灯按 dsh 的 `(16, 18)` 内缩。透明带换掉了原生标题栏这块拖拽区，拖拽就改由页面里打了 `data-window-drag` 的行提供 —— 侧栏顶部一条 52px 的条（负外边距抵消列内边距，让它的盒子够到窗口上缘）、品牌行，以及中间栏顶部（有会话时就是对话头部本身；新会话时没有头部，那里另渲染一条 40px 的空行），正好是 dsh 的那几处。Electron 按几何合成 app-region（不看层叠），所以两条规则让这些行仍然可点：交互控件（`button` / `input` / `[role]`…）自己 `no-drag` 退出，portal 到 `#root` 之外的浮层（行菜单、标签菜单、对话框）由 `body > :not(#root)` 一并退出 —— 与 dsh `ui-web/src/base.css` 的两条一一对应。品牌行再上提 12px 缩回条子下面，让 π 字标落在红绿灯下方（红绿灯约到 y 30，字标从 y 48 起）。同一个红绿灯带也会压着设置页：那一页整块盖住外壳（`SettingsPage` 取代 shell 渲染），左栏第一件东西就是「返回应用」，于是它按 dsh 的 `--dsh-frame-top-clearance`（48px，声明在 `html[data-platform='darwin']` 上）把左栏整体下移，返回按钮落在 y 48，不再和控件叠在一起、也不再被它们吃掉点击。Windows 与 Linux 不跟：那里照旧用平台自己的标题栏，不自绘顶部行。

**缩进用的是行内 `padding-inline-start`，不是外边距，而且两层同缩进。** 被外边距推开的是整行连背景一起，而 dsh 的悬停/选中填充是要铺满整列的；会话行也不再比工作区行多缩 26px，因为 dsh 两个层级共用同一个 `--dsh-workspace-indent`（每层 12px，这里原来一层 16px）。工作区行因此还多拿那 2px 组间距，凑出 dsh 的「组内 2px、组间 4px」节律。一处刻意不跟 dsh，在代码里注明：品牌是字母标记而不是字标美术件。行的操作按钮一度是第二处（绝对定位的一簇），现已回到 dsh 的 flex 行，见下一段。

**搜索框是 dsh 分组头里就地展开的那个，不是另起一行。** dsh 的搜索活在「工作区」分组头内部（`ui-workspace/rows/WorkspaceBrowser.module.css`）：收起时是分组头右侧一枚 28px 放大镜 —— 在「工作区」标签与「添加工作区」之间，`margin-left: auto` 把它和尾部动作一起推到右侧；点它（或整行）展开成一个 30px 的胶囊：`border-l4` 的 0.5px 发丝、`--dsw-radius-md`（12px）圆角、透明底，8px 的圆角只在收起时出现。同一下「工作区」标签（`max-width: 45%` → 0）与尾部动作（`max-width: 60px` → 0）让位，输入框 13px/18px 淡入，放大镜缩到 11px，右侧多一枚 24px 的清除按钮。这些取值逐个照搬，改的是它落地的状态模型：dsh 用组件内的 `searchExpanded`，这里仍用 `app-state` 的 `searchOpen` / `sessionQuery`（`sessionQuery` 还要驱动列表筛选与「把分页的工作区拉全」），于是 `toggleSearch` 拆成 `openSearch` / `closeSearch` —— 收起一定连查询一起清掉，因为一个看不见的筛选条件既无法发现也无法清除。交互三条也照 dsh：点击整行（不止图标）聚焦输入框；Escape 与清除按钮都是「清空 + 收起」；点别处一律失焦，但只有查询为空时才真正收起。

**视图选项菜单把 dsh 的三种分组和两种排序搬了过来，但默认值刻意不同。** dsh 在分组头右侧放一枚 28px 的 `IconSlidersTwoOutline16`，点开是一个带组标题的浮层（`ui-workspace/rows/WorkspaceBrowser.tsx` 的 `ViewOptionsMenu`）：`分组方式`（按工作区 / 按工作区树 / 单列表）+ 分隔线 + `排序方式`（手动排序 / 最近更新），当前项在行尾带一枚 14px 的勾，组标题 11px `label-tertiary`、每行 30px（dsh 的 `dense`）、分隔线 0.5px `border-l2`。这些取值逐项照搬，落地在 `sidebar-view.ts` 加 `ViewOptionsMenu.tsx`：状态是 `groupBy` / `orderBy`，缓存在 `localStorage` 的 `pi-web-simple.sidebar-view.v1`（dsh 由它的 store engine 的 `persist` 键持有，这里没有那套引擎，就照右侧栏布局的老办法自己读写）。**唯一不跟的是默认值**：dsh 默认 `workspace`（工作区平铺），这里默认 `workspace-tree` —— 嵌套是菜单出现之前这个侧栏唯一的分组方式，而且本项目的项目是「一个目录一个地注册」的，一个 monorepo 会一次进来好几层路径；菜单一键就能换成平铺，反过来却不是不知道树存在的人能做到的。`flat`（单列表）没有工作区行，也就没有「展开其余 N 个会话」，所以它要求整份列表：`refreshSessions` 在这一点上把 `limit` 放开成 undefined，`setGroupBy('flat')` 顺手把每个工作区都拉全。

**手动排序把「排列」当成两件不同的事：工作区归服务端，会话归这个浏览器。** dsh 的工作区顺序本来就在 Host 里（拖拽走它的 `insertWorkspaceBefore`），这里已经有对应的 `PUT /api/projects/order`，所以 `moveProject` 只算落点、把整份 id 顺序交给服务端；`moveWorkspace` 的落点语义是「插到这个工作区之前，或（没有锚点时）最后」，与服务端「必须列出每个项目恰好一次」的校验对得上。会话则相反：dsh 把每个 account 的手动顺序存在浏览器本地（`sessionOrderByAccount`，单列表另有一个 `__flat_session_order__` 账户），这里同名照搬（`FLAT_ORDER_KEY`），拖拽只写 `localStorage`。**两侧都只认同一个父级内的移动**：工作区只跟同级兄弟换位（`parentOfMap` 就是这条规则的全部），会话只在同一个 account 内换位 —— 把 `/a` 拖进 `/b` 的子树改变的是路径模型而不是顺序，与其静默重排不如拒绝，dsh 的 `compatibleDrag` 也是这么卡的。已经落到磁盘的会话都能拖，唯独浏览器自建的草稿不行：它还没有文件，也就没有位置可存，dsh 同样把它排除在拖拽之外。

**拖拽状态住在整棵树上，不在某一行里。** 一个工作区可以被丢到另一个（不同的）树节点的头上，两行必须对「正在拖什么、标记画在哪」有同一个答案，所以 `useSidebarDrag` 由 Sidebar 持有、每个行只拿自己那一份接线（dsh 把同样的状态放在它的 `SessionTree` 上，行拿到的就是 `RowDragProps`）。**唯一真相源是 ref 而不是 state**：`dragover` / `drop` 可能在 React 重渲染发起拖拽的那一行之前到达（指针一移动浏览器就发事件，而指针下面那张 DOM 是上一次提交画的），从 state 读的话，行会把一个它还没见过的拖拽判成「别人的」并拒绝落点；因此所有判定都读 `live.current`，state 只负责让标记重绘。插入标记是 dsh 的 `::before`/`::after` 原件：两段 5×7 的 45° 渐变拼出一个左端小箭头，接一条从 x=4 到行右内缩的 2px 实线，颜色 `--dsw-alias-state-business-primary`；会话行 `right: 4px` / `top: -7px`，工作区行铺到右边缘、外扩到 `-8px`（行更高，两个标记会被放在一起看）。文档级还挂了一对 `dragover`/`drop` 监听：指针在行外松开时，浏览器的默认处理会把落点画成「拒绝」，那会在 `dragend` 提交最后一个标记之前闪一下。

**图标取的是 dsh 的 `ui-primitives/src/icons/index.tsx`（chrome），不是工具行那一套。** 这里有两套 dsh 图标很容易混：工具行（`dsh-icons.tsx` 里的 `terminal` / `browse` / `edit` / `code` / `search`）是 Figma 导出的**填充**图形，而侧边栏的 chrome 是**描边**的 `Icon*OutlineRegular`（1px）—— 只有极少数是填充（展开三角、省略号的三个点）。侧边栏每一枚都按 chrome 那套取：新会话=气泡加号、搜索=描边放大镜、重命名=方框加笔、删除=描边垃圾桶、设置=描边齿轮；工作区的文件夹、展开三角、溢出省略号也一并换成了当前 artwork。注意**两套里的同名图标不是同一枚**：`search` 是工具行的填充放大镜，`searchOutline` 才是侧边栏的，所以它们各自一个 glyph 名、不互相顶替。为了让「半填充半描边」那两枚（`projectAdd` 的加号、`rename` 的笔）能画对，`Glyph` 多了一条逐 path 的 `stroke` 开关 —— 原先只有 glyph 级的 `strokeWidth`，一个开关没法同时画出两半。

**整行都是切换目标，而不只是标题文字**。会话行的标题按钮用一个拉伸的伪元素（`.sessionTitle::after` + `inset: 0`）铺满整行：仍是**一个**真实控件（键盘焦点和读屏不会看到多余东西），但行的内边距、时间戳、以及短标题旁边的空白都算在内 —— 实测非悬停状态下 225px 行宽的采样 76/76 全部命中。一个容易踩的坑：`inset: 0` 必须相对已定位的 `.sessionRow` 解析，否则只铺开标题自己那么宽。

**会话行的操作按钮是行里 `flex: none` 的一员，不是绝对定位的一簇 —— 悬停时标题因此是被挤到按钮左侧，而不是被按钮盖住；按钮的悬停态也只提亮颜色，不铺底色。** 早先那版把按钮绝对定位在行右侧，再用一条从透明开始的渐变把时间戳压掉：绝对定位不占位，`flex: 1` 的标题便仍按整行宽度排版，长标题一直排到图标底下，文字与图标叠在一起（就是「标题遮挡图标」那一眼）。dsh 现在的 `Rows.module.css` 是把它放回 flex 行 —— 悬停时按钮入场、时间戳退场，标题自动收缩，从不重叠。整行点击目标不受影响：`.sessionTitle::after` 是定位元素，按钮簇只需自己一条 `position: relative`，就按 DOM 顺序排在它之上并保留自己的点击，不再需要 `pointer-events: none` 那套「把透明的一截让出去」的把戏。按钮的悬停态也照 dsh 的行内规则来：默认 `label-tertiary`，悬停只升到 `label-primary`，**不加背景** —— 灰色方块是头部那枚 28px 控件（`SidebarRoot.module.css` 的 `.iconButton`）的语言，行内按钮所在的行在指针下已经有底色，再加一块就是两层。最后还照 dsh 补上了「菜单打开时钉住这一行」：工作区行的菜单 portal 到 `document.body`（见 `.projectMenu`），指针一旦移到菜单上，行就脱离了 `:hover`；dsh 用 `.projectRow.menuOpen` 让有下拉菜单的行保持底色与按钮，这里也随 `menuAt` 给行加同一枚类。

**右侧栏是「每会话一份的面板」，不是全局抽屉。** 布局（打开态、呈现方式、宽度、标签页列表与选中项）按会话路径分支，键为 `pi-web-simple.rightbar.v1.<sessionPath>`；切会话看到的是那个会话自己的面板，刷新后恢复（**但恢复成关闭态** —— 打开面板是头部那次点击的事，页面加载不该自己弹一个出来，这一条照 dsh）。draft 会话不落盘：它的路径一秒钟后就会被真实路径替换，存下来只会在下次多出一个不会再出现的键。首尾两条 dsh 规则也照搬：**面板打开时若没有标签页就先种一个「文件」页**（于是永远不存在空面板），**关掉最后一个标签页就一起关掉面板**（于是不需要单独的「关面板」手势）。标签页四种：文件、预览、变更、浏览器。`+` 菜单给出可以直接新建的三种（文件、变更、浏览器）——预览不在里面，它从文件树或变更面板点开，一个地址就是一个标签；文件与变更每个项目只允许一个实例（同一个工作树只有一份文件树、一份改动）。

**标签上的右键菜单关的是「一组」，而关标签是这一层唯一会杀进程的动作。** dsh 的停靠组件自己在标签菜单里只放一项——关闭本标签——其余留给扩展位（`sidebar.right.tab.menu.item`）；这里就照那个位置放它自带的一项，再在它后面追加「关闭其他标签页」「关闭全部标签页」。它恒定排在第一项，因为「每次都在同一个位置找到同一项」比省一行更值钱；而只剩一个标签时**只**给这一项——三个名字说同一件事比一个更难读。菜单渲染进 `document.body`：标签条是**故意**横向滚动的（四个标签时不让每个标题缩成两个字），画在它里面的菜单会跟着一起被裁掉、被滚走，dsh 为同一个原因也这么做。**「关掉标签会连 shell 一起杀」这条规则只此一处**：它原先写在 ✕ 的 `onClick` 上，那时 ✕ 是唯一的关闭入口；现在菜单能整组关，规则就收进 `close-tabs.ts`，✕ 也改走它，于是不存在第二份拷贝。折叠侧栏、切会话、刷新页面都只断开、不杀——后台跑着的构建因此不会被收起侧栏掐断。

**终端标签页在这个版本从右栏撤下了。** 撤销的范围只到界面：`+` 菜单、空面板的引导卡与 `Ctrl` + 反引号都不再提供入口，`parseSurface` 读到 `kind: "terminal"` 的标签会当作不可达记录丢掉，所以旧布局不会带回一个既画不出也打不开的标签。服务端的 `/api/terminal` 路由、`TerminalTab`、`terminal-state` 与 `close-tabs.ts` 里那条「关标签就杀 shell」的规则都还在，`node-pty` 仍是可选依赖；恢复入口时不必重写它们，但眼下这层代码没有界面调用方（`TerminalTab.test.tsx` 与 `terminal-state.test.ts` 仍在跑）。



**分屏是两个窗格，不是一棵还能再分的树。** dsh 的停靠模型是一棵归一化的递归 split 树（`engine/tree.ts` 的 `nodes` / `rootId` / `floats` / `activePaneId` / `expanded` / `mode`），这里是一份扁平的 `panes: RightbarPane[]`（最多两格，`MAX_DOCK_PANES`）加一条可选的 `sizes: number[]`。这不是图省事：**dsh 自己的右侧栏就用不到递归形状**——`SidebarRight.tsx` 把 `canSplit` 限成「当前只有一格」、`dropZones` 写死 `"horizontal"`，而 `TabLayout.tsx` 在「既不是一格、也不是两格横切」时直接抛错。那棵树在那个入口下只有两种形态，用数组表达它就少一层永远走不到的递归；代价是没有分屏方向可选（只有左右，没有上下），这一条写进了[已知限制](./known-limitations.md)。

**浮窗不是第二种东西，而是 `host: "float"` 的窗格。** 这一条是照 dsh 的模型抄的：浮窗与停靠窗格是同一个类型，差别只在 `host` 和「不画标签条」——它只装一个标签页，而一个装不了第二个标签的条没有东西可选。所以它的正文走同一个 `TabBody`，`unfloatPane` 把它收回来时标签自己的状态（shell、滚动位置、地址）什么都不丢。布局每会话一份落盘（`pi-web-simple.rightbar.v2.<sessionPath>`，v2 那一版起包括 `floats`），刷新后浮窗还在原来的位置。

**被清空的停靠窗格一律合并掉，而且从不补种。** 两处与 dsh 不同，原因都是这里没有树。dsh 只合并「不是根节点」的窗格，因为树需要一个节点待在那里；这里是数组，没有必须保留的根，所以**每一个**被清空的窗格都消失，`sizes` 在同一步作废（`settleDock` 是唯一做这件事的地方）。反过来，dsh 会在合并后 reseed 一个 guide page 把空位填上，这里不补种：文件树与变更面板是**每项目一份**的视图，补种等于把同一个项目的文件树画两遍。

**被拖出左上角的浮窗，两个轴都钳回 0。** dsh 的 `movedRect` 只钳顶部，因为它假设抓手总在可视区里；这里的抓手就是浮窗自己的头部，浮窗左边缘或上边缘被推出视口之后，唯一能抓的地方就跑到屏幕外了——于是两个轴都钳，代价是它不能骑在视口边缘上。

**缝隙必须画在两个窗格之间，这一步踩过一次真坑。** `PaneTree.tsx` 在 dsh 里把分隔条渲染在**每一个 cell 之前**（`{index > 0 && <div className={css.divider} />}`），所以它落在两个窗格中间；这里一开始是 `panes.map(...)` 之后再追加一个，于是它成了行的最后一个子元素——宽度 0、发丝线 0.5px、`role="separator"`、8px 命中区全都照旧，看起来一切正常，只是画在行的**末端边缘**：那里没有缝隙可画，那 8px 的抓手也伸到了视口之外（实测 `x = 1280`，窗口宽 1280，`elementFromPoint` 返回 null）。这类错误静态断言抓不到，是探针里那一段「按住缝隙往左拖、量两格宽度」把它揪出来的；现在 `Rightbar.test.tsx` 也钉了一条断言，比对分隔条在标记里的位置确实夹在两个窗格之间。

**浮窗层的层级写在 CSS 里，不写在行内样式上。** 浮窗原来是按深度算 `zIndex: depth + 1`（拖拽中的那个再用 `floats.length + 1` 抬顶），而行内样式压过样式表里的 `.float { z-index: 40 }`，于是整层落到了 1——低于它本该浮在之上的东西：停靠栏 30、应用外壳 20、侧栏 40。几何断言全都照样通过（位置、尺寸、portal 都对），只是面板在跟侧栏重叠时会画在侧栏底下。现在两个高度都在 CSS：`.float` 是 40，被手势抓着的那个加一枚 `.floatLifted` 到 41。层内的先后交给**绘制顺序**（浮窗按底到顶渲染，所以后来者在上），这也是 dsh 的模型——它给每个浮窗同一个 `--dsh-dockkit-float-layer`，靠 Grid 顺序分层。

**拖拽要有一层盖住视口的遮罩，因为指针捕获过不去进程边界。** 这是本层唯一一处 dsh 没有的东西，理由是一个实测出来的浏览器行为：`sandbox=""` 的框是不透明源，浏览器给它**单独一个渲染进程**，而 Chromium **不把父文档的指针捕获带过去**——指针一进那个框，父窗口就再也收不到 `pointermove`，也收不到 `pointerup`。停靠栏里的 HTML 预览正是这样的框（`html-frame.ts`，见上文那两把锁），于是「把标签拖到预览上放」这条最自然的操作会**卡住**：提示层留在屏幕上、手势永远不结算，直到下一次按下把它顶掉。这不是监听器写法的问题——事件在任何属于我们的处理器跑之前就已经被路由到另一个进程了，父文档里没有任何办法补上。能修的是**不让指针进那个框**：手势期间给整个视口盖一层透明的 `gesture-shield.ts`（`data-rb-shield`，z-index 45），命中测试落在它身上，而它在这个文档里。指针捕获仍然生效，并且**照旧把事件（包括兼容鼠标事件）重定向回手势起点的那个元素**，所以这层遮罩偷不走标签的点击——「按下标签、松手在标签上」仍然是一次切换标签的点击。它按引用计数挂载，因为「新的一次按下顶掉旧手势」会让两个手势重叠一帧；它的生命周期就是 `AbortController` 的生命周期（松手、取消、被顶掉、卸载都走 abort）。遮罩用**行内 DOM 而不是 React 元素**：它必须在浏览器路由下一个指针事件之前就在文档里，而手势自己的预览要等到「触发它的那次移动」之后的那一帧渲染才进 DOM。遮罩期间的指针样式由于势自己提供（`GestureFollowers.cursor`），因为这时指针底下已经不是那枚抓手了——拖标签是 `default`，拖缝隙与栏边缘是 `col-resize`，拖浮窗头部是 `move`、拖它的角是 `nwse-resize`（后四个都是 dsh 画在同一处抓手上的值）。

**四个手势共用一个「一次只跑一个」的机制。** 停靠栏与浮窗层的手势都从 `pointer.ts` 的 `useGesture` 出发：一次只允许一个手势，每个手势只认发起它的那个 `pointerId`，结束（松手 / 取消 / 被下一次按下顶掉 / 卸载）时统一跑 `reset` 清掉预览。栏边缘那条 5px 的抓手原本自己写了一套 `useRef` + `onPointerMove` + `setPointerCapture`，现在也改走同一条路——它原来只在指针留在文档里的时候才收得到移动，而它的左边正是对话区。改完两边都短了一截，也顺带把「遮罩盖住自己、自己的 `onPointerMove` 再也不触发」这种自相矛盾的写法去掉了。

**呈现方式两种，`push` 与 `fullscreen` 共用同一棵内容树**（切换不重挂标签页，正是 dsh 的做法）。`push` 时面板是 shell 的第三列，宽度由左边缘 5px 的 `role="separator"` 拖拽决定：拖动过程中只改内存（每帧写一次 localStorage 是白花），松手才落盘；`fullscreen` 直接 `position: fixed; inset: 0` 覆盖视口，下面的列不动，所以退出时没有重排闪烁。宽度上限 900px、下限 300px，越界即钳制。

**文件读取走的是项目根的相对路径，不是绝对路径**。`/api/projects/:id/files?path=` 与 `/api/projects/:id/file?path=` 两个端点都先做词法校验（拒绝 `/` 开头、盘符与 `..`），再 `realpath` 两次比较（项目根与目标都要 canonical），因此**指向项目外的符号链接会被拒绝**而不是被跟随——这一步是必须的：服务器没有任何鉴权，一个能按绝对路径读文件的端点就是一台通用文件读取器。目录只列**一层**（`readdir` → 目录在前、自然序大小写不敏感；上限 500 条，超出给一行「仅显示前 500 项」），展开时才取下一层且折叠后缓存保留。

**预览有六个形态，判据分两层。** 服务端只回答四选一：`text`（UTF-8）、`image`（base64）、`pdf`、`unsupported`。`unsupported` 是**一个答案而不是错误**，所以它走 200 而不是 4xx：已知的二进制容器（office、压缩包、音视频、字体……）直接给理由，没列出来的靠「读出来的第一个 NUL 字节」判定。`pdf` 与它分开，是因为两者说的是不同的事——「这里画不了」和「谁都画不了」：PDF 有自己的查看器，也就是浏览器那个，所以 `/api/projects/:id/raw` 把字节按 `application/pdf` 流给一个 iframe，这个标签页既不读也不重新编码它（`content-type` 加 `x-content-type-options: nosniff`：那个类型正是「谁来画」的判据，而 PDF 的框**故意不加沙箱**，因为要看的是查看器而不是文件）。前端再按扩展名决定画法：Markdown 走对话里同一个 `Markdown`，`.html`/`.htm` 走沙箱 iframe，其余文本按有没有 shiki 语法分成代码和纯文本，图片走 `<img>`（含 SVG——它画在 `<img>` 里，脚本不会执行）。

**沙箱 iframe 有两把锁，因为这个应用自己一个安全响应头都不发。** `sandbox=""` 是浏览器给的承诺：脚本、表单、跳转一概不发生，而且框拿到的是不透明源，文档读不回宿主。`html-frame.ts` 再往文档里塞一条 CSP（`default-src 'none'`、`script-src 'none'`、图片/字体/媒体只许 `data:`、连接与表单全关），因为一个不跑脚本的页面仍然可以用一张图片的 URL 把看到的东西带出去——`sandbox` 管不住「取」。策略必须**写在文档里**：`srcDoc` 的框没有自己的响应可以带头，而 pi-web 服务端本来就不发任何安全头，没有东西可继承。插入位置也有讲究——`<meta>` 里的策略只管它后面解析到的内容，所以它落在 `<head>` 之后；没有 head 就落在 `<html>` 之后，再没有就落在 doctype 之后（无条件前置会毁掉 standards mode，因为不在首位的 doctype 会被忽略）。**没有 dsh 的第二条路**：dsh 在开启开发者工具时会把本地脚本与样式内联成 blob URL，让页面真的跑起来；这里没有那个开关，「已禁用脚本与外部资源」是一句陈述，不是一个状态。

**框的背景是白的，不跟主题走。** dsh 的预览框用 `--dsw-alias-bg-base`，但那里画的是 dsh 自己的渲染结果；这里画的是**别人的**文档，一份不写背景色的 HTML 在深色主题下就是黑底黑字。内嵌浏览器的框早就是这个理由这么做的。

**超出一屏的文本改成翻页，而不是截断。** 整份读取的上限是 1 MB，超出后原样只在上方写一句「仅显示前 1 MB」——读者被留在文件开头，而后面再也够不着。现在这种文件连那一段都不画，改走 `/api/projects/:id/text`：一页上限 256 KB 且最多 2000 行，**一定在一行结束后收尾**（唯一例外是单行本身就超过一页，那时按字符边界切开，`utf8SafeCut` 从窗口最后一个字节往回找到那个序列的首字节，把整个多字节字符留在同一边），返回 `nextOffset` 与 `eof`。按**字节偏移**而不是行号寻址：行号要先读完它前面的一切才知道在第几行，40 页之后的日志会重扫 40 个越来越长的前缀，而偏移让整趟走读变成每个字节只读一次。前端一次只画一页，页与页之间用一条写着行号的虚线标出接缝，底下是「读取更多」与「已显示 N 行」。**不自动加载**：一个几百 MB 的文件不该因为滚到底就把浏览器吃掉，翻页也因此从不是「意外多读」。

**翻页时那一页画成纯文本，哪怕它是源码。** 接缝必须看不出来，而按页调 `CodeBlock` 会在一个本没有接缝的文件中间插进语言标签和复制按钮；一页一页分别高亮，也把「只看屏幕内那几块」这件事丢掉了。行号标在接缝上，所以定位依然读得出来。

**只有文本会被翻页，Markdown 也不例外。** 判据是服务端那句 `truncated`——它说的是「这一次读取没能装下整个文件」，而一个 2 MB 的 README 用 `Markdown` 渲染出来只会是灾难。图片与 PDF 不参与：前者超限直接拒绝（半张图比没有更糟），后者根本不经过读取这一步。

**内嵌浏览器是沙箱 iframe，历史由自己记。** 地址栏与工具栏的后退/前进都在本地 `history[]`/`historyIndex` 里（每条上限 50 项），输入新地址会像浏览器一样截断前进项。默认沙箱与 dsh 相同（`allow-scripts allow-forms allow-same-origin allow-popups allow-popups-to-escape-sandbox`），工具栏保留一个「仅本次生效」的关闭开关。**一处与 dsh 不同的取舍**：dsh 给无 scheme 的地址一律补 `https://`，这里对回环地址（`localhost`、`*.localhost`、`127.*`、`::1`）补 `http://` —— 这个标签页存在的理由就是本地 dev server，给它一个 https 地址等于永远打不开，而「请自己补 scheme」对一个地址框来说不是个好答案；其余主机仍然补 https。`file:` / `data:` / `javascript:` / `mailto:` 一律拒绝，带用户名的地址也拒绝。

**变更面板读的是两份 diff，而不是一份 `git diff HEAD`。** 已暂存是 `git diff --cached`（index 对 HEAD），未暂存是 `git diff`（工作区对 index）—— 同一个文件可以同时在两边（`MM`）。一份合并的 diff 无法告诉面板「暂存这个文件」到底会搬走什么，而暂存之后未暂存那一份必须成对消失：这正是两条命令划出的那条界线。服务端（`git.ts`）先用 `git status --porcelain -z` 拿状态（`-z` 给的是原始路径，不用去解 git 的引号转义，含换行的路径也不会被当成记录边界），再对**每个文件每一侧**单独跑一次 diff。为什么不跑一次合并的 diff 再在 `--git` 块头切分：那样得去复刻 git 对含空格/非 ASCII 路径的引号规则，而逐文件的另一个好处是**限制才有意义** —— 一个巨大的文件（压缩后的 bundle、lockfile）只截断它自己，而不是拖垮整个面板。所有 git 调用走 `execFile` 的参数数组（从不拼 shell 字符串），并带 `GIT_OPTIONAL_LOCKS=0`（只读观察者不写 index，不跟用户开着的终端抢 index 锁）、`GIT_TERMINAL_PROMPT=0`（需要凭据时立即失败，而不是卡在没人看得到的提示上）与超时/缓冲上限；单文件补丁上限 256 KB，文件数上限 200（超出报 `omittedFiles`）。

**变更面板跟着工作区文件走，而不是等用户点刷新。** 服务端每注册一个项目就递归 watch 它的工作树（`workspace-watch.ts`），debounce 400ms 后只发一个 `workspace_changed`——它只说「有东西动了」，不说是什么，也不读 git。要不要重读 `git status` 由面板决定：`node_modules` 的路径段在服务端就被滤掉（依赖目录的 churn 是变更面板唯一不需要为之重载的东西），面板只在**挂载时**订阅（也就是只有它开着才订阅），而且写操作进行中不自动刷新——重读还在路上时再叠一次，只会让旧回复有机会覆盖新状态。

**每个写操作都回答「重新读到的状态」，而不是一句 ok。** 暂存/取消暂存、提交、推送、还原、切分支都是如此：面板从不展示一个它自己根据「预期 git 会怎么干」算出来的列表。git 的拒绝（没有暂存的改动、没配 user.email、推送被拒）被包成 `GitError` 并**原样带上 git 自己的那句话**（`nothing to commit, working tree clean`），路由层映射成 400 —— 这类失败是用户的动作没落地，不是服务器坏了；页面上就显示在按钮旁边。提交后新 commit 的 hash 也**不是从 `git commit` 的输出里抓的**，而是重新读一次历史的首条，这样即使 hooks 在提交过程中改写了历史，面板也不会指向一个从未存在的 hash。

**推送有且只有一种形态：不 force。** 有上游就是 `git push`；没有上游就 `-u` 推到 `origin`（没有 `origin` 时用唯一那个远端），因为「第一次推这个分支」在哪个 git UI 里都是这个意思；一个远端都没配就直说「这个仓库没有配置远端」，而不是把 git 的 `origin does not appear to be a git repository` 丢给用户。按钮上带 `↑N` 告诉你要推几个提交。

**面板只回答一个问题：这个项目里有什么没提交。** 曾经还有一个「本轮文件」范围（从会话转录的 `write`/`edit` 工具调用提取这次对话碰过的文件），后来删了：同一个文件通常在两个范围里是同一个理由，而一个大多时候只展示上方列表子集的开关，花的注意力比省的更多。要按会话过滤，转录就在手边，但它不应该占据面板的顶层开关。

**提交框在最上面，文件列表在它下面滚动。** 原来提交框在列表底部（与设计稿一致），但一个变更集长的面板里，“提交”变成要先滚过所有文件才够得着的按钮；而读完任意一行文件后要做的就是提交。所以它现在是固定的顶栏（输入框 + 提交 + ↑推送），下面才是分支行与两个文件列表。面板只此一个范围，也没有了分段控件。

**“不是 git 仓库”是一个答案，不是错误。** 那个分支返回 200 + `repository: false`，面板就写一行字，而不用 4xx 把一个很常见的情况（打开一个普通目录）画成失败。同理，二进制文件由 git 自己报 `Binary files … differ`、未跟踪文件根本没有对 index 的差异，两者都不编造补丁：前者写「二进制文件，无法显示差异」，后者写「未跟踪的新文件」并给一个「查看文件」（内容在预览页才读得到）。未跟踪文件也不给「还原」按钮：`git restore` 对看不见的文件无能为力，而删掉一个 git 从未见过的文件不该是「还原」按钮悄悄干的事。

**还原是这里唯一会丢东西的动作，所以它多问一句。** `git restore --worktree`（不碰 index —— 还原说的是磁盘上那份），点下前先 `confirm`，而确认文案里写着具体文件名，不是一句「你确定吗」。

**diff 的文本理解只发生在一处。** 前端 `diff-parse.ts` 是个纯函数：把 git 的 unified diff 解析成 hunk 列表，按 `@@ -a,b +c,d @@` 的起点给两侧分别编号，并把 `+`/`-`/上下文行归到自己的轨道上。文件头里的 `+N -M` 就是这次解析数出来的 —— 统计与绘制共享同一遍扫描，它们不可能互相矛盾。**文件默认是折叠的**：一个变更集常常很多文件，第一眼该看到的是它的形状（哪些文件、各改了多少），补丁就隔一次点击；打开面板本身不等于要求把所有行都画出来。展开之后还有第二层折叠（按 hunk）：一个文件可以带好几段相隔很远的改动，而往往最有意思的那段最短；超过 80 行的 hunk 默认收起，并把行数写在 hunk 头上，不静默藏东西。解析器有 9 个用例盖住多 hunk、`/dev/null`、二进制、空补丁、空上下文行与 `\ No newline at end of file`。

**`+` 菜单曾经被标签条裁掉。** 第一版把 `overflow-x: auto` 放在 `.strip` 上，于是锚在条内的绝对定位菜单被滚动容器裁成 0 高——a11y 树里还在、点不到。现在滚动只发生在内层 `.chips` 上，`.strip` 自己不裁剪，控件永远不被裁。标签 chip 也给了 72px 最小宽度：四个标签挤在 420px 里时，与其把每个标题压成「REA…」，不如让 chips 横向滚动。

**新会话页是一个独立的空状态**：未选中会话时不再是一个「请选择会话」的占位，而是 dsh 风格的居中页 —— 品牌标记 + 标题 + 「预览版」标签、工作区选择器、大圆角输入框，以及输入框右下角的模型选择器。在这里输入第一句话会同时完成两件事：立即切到 draft，并把这句话排队交给即将就绪的会话；如果提前选了模型，这个选择随同一条请求交给新会话（不选就让 pi 用它自己的默认模型）。

**内置命令必须由 Web 端自己实现**。pi 把 `compact` / `export` / `session` / `name` 这类命令放在独立的 `BUILTIN_SLASH_COMMANDS` 里，**永远不会出现在 `get_commands` 的返回中** —— 因为在 TUI 里它们是 TUI 自己实现的（打开设置菜单、读剪贴板、导航会话树）。`RpcSlashCommand.source` 的类型就是 `"extension" | "prompt" | "skill"`，没有 builtin。

所以 Web 端要同时提供清单和行为：只列出**有对应 RPC 方法**的命令，`/tree`、`/settings`、`/copy` 这些需要专门 UI 的不列 —— 菜单里点了没反应的选项比不列出更糟。执行时走 `POST /api/sessions/:id/command`，文本不会进入模型。

**输入框里的 `/` 补全**：命令列表来自运行中的 pi 进程（`get_commands` RPC），所以服务端优先复用该项目的活跃会话，没有就走预热进程，结果按项目缓存 60 秒。补全覆盖三类：扩展命令、prompt 模板，以及注册为 `/skill:name` 的技能。pi 在投递 prompt 前会自己展开 skill 与模板命令，所以前端只负责补全文本，不做任何替换。候选按「名字前缀 → 名字子串 → 描述」排序，上下键选择，Enter/Tab 补全（此时不会发送消息），Esc 关闭。对话输入框和新会话页共用同一套逻辑。

**两张菜单的开关只认 textarea 自己的值与光标，所以「发出去」得自己说一声。** 菜单的词法（token）是从 DOM 里的 `value` + `selectionStart` 现算的（`sync()`，靠 `onChange`/`onKeyUp`/`onClick` 喂），这样输入法、粘贴、改光标都不会让它错位。代价是**程序化地改草稿它听不见**：`Composer.submit()` 里那句 `setText("")` 只让 React 改 DOM，不触发 `input`，于是菜单一直开着——而且它是个浮在输入卡上方的层，会盖住对话流底部（最刺眼的一次，是 `/compact` 刚落下的那行 checkpoint 正好被盖住）。所以两个 hook 都开了一个 `close()`：它说的是「这个 token 没了」，而不是 Esc 说的「现在不要」，因此不留下「这个 token 被拒绝过」的记号——清空后回头再点到同一个词上，菜单该开还是开。与它相对的是另一个方向：**发送失败时草稿被放回去，菜单不会自己弹出来**，因为恢复草稿同样不经过 `input`，而这时候用户要的是改字，不是重新选一遍候选。

**扩展 UI 请求接管输入框，而不是弹窗**。pi 的自有工具不会弹确认框，但已安装的扩展可以通过 `ctx.ui.confirm/select/input/editor` 阻塞运行。这类请求**替换输入框**——dsh 的 `ask_user_question` 就是这么处理的：问题出现在你正要打字的地方，上方的对话仍然可读，回答用的还是那双手。盖一层模态则相反：它把已经发生的事遮住，只为了问一件本就属于「继续对话」的事；而「扩展在等你回答」与「你在写消息」抢的是同一个座位，同一时刻只该有一个占着。

四种请求共用一张卡片：`select` 渲染成带序号的选项列表（点击选中、Enter 提交，数字键直接选中该项——序号同时是快捷键），`confirm` 是「是 / 否」两行、点击即答，`input` / `editor` 换成自增长的文本框（`input` 用 Enter 提交；`editor` 装的是本就有换行的文本，所以 Enter 换行、Cmd/Ctrl+Enter 提交）。选项标签末尾的 `(Recommended)` / `（推荐）` 会剥成徽章——那是 dsh 的约定，扩展沿用了它——但**回给 pi 的值保留原串**，扩展是按原串匹配的。

卡片可以折叠成一行标题条，把对话让出来；关掉或按 Esc 等价于 `cancelled: true`。带 `timeout` 的请求显示倒计时：pi 到点自行结算且**不通知客户端**，所以浏览器按同一个 deadline 计时并在到点时收起卡片（不再补发响应——那时 pi 已经走完了）。请求按会话排队，一次只占一个座位；答完一个才会露出下一个，这样后来的请求不会把前一个还没看过的抹掉。

**座位只让当前会话自己的问题坐上去。** 服务端把扩展 UI 请求当公共部件广播给每个 stream（`wantsFrame` 对 `extension_ui_request` 一律放行），所以这条拦在客户端：别的会话在等你回答时，卡片不会跑到你正在读的那个对话的输入框位置——那等于让你去回答一个没人问你的问题，还占掉你正在写的那句话。它的会话行上留着「等待回答」的红点，点进去卡片就在原地（判据是 `seatOwns`，读取在 `pendingUiForSession`）。

**唯一没有地址的请求，算在「还没有会话」的那个座位上。** pi 要到第一次 `get_state` 才报出会话文件，所以一个会话的第一个问题必然在路径存在之前发出去；而屏幕上那个座位就是它被问出来的地方——正在创建的 draft，或者还没来得及创建任何会话的 hero（预热进程问的正是这个会话）。draft 拿到真实路径时会把这条请求的地址一并写上（`startDraftSession` 的回填），否则卡片会在路径替换的那一帧消失。地址一旦有，就只归那个会话：无地址的请求不会再被猜给任何一个已打开的会话，因为那时输入框该属于谁是很清楚的。

**答案按 dialog id 送回，而不是按会话路径。** 这不是风格问题：新会话在 pi 写出第一条 assistant 回复前没有落盘，而 pi 只在 `session_start` **之后**才通过 `get_state` 报出会话文件路径——扩展的第一次提问恰好就发生在 `session_start` 里。按路径回传会 POST 到 `/api/sessions//ui-response`（404），而这个进程会一直卡着。所以服务端把待答的 dialog 记在一张以 request id 为键的表里（`ui-requests.ts`），广播仍带 `sessionPath`（可能为空串：空串是「还没有会话」的判据，不只是展示用，见上文），应答走 `POST /api/ui-requests/:id/response`。同一张表还让**刷新页面不至于丢问题**：SSE 不重放历史，所以挂载时先 `GET /api/ui-requests` 把在等的问题收进来，否则那个 pi 进程会永远等一个没人知道的答案。

**回传不能走 `RpcClient.send()`。** 它是个请求/响应通道：会拿自己的 `req_N` **盖掉**调用方的 id（pi 于是永远匹配不上是哪个 dialog），然后等一条 `extension_ui_response` 根本不会有的回复——30 秒后以超时错误告终，而这期间用户以为已经答过了。dialog 应答在 pi 那侧是即发即忘的，所以服务端直接往子进程的 stdin 写这一帧。

**预热进程的提问也会出现。** 选中项目时后台已经起了一个 pi（见上文），它的扩展可能在会话还没被认领时就提问。这类请求同样进队列：它就是「这个新会话要问你的第一件事」，答完后会话接管这个进程。它按上面那条「无地址」的规则画在还没有会话的座位上（hero，或正在创建的那个会话），所以你在别的对话里读到一半时不会看到它；代价是那时没有会话名可显示，因为确实还没有名字。

`notify` 变成页面提示，但也只对当前座位上的那个会话（无地址时就是「还没有会话」的那个座位）：这类帧没有任何落脚点——没有卡片、没有红点、服务端表里也没有一行——弹给正在读别的对话的人只剩打扰，丢掉也不损失什么（`sessionInView`）。`setTitle` / `setStatus` 等终端专用请求在服务端就被丢弃（一次普通对话会产生 50 多次 `setTitle`）。

**切换会话不启动进程**。`GET /api/sessions/:id/messages` 原本走 `openSession` → spawn pi，而冷启动要 1.2–3.3 秒 —— 这就是「正在载入会话…」等待的**全部**来源，尽管转录一直躺在磁盘上。现在只有**已驻留**的会话才走 RPC（它的内存视图是权威的，可能含有尚未落盘的轮次），其余直接从 JSONL 读：`SessionManager.open(path).buildSessionContext()`，也就是 pi 自己重建会话时用的那套（compaction-aware、从当前 leaf 走树）。35 个真实会话实测中位 **4ms**、p95 23ms、最大 28ms，且**零进程启动**；7 个会话与 RPC 结果逐条比对**完全一致**（覆盖 352 条消息 / 189 次工具调用，到 3 条消息的空会话）。浏览器里实测点击到内容可见 19–160ms。

顺带一提，payload 的大头是工具输出，不是 `system` 消息（实测只占 0.3% 字节），所以没做服务端瘦身。

切换耗时降到 ~100ms 后，「正在载入会话…」自己变成了两帧的闪烁。提示文案因此延迟 250ms 才出现（`useDelayedFlag`）：快的时候什么都不显示，真的慢了再解释原因。

**思考与工具调用是同一个原语的两种形态**。两者都走 `DisclosureRow.tsx`（移植自 dsh 的 `DisclosureRow`）：折叠时是一行 24px 高——图标、名称、一个 2×2 的圆点、然后是摘要。**没有单独的 chevron 列**：悬停时图标在**原地**淡出、chevron 在原地淡入（`.iconIdle` / `.chevronHover` 占同一个 16px 盒子），这正是让一列工具调用能像段落一样紧凑的原因。展开后 leading 位固定显示 chevron、不再做悬停预览，而 `collapsedContent` 默认会被丢掉（工具行传了 `keepContentWhenOpen`，因为它展开的是输入输出而不是摘要）。行高、图标盒 16px、字形 14px、圆点 2×2、各处间距都照抄 dsh 的值。

**行距是 dsh 的 flow gap，不是一个 `gap`。** 24px 是一行的高度，行与行的距离是另一回事：dsh 的 `ChatView.column` 从不设 `gap`，而是用相邻兄弟选择器给每个 flow item 加 `margin-top: var(--dsh-chat-flow-gap, 16px)`，只把**紧跟在紧凑过程窗口之后**的那个答案项改成 8px——它是那个窗口的结尾，不是新的一步。这里照搬同一套机制（`MessageList.module.css` 的 `.assistantTurn > * + *`，答案项上的 `data-turn-process-answer`），紧凑组展开后的行列表（`TurnProcessGroup.module.css`）也统一到 16px。改之前用的是 2px：行距 26px，比行本身高不了多少，一轮下来的思考与工具调用会被压成一整块；dsh 里它们各自是 40px 一座。

**`/skill:` 命令在转录里是展开态，显示时必须折回去。** pi 在投递前就把 `/skill:<name> [args]` 解成一条用户消息：`<skill name="git-commit" location="…">`、整份 SKILL.md、`</skill>`。于是「发一条 skill 命令」在这个 UI 里曾经是**两三千字的文件倾倒**，会话标题也跟着变成 `<skill name="git-commit" location="/Users/…`（pi 的标题取首条消息）。dsh 没有这个问题——它存的就是字面 `/git-commit`，`projectUserText` 把 `/` 开头的 token 渲染成蓝字等宽的 chip。这里做同一件事：`skill-block.ts` 用 **pi 自己的正则**（`parseSkillBlock`，`dist/core/agent-session.js`）解析，气泡里只画 `/skill:<name>`（外加用户写在命令后面的参数），复制按钮复制同一串命令，服务端派生标题时也先折叠（`foldSkillCommand`，同时容错 pi 已经截断的形态——标题只有 80 字，完整块多半只剩个开头）。chip 与气泡都照 dsh：chip 是 `refChip` + `slashChip`（品牌蓝、500 字重、代码字体、无自己的底色），气泡从灰底描边方块换成 `--dsw-specific-bubble` 的浅蓝胶囊（22px 圆角、10/16 内边距、22px 行高）。chip 前还挂了一枚 dsh 的 skill 图标（`IconSkillOutline16`，一页纸加右下角一颗星），因为 `/skill:` 值得一眼认出来。图标与它的度量都取自 dsh：尺寸走 dsh 给引用 chip 图标写的 `refIcon` 规则（`1em` 见方、右侧 4px、基线 `-0.125em`），颜色不写死而是 `currentColor`，于是它与命令文字永远是同一个品牌蓝（`--dsw-alias-state-business-primary`，和 dsh 的 `refChip` 逐字节同值）。dsh 自己只给 `@文件/目录/会话` 这类引用 chip 配图标，`/命令` 没有——这一处是照它的规则补的，不是照它的用例。

**对话框下面是两枚会话级 pill，turn 级的那两个仍在每条消息下面。** 左边是 `2 轮 39 步 · 192 tok/s`（仪表图标），右边是 `364K tok · 缓存命中 56%`（数据库图标），点开各是一个详情面板（「会话统计」/「Token 用量」），位置、形状、文案都照搬 dsh 的 `StatsPills` 加 `StatDialog`——只把面板从 `position: fixed` 的 portal 改成锚在 pill 上方的绝对定位，因为两枚 pill 所在的那行从不裁切，这样省掉每次打开的一次测量。轮 = 用户消息数，步 = assistant 消息数，总量 = 计费输入（未缓存 + 缓存读 + 缓存写）+ 输出，命中率 = 缓存读 / 计费输入，并且**有未命中就绝不四舍五入到 100%**（999/1000 显示 99.9）。**速度是这一个客户端自己量的**：pi 的 usage 里没有时长，`get_session_stats` 也没有，所以 tok/s、模型用时、TTFT 只在本次浏览器会话的流式过程中累积（`useConversation` 的 `TimingState`，`message_start`/首个非空 delta/`message_end`/工具 start-end 四个边界）；从磁盘重新读回的会话只显示轮、步和用量，速度那一段干脆不出现——dsh 在自己缺时间数据时也退化成同样的纯文本 pill，而不是去猜一个数。

**输入框右下角还有两个控件：模型卡片和上下文环，位置与 dsh 相同，其中模型卡片并掉了思考强度。** 收起时是一枚按钮（provider 首字母 + 模型名 + 当前档位词），点开是一张卡：顶上居中的一行灰字报出当前档位、右上角是重新载入，中间一行模型名点开是按 provider 分组的菜单（当前模型带勾，每行右侧是它的上下文窗口），底下一条思考强度滑轨（关闭 / 极简 / 低 / 中 / 高 / 极高 / 最高，已滑过的档位在蓝色填充上留成浅白色小圆点、未到的留成灰点，档位名走 i18n，未知档位回落到原字串；**当前档就是「关闭」时不画蓝色填充、只留轨道**——`off` 不是梯子的最下面一级，是「不用梯子」，填到球心的进度条等于把「不思考」说成「思考得最少」，但轨道必须留着，否则这个档位既看不见也拖不出来，而卡上只剩一个「关」方块就显得像坏了一样）。上下文是一枚 chip：细圆弧加它代表的百分比（`12%`，75% 转黄、90% 转红，色调定在按钮上、弧以 `currentColor` 画，两者共用同一枚颜色），点开是一张「上下文」面板（窗口 / 已用 / 剩余 / 百分比）。它和模型 chip 用同一套内边距、圆角与字号——两个控件描述的是同一个会话、会放在一起读，配方不同就会读成两个来源；读数未知时（pi 刚压缩完、或磁盘上的会话没有可比的窗口）环只画轨道、读数写「未知」。三者数据来源按代价分岔——因为它们的数据根本不在同一个地方。**滑轨只在有得选时才画**：`levels` 只有 `["off"]` 时没有可选项，画一个禁用控件只会招来「为什么不能点」；`levels` 为 null（`models.json` 没描述这个模型）时画得出按钮但画不出滑轨，那个位置改说一句「正在载入思考强度…」或「思考强度不可用」——打开卡片正是触发一次 live 读取的地方，而在读过之前留一片空白，看起来就像卡片坏了而不是还没答。同理，还没有模型（新会话尚未落盘）时只是一枚写着「选择模型」的空按钮，那本来也是模型选择器的事。

**输入卡的描边比默认的 elevation 浅一档，这不是调出来的。** `--dsw-elevation-soft` 的第一段是 0.5px 发丝描边，默认取 `--dsw-alias-border-l4`；dsh 的输入卡在卡片自身上把 `--dsw-elevation-stroke-color` 重绑到 `border-l2`（菜单面重绑最浅的 l1，工作区的拖放触发态置 `transparent` 只留柔光），滚动条 thumb 也一并切到 l2 那一对。这里照做，且 `Composer` 与 hero 两张卡共用同一组重绑——它们在 dsh 里本来就是同一张 `InputBar` 卡的两个变体。卡上的字号/行高也从硬编码的 14/24 接回 `--dsh-content-font-size` / `--dsh-content-font-delta`：设置页调字号时输入框里的字跟着动，而不是只有正文动。

**发送与停止是同一枚蓝色圆钮的两个图标。** dsh 的 `.uV2eYG_primary` 只有一个 className：静止时画发送箭头，运行中画一个 10×10 的圆角方块，但底色始终是 `--dsw-alias-button-info-fill`（浅色 `deepseek-500`、深色 `deepseek-400`）、图标始终是白、悬停始终换 `-hover` 那一档、禁用态统一 `opacity: .4`，另有 0.1s 的 `background-color` 过渡。这里把原来拆开的两枚——发送读 `button-primary-fill`（浅色黑/深色白）、停止读 `bg-layer-2` 的灰底——统一回这一枚：尺寸、999px 圆角、底色、过渡一起照抄，两态只差图标（那枚白色写作 `--dsw-static-neutral-00`，值与 dsh 硬编码的 `#fff` 相同，只是用本项目的调色板拼出来）。**图标本身也是 dsh 的原件**：`InputBar.tsx` 把那两枚内联写在同一个按钮的 JSX 里 —— 发送是几乎撑满 16px 盒的实心箭头，停止是 10×10、圆角 3 的实心方块 —— 而不是 `ui-primitives` 里同名的 `IconSendOutline`（描边）与 `IconStopFill`（11×11、圆角 1）。此前这里是自绘的描边图形，1.4px 的线落在同色蓝底上等于隐形，换成实心才和底色一起读成一枚按钮。输入区的光标也按 dsh 设成业务蓝（`caret-color: var(--dsw-alias-state-business-primary)`），并把 textarea 的内边距换成 dsh 的 `4px 8px 0 14px`——右边只给 8px 是因为 dsh 的滚动容器另有一段 4px 外边距（这里由 textarea 自己的滚动条轨道承担同一角色），左边 14px 是为了与下方工具行的图标对齐。

**新会话页的「预览版」徽章也是 dsh 原件。** `state-business-tertiary` 底 + `label-primary-bluish` 字 + 0.5px 的 `interactive-bg-hover` 描边 + 24px 圆角 + 代码字体 12/18 与 `1px 7px 0` 内边距，并保留 dsh 给它的顶部对齐（`align-self: flex-start` + `margin-top: 2px`）——那是为了跟更大号的标题错位对齐，而不是居中。

**工作区 chip 的度量与图标一起从 dsh 取，不只看大小。** `HeroShell.module.css` 的 `.workspace` 给的是 4px 的图标—标签—箭头间距、28px 最小高度、`0 8px` 内边距、小圆角、13px/20px 的 500 字重与 `label-primary` 墨色，以及 `max-width: min(100%, 360px)` 配标签省略号——长工作区名缩短时，文件夹与箭头必须仍贴住剩下的字，所以省略号画在标签自己身上，而不是让三件东西一起被裁掉。底色只在悬停与 `aria-expanded` 时出现，两者共用 dsh 的那一条选择器：菜单开着时 chip 仍是有状态的。**图标不复用本仓库的 `FolderIcon`**——那是 `icons.tsx` 自绘的 1.4px 描边，摆在 13px 标签旁边偏重——而是搬 dsh 的原件：未选工作区时 `FolderCloseArtwork`（1px 描边），选中后 `FolderOpenArtwork`（fill-only，盖子 16% 内填），箭头用 `IconChevronDownOutlineRegular` 的 12px 版（原先是 `ChevronIcon` 转 90°，同一根 1.4px 的线在小尺寸上一样偏粗；转出来的角还只是旋转后的同一个字形，不是 dsh 那枚画好的向下折线）。整段节奏也跟着 dsh 回到 12px：`HeroShell` 的 stack 从标题到工作区行再到输入卡每步都是 12（figma 75:8208），工作区行另留 `.workspaceRow` 的 8px 左内缩，让文件夹落在输入卡的内边距上方。

**模型和上下文从磁盘就能答，模型列表也能——只要用 pi 自己的解析器。** 切会话不启动进程是上面那节的核心优化，所以这些控件要能在没有 pi 进程时工作：

- **会话的模型是 pi 自己写进文件里的**：每次切换都 append 一条 `model_change`（`provider` + `modelId`），磁盘上就有权威答案；显示名和 `contextWindow` 从 `models.json` 取——那是 pi 启动时读的同一份文件，不是我们自己编一份目录。没有 `model_change` 的新会话返回 null（pi 还没选过模型，编一个默认值是猜）。**思考强度同理**：pi 在首次打开会话时 append 一条 `thinking_level_change`，所以当前档位从文件里扫最后一条即可（刻意不用 `buildSessionContext().thinkingLevel`，它对没有该条目的文件默认成字面量 `"off"`，与用户真的选了关闭无法区分）。**可选的档位也能从磁盘答**：pi 的 `getSupportedThinkingLevels` 只看模型的 `reasoning` 与 `thinkingLevelMap`，这两项就在 `models.json` 里，所以 `readModelCatalog` 多读了 `thinkingLevelMap`，并在这里重写了那条规则（`xhigh`/`max` 只有 map 明确写了才算，映射成 `null` 的档位排除）——只有 `models.json` 不认识的模型（内置 provider 的模型）才会 `thinkingLevels: null`。
- **上下文用量按 pi 自己的规则重算**：`AgentSession.getContextUsage()` 算的是 `estimateContextTokens(this.messages)`，而那个函数没有从包入口导出，所以这里用导出的 `estimateTokens` / `calculateContextTokens` / `getLastAssistantUsage` 把它的十几行规则重写了一遍（有测试锁住）。压缩边界照抄：最后一条有效 usage 在压缩之前、其后又没有成功回复时，答案是「未知」，而不是一个描述压缩前上下文的数字——那恰好是用户最可能来看这个数的一刻。磁盘值与 live 值可能差千分之几（实测 209954 vs 210540）：pi 运行时那个 `messages` 是 agent 的状态（含它自己注入的 system prompt），磁盘上重建的只有会话文件里的消息。
- **可切换的模型列表在会话路径上仍然只有进程能给，但新会话不需要进程**：`get_available_models` 是 runtime 解析后的视图（带上每个模型真实的 `contextWindow`），磁盘上没有它的等价物。所以会话路径下 `models: null` 表示「不知道」而不是「一个都没有」，菜单打开时才带 `?spawn=true` 拉一次：用户主动要切换的那一刻付一次 1.5s 冷启动，而不是每次点侧栏都付。实测那一次 1.73s，之后菜单里的 8 个模型都带着窗口值。新会话页走的是另一条路：`ModelRuntime.create()` 就是 runtime 本身，十几毫秒读完 `models.json`、pi 内置的 provider catalog 与 `auth.json`，而 `getAvailableSnapshot()` 与 `get_available_models` 是同一个函数——所以它是**同一份列表**（同样过了「有凭据才算可用」的过滤，同样带窗口值），只是不联网也不起进程。

**环画的是弧，不是数字。** 它要回答的是「离上限还有多远」，那是个形状问题；具体数字在点开的面板里。环有 75% / 90% 两档变色——那是显示层的判断，不是 pi 的压缩阈值（pi 的阈值可配置），所以面板永远把原始数字写出来，不靠颜色暗示。

**「未知」画成空环，不是满环也不是零。** pi 在刚压缩完时返回 `tokens: null`，磁盘路径上也可能根本没有 `contextWindow`（`models.json` 没写这个字段，而内置 provider 的默认窗口不在依赖树里拿不到）。两种情况都只画轨道，面板里写「未知」并说明估算口径——一个看起来精确的错误数字比「未知」糟得多。

**压缩本身也落在转录里，因为那是它唯一真实的地方。** 一次 compaction 改的就是上下文本身：切点之前的轮次从 pi 的 context 里消失，取而代之的是一条摘要消息（`role: "compactionSummary"`，带 `summary` / `tokensBefore` / `timestamp`）。这条消息**本来就随转录回来**——RPC 的 `get_messages` 返回的是 `session.messages`（pi 的上下文），磁盘路径的 `buildSessionContext()` 返回的是同一套——所以这里既不需要新的服务端接口，也不需要去读 session entry。`MessageList` 把它画成 `DisclosureRow`（与思考行、工具行同一个原语），收起时报出「压缩前 324K tok」与时间，展开是摘要的 markdown（`max-height: 320px` 自己滚）——pi 写的是结构化摘要，几十 KB 很正常，不折起来会把下面的轮次顶出几十屏。它**不算一轮**：`groupTurns` 只认 user / assistant，所以轮次编号、导轨上的刻度、跳转目标都不会因为它移位（有测试锁住）。`turn-rail` 那边因此一行没改：`MessageList` 用一个 `消息 → 下标` 的索引表把 checkpoint 与「每一轮的第一条消息」对齐，再把两者按位置合并成一条 flow 渲染。

**「按位置」意味着两条路看到的位置不同，而这是对的。** 从磁盘读出的会话，`messages` 就是压缩后的 context：checkpoint 是第一条，它折叠掉的轮次压根不在数据里，所以行落在最上面——那也是那一份转录的开头。而**读者正看着的时候发生的压缩**，那些轮次还在屏幕上（它们是一条条消息事件累积出来的），行就落在**末尾、它折叠掉的一切下面**。所以 `compaction_end` 不重读转录，而是把这条 checkpoint 就地追加进消息列表：重读会拿回压缩后的 context，行被顶到最上面，而任何长到需要压缩的会话里读者都看不见它——偏偏这一刻是他最需要看见它的时候。运行中那半段也用同一套行头（同一个图标、同一行高），所以读起来是**同一条行在换状态**，不是两条互不相干的提示来去。手动 `/compact` 同样不重读，**也不再弹那行 toast**：命令跑完后 `ConversationPane` 以前会 `reload()` 一次、并且把 `runBuiltinCommand` 返回的那句话（`已压缩上下文：约 X → Y tokens`）弹成底部提示，两条路现在都没了——事件已经把 checkpoint 落进转录，重读只会把它顶上去，而同一件事在另一个角落再说一遍、数字还不一样，读起来像发生了两次。只有 `/compact` 被这样对待（`TRANSCRIPT_REPORTED_COMMANDS`）：`/export` 的路径、`/name` 的确认、`/session` 的统计都只有那一行可露脸，失败时的 toast 也照旧（失败的压缩没有行可落）。代价是 **`estimatedTokensAfter`（压缩后的大小）不再出现在界面上**——服务端仍然返回它（有测试锁住），只是这个 UI 不再有它的位置；要补的话，应该是并进那条行（「压缩前 324K → 12K tok」），而不是把 toast 请回来。

**只在轮次结束时刷新。** 上下文用量来自最后一次模型回复上报的 usage，所以流式过程中它不会变；`agent_settled` 之后拉一次既是最新值，又保证进程一定在（不会为了刷新而 spawn）。模型切换由 POST 的响应直接更新，不需要再读一次。

**新会话页有模型卡片（含思考强度），没有上下文环。** 上下文环要的是一个还不存在的会话的用量，画出来只能是空环，所以 hero 上不画。模型选择器正好相反：第一句话是选中「第一轮用哪个模型」的最后机会——会话一旦创建，第一轮就已经按 pi 的默认模型跑起来了。所以那张卡右下角放着和输入框同位置的 picker（列表由服务端的 `ModelRuntime` 直接解析，见上），选了就随首条消息 POST 给 `POST /api/sessions`，服务端在刚起来的会话进程上 `set_model`；**实测这一步不会让空会话落盘**（pi 只在第一条消息到达时才写文件），所以「选了模型但没发消息」不会留下一个空会话文件。思考强度是同一套：创建时在 `set_model` **之后** `set_thinking_level`（顺序是承重的，因为 pi 按当前模型钳制档位），当前档位由服务端的 `SettingsManager` 按 pi 自己的次序推出来——per-model 覆盖 → 全局默认 → pi 的 `medium`——再钳到该模型支持的列表里，因为此时还没有进程来钳。没选就什么都不传，让 pi 用自己的默认。会话出现之后，模型卡片与上下文环都在输入框右下角。

**统计面板的样式抽出来共用了。** `StatPanel` 现在是两枚会话 pill 和上下文面板共用的组件（它原本长在 `SessionStats.module.css` 里），上下文面板只多了一个贴右对齐——环在发送按钮旁边，居中的面板会越过视口右缘。

**底部那两枚 pill 所在的行永远占着位置。** dsh 在没有步数也没有 token 时整行不渲染，这里**不能照做**：dsh 的 pill 是 composer 自己 dock 的条目，空的 dock 藏在 composer 本来就拥有的盒子里；而这一行是会话列（`ConversationPane`）的 flex 子项，卸载它就是把这个列高减掉 34px，输入卡会直接砸到窗口边缘。转录**每次切换会话都会被清空**（`useConversation` 在读回文件之前先 `messagesRef.current = []`），所以这条路径一次慢读就能踩中：底部栏整行消失、输入卡下坠 34px、读完再弹回来。本地服务端通常在一帧之内读完，中间态多数时候根本没被画出来——这正是它平时只表现为「偶尔」跳动的原因（实测：把 `/messages` 卡住 900ms，逐帧记录到的就是 `栏在 & bottom=770` ×1 → `栏不在 & bottom=804` ×55 → 复原 ×107）。所以改成这一行常驻、只让两枚 pill 各自按 dsh 的规则消失；`.root` 用 `min-height` 把空行的盒子撑到与满行同高（`34px + --dsh-content-font-delta-secondary`，那个 34 是行自己的 4+8 padding 加上 pill 的 20px 行高与 1px 上下内边距——读者调大正文字号时 pill 会一起长，行必须跟着它算）。判据不是「有没有东西可显示」而是「这一行的高度不能被数据决定」。

**空思考块不渲染**。模型返回的思考常常以空行开头，直接取第一行会渲染出孤零零的「思考 ·」；pi 还会产生**完全空的** reasoning 块（思考被打断）。dsh 的 `ReasoningRow` 取字面第一行，但它另一个 helper 明确用 `find(c => c !== "")`，这里跟随后者。在一个真实会话上，这消灭了 39 行里的 11 行噪音。

**流式思考跟随末尾**：正在输出时摘要取**最后一个非空行**并右对齐（`data-follow-end`），文本从左侧溢出而不是整行重新省略号——否则每来一个 token 整行都会跳一下。输出结束后回到第一行。

**执行中有一处专门的指示**。`TurnStatus.tsx` 是消息列表末尾那行「working...」——字符串本身被渐变填充（`background-clip: text` + 透明文字色），渐变以 1.8s 平移，于是那道光扫过文字而完全不参与布局。它**不随首个 token 出现而消失**：dsh 的注释写得很明白，这个标签要跨越「首字之前、工具执行、流式输出」三个阶段，而这正好是 pi 的 `agent_start` → `agent_settled`，所以窗口直接用 `isStreaming`。超过 15 秒才会追加一个 `tabular-nums` 计时——大多数轮次在那之前就结束了，闪一下反而像故障。

`isStreaming` 因此有两个来源，取并集而不是任一覆盖（`useConversation` 的返回值）：本 hook 自己的事件订阅（这一轮是在本标签页看着开始的），和 app state 里按会话路径记的运行标记（`agent_start` 点亮、`agent_settled` 熄灭，与侧栏那枚点同源）。只用前者的话，切走再切回来会把正在跑的会话当成空闲——`isStreaming` 是 hook 的内部状态，重新挂载就丢了，所以 `TurnStatus` 和输入框那枚「停止」会一起消失。服务端只按订阅过滤 token 增量（`message_update` / `tool_execution_update`），`agent_start` / `agent_settled` 对每个会话都发，正是靠这一点后台会话的运行标记才一直准。

**重试有独立的一行**。pi 在模型请求失败后会自己退避重试，这段时间界面本该是「卡住」的——而 `auto_retry_start` 带着 `attempt` / `maxAttempts` / `delayMs` / `errorMessage`，所以可以有带倒计时的「等待重试模型请求（1/3） · 8s」，倒计时归零后切成 shimmer 的「正在重试模型请求（2/3）」，展开能看到延迟和失败原因（照 dsh 的 `<details>` 结构）。这里有一处刻意的偏离：dsh 在重试进行中也显示秒数，但它的取值恒为 `1s`（helper 有 `Math.max(1, …)` 下限，而 deadline 已经过去了），显示一个永不变化的数字比不显示更糟，所以进行中的状态去掉了时钟、只留尝试次数。重试是刻意的停顿，所以它**替代**状态行而不是叠在下面：`view.retry` 非空时 `TurnStatus` 不画（两者抢的是同一行）。

**失败要落在那条回答原本的位置上。** `auto_retry_end` 带回 `success` / `attempt` / `finalError`，之前只用它清掉重试行；而 pi 放弃之后，转录里留下的是一条 `stopReason: "error"` 的 assistant 消息，消息列表却只按 `content` 渲染——于是一个没吐出任何 token 的失败（最常见的形状）**什么都不显示**，pi 设置里关了自动重试时连重试行都没有。失败行（`TurnFailure.tsx`）与重试行同形（同一套 `<details>`、同一个「失败原因」标签），但换成错误色、不带扫光：已经没有东西在跑了。它**读转录而不读流**——`getMessages` 拿得到那条消息，所以刷新、切会话、重开标签页之后这行都还在，而重试行只在当时有效。判定收在三个条件里：

1. **只认这一轮最后一条 assistant 消息。** pi 在重试成功时会把错误消息从 agent state 里删掉，但**保留在 session 文件里**（`_prepareRetry` 的注释：`keep in session for history`），所以「文件里有错误消息」只说明某次尝试失败过；只有这一轮最后一条回答是错误，才是这一轮失败了。
2. **轮次还没结束就不画。** 重试期间那条错误消息已经在转录里，此时画出来会和上面「等待重试模型请求」互相矛盾。`isStreaming` 在重试期间一直是 true（`agent_settled` 要等整个重试循环结束），所以用 `liveTurn` 一个判断就挡得住。
3. **次数只附在最后一轮上**（`view.failedAttempts`，来自 `auto_retry_end.attempt`）。session 文件里没有这个数字，所以从磁盘读出来的失败行只写「模型请求失败」，不编一个次数。

行右边那枚「重试」是**把那条 prompt 再发一次**：pi 没有「重试这一轮」的 RPC（重试循环是 turn 内部的事，`abort` 会连它一起停），能用的杠杆只有再发一遍——所以代价是转录里多出第二份用户气泡，因为那确实就是发出去的东西。这一条与「次数不落盘」一起写在[已知限制](./known-limitations.md)里。

**运行中的指示是扫光而不是转圈**：一条 300px 的高光以 2.6s 穿过整行，工具行和思考行各一份 keyframes，与 dsh 同一套动画。失败时图标换成 dsh 的 `StateDot`（外圈 10% 同色 + 内点 80%），摘要转成错误色。

**思考行与操作行的折叠，对齐的是 dsh 最新那一版，两处都改了。** 行这一层：收起时是工具自己的图标，悬停交叉淡入一枚向下的 chevron；展开时那枚 chevron 翻过来指向上方。**这里刻意没有照抄 dsh 的换图标写法**——dsh 展开时会换上另一枚「向上」的 svg，而新挂载的节点没有上一帧的 transform 可以过渡，折叠那一下会硬切；改成旋转同一枚（`transform: rotate(180deg)` + 100ms）得到同样的两个状态，而这条旋转是折叠唯一的动效，所以更值得留。行同时开始自己持有颜色：`tertiary`，悬停升到 `secondary`，标题、图标、chevron 全部 `inherit`。之前标题在各自文件里写死 `secondary`，hover 只到得了图标——一个不能跟着行走的标题，等于把状态反馈砍掉一半。

**轮次那一层的控件换成了 dsh 的 `TurnProcessNodeView`。** 整行 33px 的 `button`、底部一条 0.5px 的分隔线（那是「这些是过程、那就是回答」的边界），文案是完成汇报而不是标签：`已完成` / `已完成，用时 2分33秒`。用时只把**数字那一截**换成代码字体并开 `tabular-nums`，单位留在行自己的字面里——所以它是把本地化好的字符串按数字切开，而不是把 `duration.*` 模板再抄一份。原来的星芒图标和 `N 项` 都去掉了：dsh 现在这版只报「完成了」和「用了多久」，计数键在它的字典里已经没人引用。`formatRunDuration` 前有一次 `Math.max(1000, …)`，和 dsh 一样——一秒内结束的轮次读成「0秒」像是计时坏了。

**只有真正结束、而且是以回答结束的轮次才折叠。** 表头是一句完成汇报，跑着的轮次没有东西可汇报；失败的轮次已经有失败行在讲这件事，再折一次只会把证据藏起来。所以「活轮次不折叠」和「失败轮次不折叠」是同一个判断的两半（dsh 侧是 `turnProcessAlwaysOpen`）。代价与 dsh 相同：轮次一关闭，读者上方的内容会重排一次。折叠组与紧随其后的答案之间回到 16px——这里原来照搬过一个把答案提到 8px 的旧版 dsh，现在那两行和展开后一样走在普通节奏上，折叠与展开的密度才是同一个。

**收起的那行摘要也跟着显示模式走。** dsh 的 `settledReasoningPreview`：「标准」下思考行是 `思考 · 第一行`，「紧凑」下就只剩光秃秃一行 `思考`，正文点开才看得到。**流式那一段是无条件的**——那一行是模型当下唯一的外显，任何策略都不该把它拿走。策略是记在 `data-preview` 上、由 CSS 藏起来，而不是在 React 里条件渲染：节点在策略翻转时保持同一份身份。

**默认显示模式改成了「紧凑」。** 那是 dsh 的默认，也是新读者更可能想要的：一个已经结束的轮次不必把每次工具调用都摊开。只有**默认值**动了——`store.json` 里已经写明模式的用户不受影响。

**任务清单现在和 dsh 同形，因为它就是照 dsh 写的。** `todo` 工具由本包自带的扩展（`extensions/todo.ts`）注册，不再是装别人的包：每次调用带回**整份**列表并替换旧的，一条任务是 `content` 加三态 `status`——没有 id、没有依赖字段、没有墓碑，因为整表替换不需要身份，也因为没有第二次调用需要认出某一项。它和 dsh 的 `todo_write` 唯一的差别是名字（这里仍叫 `todo`，面板与转录行都按这个名字分派，换过工具之前的老会话也叫这个名字）。**「这份列表属于谁」也照 dsh 的规则**：plan 在下一轮开始时清空，而 `turn/end` 保留——一轮刚结束时读者要看得到刚完成的清单，下一轮开始时它就不该再装作是这一轮的计划了。

**当前清单是转录的一个投影**：每次成功调用都在 `details.todos` 里带回写入后的完整列表，`projectTodos` 于是从**当前这一轮**反向扫描、取最后一份读得懂的快照，而不是这个 UI 要自己维护的状态。轮次的边界是 `currentTurnStart`：最后一个 pi 已经接手的用户消息，而排在队列里、pi 还没拿起来的那几条不算开新轮（与 `groupTurns` 同一条规则，`undeliveredPrompts` 就是那个数）——否则一条还没被处理的消息就把正在进行的计划提前擦掉了。边界在转录里，所以「清空」不需要任何人去清：`/reload`、分支、compaction 之后算出来都是同一个答案。终端的 `/todos` 覆盖层走同一条边界（`readTodos` 从会话分支重放，只扫最后一个用户消息之后），两个界面因此说的是同一件事——只是那份覆盖层现在只存在于手工加载了 `extensions/todo.ts` 的终端会话里（包清单里没有这个文件，见上文）。当前形状的解析是**全有或全无**：一条任务读不懂就丢掉整份、再往前找一份，因为「少一行的列表」不是一个更小的列表，而是一份从来没存在过的清单。旧的增量载荷（`@juicesharp/rpiv-todo` 的 `tasks` / `subject` / `deleted`）读得宽松一些——墓碑在那种载荷里是正常内容而不是损坏迹象——所以换成自研工具之前的老会话仍然显示得出自己的清单，只是 id、依赖与 `activeForm` 不再渲染。

**面板在输入框上方，默认折叠，空清单不渲染。** header 是清单图标 +「任务」+ `2 已完成 · 1 进行中 · 3 待处理`（用 U+2002 分隔——ASCII 空格会被 HTML 折叠成一格），展开是 `max-height: 180px` 的清单。卡片宽度是输入卡的内容宽 `− 32px`（dsh 的 dock 比 composer 每侧内缩 16px，写成 `width: calc(100% - 32px)` 是为了窄窗口也守住这 16px，只留 `max-width` 会在卡片先收窄时变成齐平），与输入卡的间距是 dsh 那个 stack 的 6px（`--dsh-composer-stack-gap`，不是 composer 自己的上边距——`Composer.module.css` 的上内边距是 0）。卡片面照 dsh 的菜单面走：不要布局边框，用 `--dsw-alias-border-l1` 的 elevation 描边 + `--dsw-radius-lg` 圆角 + `--dsw-elevation-panel` 抬升（`--dsw-elevation-stroke` 画在盒外，所以描边不吃内边距）。**两处标记（mark）照 dsh 的分法走，而不是照我们的偏好。** 面板用 dsh 面板那套紧凑状态语言 `StateDot`：未开始与已完成是 10px 槽里一颗 6px 实心点（`--dsw-alias-state-idle-primary` / `--dsw-alias-state-success-primary`，槽不变所以行文本不会在状态之间跳），进行中是唯一不是点的那个——14px 双圆环，完整环垫在底下、一段弧在 1.5s 里呼吸同时整个字形旋转（`prefers-reduced-motion` 下停成一段固定的 18 单位弧）。面板的行因此把标记写成 `role="img"` 加状态词，而不是 `aria-hidden`：在那一面上形状是状态唯一出现的地方，dsh 也是这么标的。header 的两个图标同样换成 dsh 面板用的：清单图标用 `checklistOutline`（16 画板 1px 描边，而不是本项目那份填充的 `checklist`），折叠箭头用 `chevronDownOutline`（与 dsh 的 chevron 逐字节相同，折叠时旋转 180°——dsh 的 up 箭头正好是 down 箭头关于中心的镜像，所以那是同一个像素而不是相近）。转录里 diff 卡保持本项目自己的三个环形字形（绿圈勾 / 蓝色渐变环旋转 / 虚线空环），**它们不是 dsh 的面板美术**——dsh 全库没有「圈里一个勾」的图形，它给 diff 行用的是勾/播放图标加状态词——所以留着不动，差异写在这里而不是假装一致。

**转录里那一行的摘要与 dsh 一致**：`3/7 已完成 · <正在进行的任务>`，并行进行的其余任务进一个不收缩的 `+1`（拼进摘要就会被窄行先截掉，而那恰好是它唯一要说的事）。整份清单就在**参数**里，所以一次还在跑、或最终失败的调用也能给出真实摘要，而不是退回「工具调用」；`details` 到位后以结果为准，展开的也是这份清单——dsh 展开的是原始参数，对它来说那就是全部信息。

**面板会裁掉过期的完成项，转录里的展开体不裁。** dsh 不需要这一层——它的 plan 每轮清空，列表本来就短——而一轮里也可能完成十几项（扇出式迁移、批量改名），面板却只有 180px 高，展开它的人问的是「还剩什么」。所以面板只留**最近完成的 3 条**（`PANEL_COMPLETED_LIMIT`），其余折成末行 `+37 项已完成`；未完成的永远不裁。留最近而不是最旧，是因为清单按计划顺序写入，最近完成的正好挨着还在进行的工作——可见窗口因此是连续的，而不是中间被挖一个洞。转录里的展开体不裁：那是一份历史记录，裁剪它就是撒谎。

**设置分两层，因为它们真的属于两层。** 侧栏底部的「设置」进入一个全屏设置页（左栏导航 + 右栏内容，照 dsh 重建）。导航有四项——**通用设置**、**模型**、**插件**和**MCP**——它们各自的内容来自不同的地方：

- **外观 / 字号大小 / 对话显示 / 繁忙时的发送行为** 存在本项目的 `store.json` 里。pi 没有对应物，改它们不该影响终端里跑着的 `pi`。
- **自动压缩** 属于 pi，所以是从一个活的 pi 进程 `get_state` 读回来的，写也走 `set_auto_compaction`。一个项目进程都起不来时这一行显示为禁用——**宁可禁用，也不要显示一个我们猜的值**，否则用户会把它「改成」它看起来已经是的样子。
- **模型提供方** 既不在我们的 store 里，也没有 RPC，所以直接改 pi 的两个配置文件（下一节）。
- **插件（扩展）** 同样既不在我们的 store 里，也没有 RPC——而且这一次连「当前加载了哪些」都问不到，所以清单由 **pi 自己的资源解析器**算出来（下文「插件清单为什么交给 pi 自己解析」）。顶部还常驻了任务清单扩展的安装入口——对话页那条提示可以关掉，这一处不关。
- **MCP 服务器** 是 pi 内置的能力，配置就是 pi 自己读的两份 `mcp.json`（用户级与工作区级）；这一节按 pi 的合并规则读它们，再写回定义它的那一份（下文「MCP 管理为什么要自己解析这两份文件」）。

**外观：深色主题是 dsh 的原件，不是调出来的。** dsh 的主题包里有四个 `body[data-ds-dark-theme]` 块，重新指向整套 static 色阶再由 semantic alias 引用它。它们本来就在 `design-platform.css` 里（当初是逐字移植的），只是**从来没生效过**——dsh 的运行时写的是 `data-ds-dark-theme`，而本项目写 `data-appearance`。把选择器改成 `html[data-appearance="dark"] body` 之后，深色立刻是对的：`--dsw-alias-bg-base` → `rgb(21,21,23)`，`--dsh-scrollbar-thumb` → `rgb(60,60,61)`，连思考行的渐隐带都从白换成 `#151517`。

**选择器写成 `html[…] body` 而不是 `body[…]` 是有原因的**：浅色 token 就声明在 `body` 上，深色块必须**在同一元素上比它更具体**，而不是去命中它的后代。三个 token 表（`design-platform` / `gradient-shadow-text` / `shiki`）都是这个形状。

**代码高亮是这套 token 表的第一个消费者。** `highlight.ts` 移植的是 dsh `ui-primitives` CodeBlock 的静态路径：主题不是某一套内置配色，而是 `createCssVariablesTheme({ name: "css-variables", variablePrefix: "--shiki-", fontStyle: true })` —— token 颜色就是 `shiki.css` 里那 9 个变量，浅色声明在 `:root`，深色声明在 `html[data-appearance="dark"] body`。所以切外观是**重新解析颜色**，不是重新高亮。改之前这里写死 `github-light`，深色主题下代码块是唯一一块仍然发白的面板。

**引擎换成 JavaScript 正则，因为 wasm 比语法更贵。** dsh 用 `createJavaScriptRegexEngine({ forgiving: true })`，并把 `lazyCompileLength: Infinity` 交给 oniguruma-to-es（长 pattern 首次用到时才编译），本项目照抄。代价是少数语法不支持的模式被跳过（`forgiving` 就是为此存在的），换来的是不再下载 shiki 的 Oniguruma wasm：同一份产物实测，主包 633.9 KB + wasm 622.3 KB（gzip 200.6 + 231.2）变成主包 902.9 KB 且无 wasm（gzip 239.0），首次打开少下约 195 KB。

**语言表照抄 dsh，因为「支持哪些语言」是一个产品决定，不是 shiki 的决定。** 26 种语言、43 个别名（`ts` / `js` / `jsx` → `typescript`，`bash` / `sh` / `zsh` → `shellscript`，`yml` → `yaml`…），其中 `typescript` / `shellscript` / `json` 随入口 chunk 一起到（dsh 的 `Lm`），其余 23 种走动态 `import()`。不在表里的语言渲染纯文本——dsh 对 `diff`、`text` 也是这样，而 shiki 的 web bundle 认得它们，所以这曾经是「本项目比 dsh 高亮得多」的一处。

**grammar 是「先进视口，再按需到货」。** 代码块进入视口才请求 grammar（照 dsh 的 `useLangReady`，一个只触发一次的 IntersectionObserver），`import()` 落地后由 `useSyncExternalStore` 订阅重渲染上色——dsh 用的是同一套两段式（`n8` / `yo`），而不是每个代码块各维护一个 async 状态机，也不会为长转录里没滚到的代码块拉语言 chunk。**首帧的可见性是本项目补的**：IntersectionObserver 要等到下一个任务才回答，照搬的话一块已经显示在屏幕上的栅栏会先画一帧纯文本、下一帧才上色，每个代码块都闪一下。所以进观察之前先用 `useLayoutEffect` 同步量一次 `getBoundingClientRect()`——布局副作用在绘制之前跑完，这次翻转落在屏幕之外，读者只看得到上色之后的样子。纯文本与高亮两态也共用同一个 `.code` 盒子：grammar 到货只换掉盒子里那个 `<pre>`，容器自己不被卸载，块不位移，水平滚动位置也不丢。

**流式路径也是增量的，和 dsh 走同一条路。** dsh 的 CodeBlock 在流式期间用 `codeToTokensBase` 接上一次的 `grammarState` 按行追加；`highlightStep` 移植的就是这套机制：把「最后一个换行符之前」当作冻结前缀，连同它的 `grammarState` 和已经渲染好的 HTML 一起传给下一次，每个新 delta 只重新 tokenize 正在写的那一行——TextMate 的 tokenize 单位就是行，行内没有可续接的点。一批 200 行 typescript（约 9 KB）实测：全量一次 101ms，而续接之后重算最后一行 0.6ms、追加一整行 0.45ms、把 200 行已冻结的 HTML 拼起来 0.02ms——每帧的成本从 O（整块）降到 O（行）。HTML 是自己拼的（`renderToken` + `wrapHtml`），因为这条路径只需要 shiki 的 token、不需要它的 hast；`getTokenStyleObject` 负责把 fontStyle 位掩码翻成 `font-style:italic` 这样的真 CSS，`mergeWhitespace` 则照搬了 shiki 在拼 hast 之前那一步（把纯空白 token 并进后一个 token），不照搬的话每个词间空格都会是自己的一个 `<span>`，代码块的 DOM 大概翻倍。冻结只发生在「完整行」上，未完结的最后一行每帧都用冻结点的状态重算，所以块注释或模板串里那种跳行结构在流式期间颜色也是对的。

**单行长度上限不是保守，是必需。** JS 正则引擎的单行成本非常非线性：一行两万个字符实测要 **52 秒**，整页在这期间都是死的（原生 Oniguruma 不会这样，dsh 因此没有这道闸）。所以每次 tokenize 都带 `tokenizeMaxLineLength: 2000`——超过这个长度的行不参与分词、以纯文本渲染，栅栏本身照常显示。两千字符已经远超手写代码的任何一行，而更长的行本来就是压缩产物或数据倾倒，给它们上色不值得冻住页面。整块另有 2 万字符的上限，只作用于全量路径（见「已知限制」）。

**预热不再只覆盖入口语言，因为没预热的 grammar 会「先粗后细」。** JS 引擎的 pattern 是用到才编译的（`lazyCompileLength: Infinity`），一个从未跑过的 grammar 第一次 tokenize 出来的 token 比之后每一次都粗——同一块代码第二次绘制时颜色会变，正是这次要消灭的那类闪烁。所以 `warmUpLanguage` 在每条 tokenize 路径前被调用：动态 `import()` 的 grammar 落地后、在通知重渲染之前先跑一遍 `WARMUP_SAMPLES`（注释、字符串、数字、函数、标签、SQL 各一），保证第一次真实渲染就已经稳定。

**流式期间的「闪」和「跳」是另一组问题，按四个来源分别收拾。** （1）`message_update` 每个 token 触发一次 `setState`，比屏幕刷新快得多，`useConversation` 用 `requestAnimationFrame` 把它合并成每帧最多一次发布——`slotRef` 照常累积，落到的那一帧带着期间所有 delta，于是快流不再掉帧、跟随滚动也不再一顿一顿。（2）流式中的 assistant 消息**渲染在它即将落进的那一轮里**，而不是接在整条转录后面：pi 把提交后的消息追加到转录末尾，所以 partial 在最后一轮里的槽位正好就是它提交后要占的槽位（`group.messages.length`），React 于是在 `message_end` 时复用整棵 DOM，而不是把每个代码栅栏和思考行丢掉、再挂一份一模一样的（那会让代码块重新上色、思考行自己折回去）。只有转录里还没有任何一轮可挂靠时才退回独立渲染。（3）跟随滚动挪进 `useLayoutEffect`，滚动容器上关掉 `overflow-anchor`——原来在 paint 之后才贴底，每一帧都能看见「内容先跳上去、再弹回底部」，而浏览器的滚动锚定又在同时做反向修正。（4）`.code` 用 `scrollbar-gutter: stable` 预留横条位置：流式里一行会一个个字符地长过容器宽度，经典滚动条冒出来的那一下等于整块长高约 15px，下面所有东西跟着下移。另外 `Markdown` 按 `text` 记忆化、高亮结果按「语法 + 源码」缓存：前者让每个 delta 不再重新解析整个转录（包括几屏前早就定稿的答案），后者让 partial 变提交消息、折叠组展开收起这些「同样的文本再渲染一次」不再重新 tokenize。

**字号只写一个变量，其余靠 CSS 派生。** dsh 的字号是 10–22 的整数（`Schema.number().step(1).min(10).max(22).default(14)`，`packages/client/ui-theme/src/theme-settings.ts`；设置页的 `FontSizeRow` 读同一对常量，所以没有第二套范围）。`--dsh-content-font-size` 由设置页写成 `body` 上的内联属性——dsh 的 boot 脚本与 ThemePresenter 都写在这里，`gradient-shadow-text.css` 也是在 `body` 块里用 `calc` / `min` / `max` 从它派生 `--dsh-content-font-delta` / `-secondary` / `-delta-secondary`（那份是 dsh 原件，本项目一直就有）。范围与默认值现在都跟 dsh 一致（`server/src/store.ts` 的 `FONT_SIZE_MIN/MAX/DEFAULT`，前端 `DEFAULT_SETTINGS` 与 `web/src/lib/types.ts` 的边界常量跟着它）。同一个值也写在 `:root` 的 `--dsh-content-font-size` 上：第一帧的绘制发生在 `/api/settings` 返回之前，两处不一致的话会先闪一下再跳。变量自己的 `14px` 回退保留不动——那是 dsh 原件里的写法，只在根本没有声明该变量时才生效，而上面这一行恰好把那种情况排除掉了。

**真正断掉的是消费端。** `Markdown.module.css` 把正文字号硬编码成 13.5px、标题 19/17/15/14px，`MessageList.module.css` 把用户气泡写成 13.5px——全都不读那几个 token。后果是：改字号时只有工具行和思考行会动（它们读 `--dsh-content-font-size-secondary`），而读者停留最久的**正文一动不动**。接上 dsh 的 `--dsw-font-markdown-*` 尺寸后，正文 14→17px 时行高跟着 24→27px，标题按同一像素增量保持层级。顺带把基准从 13.5px 拉回 14px：dsh 的 `--dsw-font-markdown-base-font-size` 就是 `--dsh-content-font-size`，13.5px 是当初手写时滑掉的。code 与行内 code 保持固定，dsh 把它们归为密集次级文本。

**字号越界是拒绝，不是夹取。** 服务端校验 `Number.isInteger` 且 12 ≤ n ≤ 17，不合法直接 400。stepper 的按钮在边界上禁用，所以 UI 根本产生不出一个会被拒的值——一个悄悄存成别的数字的设置项比一个报错的设置项更难查。

**「对话显示」对齐 dsh 的四档，两层折叠，不是按消息。** 第一层是整轮：已完成轮次的思考与工具调用收进一行完成汇报，答案保持在原位；进行中的轮次没有这一层（表头是一句完成汇报），但见第二层。第二层是按步：一轮内被回答隔开的每段 process 各收成一个小分组，标题是活动摘要（`已读取文件并搜索代码`）或进行中的 `正在读取文件`；**正在流式的那一段也在里面**：`stepGrouping: 'collapsed'` 折的是「所有轮次」，所以运行过程中过程行同样折进小分组。四档由 dsh `ChatPresentationPolicy` 的三个字段决定（移进 `transcript-policy.ts`）：`foldCompletedTurns`（`verbose` 之外都为真）、`stepGrouping`（`compact`/`standard` = `collapsed`，`detailed` = `history`，`verbose` = `none`）与 `settledReasoningPreview`（只有 `compact` 为假）。所以 `standard` 折每一段、`detailed` 只折已关闭轮次的段（流式中平铺）、`verbose` 完全不折 —— **这是 standard 与 detailed 唯一的可见差别**。默认值跟 dsh 桌面端一致是 `standard`（上游对桌面注入的默认就是它）；两档时代存下的 `normal` / `expanded` 读入时迁移成 `standard` / `detailed`，所以存量 `store.json` 里的 `normal` 现在也会折叠，包括运行过程中。**这是对齐 dsh 最新版时改的**：此前只有「紧凑」折，「标准」平铺。这里踩了一个真坑：分区最初放在渲染单条 assistant 消息的组件里，于是一轮里每次工具往返都产出一个「执行过程」行——一个真实会话上量到 **23 个组**，而正确的数字是 **3**。改成在轮次层先把 assistant 内容拍平再分区后，3 个组分别是 27 / 16 / 12 项，加起来 55 = 32 个工具 + 23 个思考，**数量精确对上**。

**「繁忙时的发送行为」是本项目的设置，不是 pi 的。** pi 有 `set_steering_mode` / `set_follow_up_mode`，但它们管的是**已经排队的多条消息怎么投递**（`all` 还是一条一条），而 dsh 这一项问的是**Enter 键用哪种投递**——那是客户端选 `prompt`/`steer`/`followUp` 时决定的。所以它进 `store.json`，而且是 Composer 投递行为的**唯一来源**：输入框上不放开关。同一个问题有两个能改的地方，就得回答「哪个说了算」，而设置里改了、输入框里还留着上次点过的那个，是个纯陷阱；那个开关本身也不落盘，刷新就没。不常用的那一种本来就够得到：**Cmd/Ctrl+Enter 永远走另一个**（dsh 的说明里明确写了这一点，本项目此前没有实现），为一枚一运行中就出现的按钮不值得换掉这条规则。

**改 pi 的全局设置会让其他驻留进程过期。** `set_auto_compaction` 写的是 pi 自己的配置文件，而只有**新启动**的进程会重新读它——已经跑着的进程继续用它启动时那份。所以写入成功后除了当前 handle 之外全部关闭（`closeAllExcept`），代价是下次切到那些会话要付一次冷启动。改设置是低频操作，用一次稍慢的切换换「另一个开着的会话不会显示旧值」，值。

**没有「权限」也没有「语言」，因为做不出真的。** dsh 的权限是三档「仅可查看 / 工作区内修改 / 完全权限」，pi 侧对应的是 `trust`——而那是**「是否信任这个项目的动态配置（`.pi` / `.agents/skills`）」**，项目级、没有 RPC、语义也不是工具执行级别，放进「通用」里是错位的。语言则是单语言项目：列表里只有一个选项，等于摆了一个不会变的下拉。两项都留空，而不是放个占位。

### 快捷键

**协议是纯函数，碰 DOM 的只有一处。** `lib/shortcuts/binding.ts` 里没有 `KeyboardEvent`：它认的是 `{ code, modifiers }`——**物理键，不是 `key`**，因为 `⌥⌘B` 在 macOS 上打出来的字符是个 `∫`，按字符匹配迟早会散架。它负责规范化修饰键顺序、比较、拼键帽串。`environment.ts` 同样纯，输入只是 `{ desktopPlatform, userAgent }` 两个字符串。真正接触浏览器的只有 `use-shortcuts.ts` 里那一个 `window.addEventListener("keydown")` 和旁边的适配器，把事件压成同一个 `ShortcutGesture`。这条界线不是洁癖：正因为比较是纯的，那批断言才能在 Node 里对着真键盘事件跑（`Input.dispatchKeyEvent` 发出的就是同一批字段），不需要 jsdom。

**命令表由动手的那个功能注册，外壳只装监听。** 「打开右栏」这条命令的属主不能是右栏本身——它得在右栏还没打开的时候就能被按下。所以命令表在 `features/rightbar/shortcuts.ts`，`layout/AppLayout.tsx` 负责装上它（dsh 也是这个分工：快捷键服务挂在外壳，命令由各自的 feature 注册）。监听装在 `AppLayout` 还有一个本地原因：设置页是**取代**外壳渲染的，不是盖在它上面，所以 `AppLayout` 始终挂着，必须靠一个 `!settingsOpen` 关掉监听，否则在一个既没有会话、也没有右栏的页面上它仍然活着。

**浏览器列和桌面列不同，是因为那几个键已经归浏览器了。** `⌘P` 是打印、`⌘T` 是新标签页、`⌘⇧B` 是显示/隐藏书签栏——都拦不掉。所以浏览器运行的默认值改走 `⌥`（`⌥⌘P` / `⌥⌘T` / `⌥⌘B`），桌面版（Electron 壳，没有这些抢占者）保留 dsh 桌面版的原始绑定。`` ⌃` `` 两边一样，因为 dsh 刻意没把它设成 `primary`。

**键帽串的修饰键顺序是 `⌃⌥⇧⌘`，不是 `⌘⌥⇧⌃`。** 这不是随便定的：macOS 自己就按这个顺序印修饰键，`⇧⌘B` 与 `⌥⌘B` 正是系统「键盘」设置里的写法。渲染成 `⌘⌥B` 在 macOS 用户眼里像是打错了。Windows/Linux 用 `Ctrl+Alt+B`，顺序同样照 dsh 的 `modifierOrder` 走。

**`⌥⌘↵` 差点连带发出三条消息。** 这里有**三处** `Enter` 提交（`Composer`、变更面板的提交框、扩展问答卡片），它们原本只看 `event.key === "Enter"`，而 `⌥⌘↵` 现在归「面板全屏」——不处理的话，按一下会同时发消息和切全屏。三处都在 `Enter` 分支上加了「不收 `Alt`」，关键在于**同时不 `preventDefault`**：事件要留给快捷键层。dsh 的 Composer keymap 在同一处画了同一条线，注释原话是「返回 true 可以停掉 Lexical 的兜底换行，但**不消费**应用快捷键需要的那个 DOM 事件」。

**遮罩层只在真的挡住时才吃按键。** 层选择器是 `[role="dialog"][aria-modal="true"], [role="menu"]`——这不是 dsh 那个选择器的逐字拷贝，因为它对这里多了两种东西：转录里的扩展问答卡片是 `role="dialog"` 但**没有** `aria-modal`（它是一张卡，不是模态），用量弹层也是，这两种必须让快捷键照常工作，否则按 `⌥⌘B` 会莫名其妙什么都没发生。三个 `role="menu"` 弹层都是「打开时才渲染」，所以严格的选择器不会被永久挡住。

**提示文案与监听器读同一张表。** 按钮 `title` 里那句「收起右栏（⌥⌘B）」是从命令自己的 `defaults[runtime]` 现算的，不是手写的——手写就有两个地方要同步，而它们迟早会不一致，表现就是「悬停说按这个键、按下去没反应」。测试里有一条跨 `runtime × platform` 全组合的断言：同一个组合不能有两条命令，把「每个平台上的绑定唯一」这件事在表里就验掉。

### 输入框里的目录引用

**引用只显示目录名，发出去的是完整路径。** dsh 的 chip 背后是它自己的文件引用语法（`@dir/`），pi 没有这一层：`@file` 参数在 RPC 模式下被明确拒绝（`cli.js` 里那句 “Error: @file arguments are not supported in RPC mode”），TUI 的 `@` 补全也只是编辑器行为、不落在消息里。所以拖入文件夹插进去的是 `alpha/` 这样一段短名字，由输入框在发送时展开成完整路径（相对当前工作区，工作区外保留绝对路径）——而尾斜杠正是它区别于“一个恰好含斜杠的词”的标记（`referenceSpans` 的形状：行首或空白起、非空白字符、以分隔符结尾，且不能是 URL；没有 `@` 之后，这三条边界是承重的，不是修辞）。dsh 把 label 与 ref 一起存在那个原子节点上，这里 label 就是草稿里的字，而“label → 路径”的表放在唯一同时知道两者的地方（`useReferenceDraft`）。两个方向因此都有确定的答案：**手改过的 label 不再是那张表造出的字符串，于是不再解析、按用户看到的样子发出去**；反向的错误（把用户没写过的路径塞进消息）不可能发生，因为 label 只为这个输入框真的收到过的路径而造。

**同名目录不撞车。** label 默认取最后一段，被占了（无论是另一个目录还是用户手打的同名 token）就往外多带一段，一直到整条路径；同一个目录再拖一次则复用已有的名字。用长度换唯一性，而不是给 chip 加编号——`alpha/` 与 `alpha-2/` 会让人以为它们真是两个不同的目录。

**编辑器仍然是 textarea，chip 是画在下面的一层，而图标画在草稿自己的字符上。** dsh 为此写了一整套 contenteditable 引擎（Lexical decorator 节点、原子节点、投影与光标映射），这里不要那个代价：斜杠菜单、输入法、选区、自适应高度、粘贴图片全都靠 textarea 的原生行为，换成 contenteditable 等于把它们全部重写一遍。换来的做法是把 textarea 的文字设成透明（`caret-color` 不受 `color` 影响，光标照常画），下面压一层同样排版的镜像，由它把引用画成 chip。**chip 绝不改变宽度**——光标位置来自 textarea 自己的排版，宽度一变，光标就落在字的旁边而不是字与字之间——所以 14px 的图标不能挤进文字流，只能画在已有字符上：拖入的引用自带一个**图标槽**（`REFERENCE_SLOT`：一个 em 空格加一个空格），镜像层把图标盖在 em 空格上。图标左边缘因此正好落在普通文字的起点（不必为了它加宽卡片内边距），句子中间的引用也一样有图标、且不会压到前一个词。**没有任何一步依赖 em 空格真的等于 14px**：镜像层排的是与 textarea 一模一样的字符，字体把它渲染成多宽，两层就都是多宽，错位无从发生。**chip 对光标也是一个整体。** dsh 的 chip 是 Lexical decorator 节点、`isKeyboardSelectable()` 为假——所以一次 Backspace/Delete 就删掉整个节点，光标不会走进它内部；这里没有节点，但同一件事可以算在字符范围上：`referenceAtCaret` 判定光标是否落在某个引用内、或贴着按键来的那一侧，是就删整段（连图标槽一起）。插入后**总留一个空格**（dsh 的插入规则：原处是空格就复用，否则补一个），光标落在那之后——所以接着打字是与引用分开的一个词，而不是粘成 `alpha/x`。

手打的引用没有槽，于是只有颜色、没有图标（那里图标下面会是字母）。两类引用的边界也不一样：带槽的**即使句子紧接着它继续写**（`alpha/x`）也仍是 chip——槽是拖入写的、手打碰不上的形状，所以它不需要两边的空白——而手打的仍要求两侧空白，否则 `and/or` 那样的词就会变成文件夹。同一条纪律还决定了两个细节：选区填充必须半透明（否则不透明的选区会把下层正在被选的字盖住），textarea 的滚动条要隐藏（哪一层留出滚动栏、哪一层不留，换行点就分开了）。

**引用是相对工作区的，工作区外保留绝对路径。** 消息最终由 pi 在项目 cwd 下执行，相对路径就是它自己会解的那一个；一长串 `../` 虽然也能解，但工作区一搬就全错。浏览器拿不到文件夹的位置（与目录选择器同一道墙），所以网页版拖入文件夹只抬一条提示——这也正是 dsh 的选择（`attachment.directoryDesktopOnly`）。

**没做的那一半，以及为什么。** dsh 的 chip 能悬停、能点开（`appearance: 'file'` 带 `cursor: pointer` 与 hover 底色），这里只有静止态：镜像层不收指针事件（点击必须落在 textarea 上，那是唯一能编辑的地方），而在两层之间做命中测试等于把“光标在字符间的位置”重新实现一遍。悬停与点开要真做，该往 contenteditable 走，而不是在这层上再加一层。

### 输入框里的文件引用

**`@` 补全插进去的仍然只是路径，不是文件内容。** pi 在 RPC 模式下没有 `@file` 语法（`main.js` 里那句 “Error: @file arguments are not supported in RPC mode”），所以没有任何下游会把它展开；TUI 的 `@` 补全也只是编辑器行为，插入 `@path/to/file` 文本就结束了。这里照搬那一半：句子交给 pi 时带的是 `@src/lib/api.ts`，模型用自己已有的 `read` 去打开——pi 的 read 已经有行号、图片与 PDF 处理、自己的截断策略，自己拼一份 `<file>` 块不仅要重写这些规则，还会让上下文环的数字在发送那一刻悄悄涨一截。CLI 的 `@file` 参数确实会展开成 `<file name="…">内容</file>`（`cli/file-processor.js`），但那是参数解析而不是消息语法，在 RPC 里复刻它等于发明一套只有这个前端认识的口径。代价是多一次工具往返，而这是 pi 自己的回合里本来就会做的事。

**索引走 `git ls-files`，不是逐层列目录，也不是 pi 的 fd。** 补全要答的是「名字」：用户打的是 `@useComposer`，而不是一层层走进目录，所以逐层请求（右侧栏那种 `/files`）在这里没法用——一次按键就要把整棵树读进内存。`git ls-files --cached --others --exclude-standard` 一句话给出全部路径，而且三重恰好：一个进程而不是一次递归遍历；`.gitignore` 已经过滤过（agent 找不到的文件也不该出现在菜单里，这与 TUI 用 fd 得到的是同一套）；目录从文件的父路径推导，所以 `@src/` 这种「想往里走」的查询也有答案。不是 git 仓库的工作区回退到一次有上限的遍历（深度 8、两万条、跳过 `node_modules` / `dist` 这类），`getProject` 的项目白名单是唯一的入口检查——索引永远只在一个用户本来就能浏览的目录里建。索引按项目路径缓存 5 秒：一次按键一次 `git ls-files` 不可接受，而缓存过期重来的代价，比菜单里多一个刚删掉的文件小。

**匹配是「名字优先、路径其次、子序列最后」，同档里短的靠前。** `@api` 先给 `api.ts`，再给 `api/handlers/deep.ts`，最后才是把 `a`、`p`、`i` 拆散在长路径里的那些；同为名字命中时按路径长度打破平局，同长时目录在前——敲到目录通常是想到进去。这些规则是纯函数（`matchScore` / `rankEntries`，在服务端并有测试），客户端只渲染服务端给的顺序，不存在两处各排各的。

**目录不是终局，选完菜单不关。** 选一个目录插入的是 `@src/lib/`（带分隔符）、光标贴在 label 上而不是后面，菜单立刻按新 token 重新查询——`@src/lib/ap` 就是这样一层层走出来的，与 TUI 的目录补全一致（它的插入同样不加尾随空格）。选文件才是终局：插入 `@api.ts`、补一个空格、关掉菜单。**`@` 只认「开一个词」的位置**：行首、空白、开括号与引号之后，以及中文标点之后（`看看，@api` 触发，`看看@api` 不会——汉字不是边界，这点和 pi-tui 的 `autocompleteBoundaryRegex` 一致），所以 `mail@example.com` 是普通文本。路径里有空格时 token 写成 `@"my file.ts"`，展开回句子时这层引号也补回去——句子在空格处断词，一个未加引号的路径会在那里断成两个引用。

**chip 复用目录引用那一整套，只多一个 sigil。** 同样是「写入时换成短 label、`useReferenceDraft` 里存 label → 路径、发送时展开回路径」，同样共用 `REFERENCE_SLOT` 那个图标槽、同一套「同名就往外套一段目录」的铸币规则、同一个 `referenceAtCaret`（一次 Backspace 删掉整块，光标不会走进 label 中间）。差别只有两处：token 带 `@`（图标也跟着从文件夹换成文件），label 不带尾斜杠。一个细节两者共享：**再选一次已经在草稿里的同一路径，复用已有 token**——否则第二次提到 `src/lib/api.ts` 会铸出 `@lib/api.ts`，看上去就像指了两个不同的文件。而**手打的 `@api.ts` 不是 chip**：只有补全写进去的才带图标槽，手打的照旧是普通文字、发送时也不会被展开——「编辑过的 label 不再解析」那条规则的另一面，句子发出去的就是用户看见的。

**客户端只负责「什么时候问、答给谁看」。** 查询是防抖的（120ms——一次按键一次请求等于把本地服务当外网用），过期回答按 `(项目, query)` 丢弃而不是渲染（否则快速退格会让菜单从新到旧回放一遍），新答案未到之前保留上一个列表以免空一帧。**空菜单有四种处境，只有一种与用户的输入有关**：还在搜、没有匹配、这个项目的索引本来就是空的、请求失败。第四种在数据结构上就和前三种分开（`error` 与空列表是两个字段，不是同一列表的两种长度），因为把「服务端没回话」说成「没有匹配」会让人去改自己打对的那个词——而真正的原因可能是服务端跑的还是旧代码。服务端那边也把两件事分开：项目目录不存在是 404 加路径，不是一份空索引。`@` 与 `/` 两个菜单不会同时打开（触发字符不同），但渲染顺序与按键顺序还是显式写下来，而不是靠「它们碰不到」这句推断。

### 转录里的文件引用

**回答里能变成 chip 的只有两种写法，第三种不做。** 一种是作者显式写的链接：`[the loader](src/app.ts#L24-L30)`，GitHub 风格的 `#L24` / `#L24-L30` 是唯一认得的锚点，而带 `?` 的目标（`src/app.ts?plain=1`）整条拒绝——那是托管站的约定，这个前端解不开，把它剥掉打开另一个东西比不打开更糟。另一种是行内代码：`` `useConversation.ts:396` `` 与 `` `src/app.ts:24-30` ``（模型从 forge 复制来的 `#L24-L30` 也认）。**裸文本路径不做**，因为一句恰好含斜杠的话与一个引用在文本上无法区分，而所有把它俩分开的尝试都会把普通句子变成控件——dsh 的 Markdown 渲染器同样只认这两条通道（`file-link.ts` + `MarkdownFileMentions`）。行号从**最后一个冒号**读起（`:24`、`:24-30`，区间超过 500 行就截断），所以 Windows 盘符不会被当成行号；`weird:file.txt` 这种带冒号的名字则因为 `weird:` 长得像一个 scheme 而被拒——唯一被放行的单字母 scheme 是盘符。

**渲染器不猜路径，词汇表在本轮手里。** chip 存在的前提是「这个 token 真的是一个文件」，而这个判断需要一份真实文件的清单，`Markdown` 没有也不该有——它是七个地方共用的纯渲染器。判断因此放在轮的边界上（`turn-refs.ts`）：把这一轮每个工具调用参数里的 `path` / `file_path` 收集起来（读过的也算，不只是写过的，因为回答里提到的多半是刚读的文件），精确拼写优先，其次**basename 唯一命中**——和 dsh 的 `producedFileMentions` 同一条规则，也是 `` `index.ts` `` 在一个提了三个 `index.ts` 的轮次里保持普通代码的原因。词汇表取「本轮」而不是「整个工作区」：后者需要一个按 token 反查的索引（现在只有模糊搜索接口），而名称撞车在这种规模下只会更常见。解析器与匹配器都是纯函数、各有一份测试，所以这条规则可以单独钉住。

**流式期间一律不做，命中失败也不降级。** 一条写到一半的路径还不是引用，一个还没说完的回答的词汇表也还没定型——这时画出来的 chip 是猜的，下一个 delta 就得撤回来（dsh 的渲染器把这件事写成 `streaming ? undefined : parseFileLink(url)`）。而**没命中就是原来的样子**：行内代码仍是行内代码、外链仍是外链，没有灰色不可点的第三种状态。链接通道额外守一条：`[见 \`index.ts\`](https://example.com)` 里的行内代码处在一个锚点内部，而 button 不能嵌在 a 里，所以 `a` 渲染器给自己那一层子树打上标记、`code` 渲染器读它——dsh 用同一个 `inLink` 标志做同一件事。

**chip 是按钮，打开的是一次应用内导航。** 它要去的不是「一个 URL」，所以没有中键新开、没有地址栏，文件不存在时也该落在预览自己的失败态里而不是浏览器的错误页。芯片读的是**作者写的文字**（`[the loader]` 就显示 `the loader`），悬停的 `title` 才是完整 `path:line`——句子需要的是`useConversation.ts:396`，不需要它前面那四层目录，而悬停有地方放两者。标签缺省时用 basename 加行区间，区间用 en dash（`a.ts:24–30`）。

**行定位落在预览标签页上，而不是一次性传给正文。** 一个文件仍然只有一个标签页（打开同名的第二个文件从来不是谁的本意），所以位置存在标签页自己身上，第二次点同一个文件的另一行是把那个标签页**移过去**，而不是叠一份副本——这也让刷新之后位置还在（`readTab` 读回它，格式不对就整对丢掉）。代码分支在有位置时换成 `CodeView`：**一行一个 DOM 行**，因为行号只在行是一个元素时才滚得到，而 `CodeBlock` 画的是整块高亮。没有位置的打开一个字都没变：还是那块高亮的整体。

**行视图也要上色，而它要的那份逐行结果高亮器本来就有。** 逐行不等于放弃语法色：`highlightStep` 的 carry 里存的本来就是 `renderLines` 的产物——一个 `<span class="line">` 一项——只是 `wrapHtml` 把它们拼成整块文档发出去。所以新增的 `highlightLines` 只是把同一份结果剥掉外壳按行交出来（`HighlightStep` 因此多带一个 `lines`），`CodeView` 把每行放进自己的元素里。主题是 `css-variables`，颜色来自 CSS 变量，所以**亮暗切换不需要重新高亮**；语法还没到的语言、超过 2 万字上限的文件、以及超长的单行都返回 `null`，那时画的就是它已经有的纯文本——颜色是升级，不是前提。

**跳进一个大文件是一次扫描，不是把前面的页读完。** 1MB 以上走 `TextPager`，它按字节偏移分页（偏移让整次阅读保持线性，代价是偏移量说不出行号）。引用要的却正好是行号，于是这个反过来的方向由服务端答：`/text?fromLine=` 打开文件、按块扫到目标行（顺带往回带 200 行，让读者往上滚还有东西），从那里读一页，并在响应里带上 `startLine`——客户端于是不用知道前面跳过了什么就能给页里的行编号。扫描是这一条路上唯一一次 O(前面所有字节) 的读，也是它只发生在第一页的原因：之后的页仍按偏移续读。客户端那个「读页直到覆盖目标行」的循环因此退成兜底（老服务端、或行号超出文件末尾），仍然保留 20 页上限。

**图片引用悬停就出图，而不是先开一个标签页。** 一个路径算不算图片由部署说了算（`isImageName` 与服务的 `IMAGE_MIME` 是同一份扩展名表），字节则走 `/raw`：`<img src>` 让浏览器自己缓存、流式读取与解码，比把整张图 base64 塞进 JSON 再交给 React 画更接近这件事本来该走的路（PDF 走这条路是因为本应用没有查看器，图片走它是因为悬停要的就是一张图）。浮层用 `position: fixed` 加视口坐标（由 chip 的 rect 算出，向上还是向下看上方剩多少空间），因为段落所在的滚动容器会在自己的边缘把绝对定位的浮层剪掉；而**滚动或缩放会关掉它**——视口坐标在页面移动之后就不对了，重新进 chip 比重新测量便宜。浮层自己接指针，中间留 200ms 让指针跨过去；图片没加载出来就地把位置换成一句说明，chip 本身还在那里可以点。读取图片的地址就挂在 chip 上（`data-file-preview-url`），所以「这个引用有图可看」与「指针还没停够久」在测试里是两件事。

**`Markdown` 的 `components` 必须是模块级常量，否则整棵子树每次渲染都会被重建。** `react-markdown` 把 `components` 的每一项当作元素类型：写在组件体内的箭头函数每次渲染都是一个新类型，React 于是卸载整棵 markdown 子树、再挂一份一模一样的。代价不只是浪费——文件 chip 的悬停计时器、代码块的滚动位置、折叠行的展开状态都随旧树一起消失。这个问题是被端到端验证逼出来的：时间线探针显示 chip 在转录稳定后约 350ms 被重挂（`ref-set` → `ref-null`），恰好把已经开始的悬停弄丢，而手工再调一次事件处理器又好了。现在四个渲染器都在模块作用域，它们需要的一切（文件词汇表、流式标志、锚点嵌套）都从 context 取，`components` 因此是一个模块级的常量对象。

### 输入框里的图片

**图片写进会话文件时只有 pi 自己的 `ImageContent` 一种形状。** 粘贴、拖入、点附件按钮是三条入口，落到同一个 `{ type: "image", data, mimeType }`——`data` 是裸 base64，不带 `data:` 前缀。模型收到的、RPC 序列化的、会话文件里存的是同一个对象。**读回来时多了一种形态**：工具结果的图会随转录返回一个 URL（`/api/sessions/<id>/image/<序号>?v=<mtime>`，见 `server/src/session-images.ts`），浏览器按需取——一个截图很多的会话把整条会话的 base64 全塞进一个 `/messages` 响应就是 15–31MB，而读者只看其中一两张。用户消息的图保持内联：一轮失败可以重试，重试要把 prompt 自带的图重发给 pi，而 pi 要的是 base64。`src` 只在渲染那一刻算出（`imageSource`：内联拼 `data:` 前缀，外链直接用 URL），这是全链路唯一一次格式转换。

**上限是两端各写一遍的同一组数字。** 5MB/张、8 张/条。粘贴时 `readImageFile` 逐张判类型与大小，失败的**不连坐整批**——拖五个文件里混一个 PDF，另外四个照常附上，被拒的那张在缩略图条下面拼成一行说明（`a.pdf：不支持的格式 application/pdf`）。服务端的 `parseImages` 是同一规则的第二遍，因为 prompt 接口不只服务于这个输入框：curl 或扩展可以直接 POST，校验放在边界上，坏块才不会等到 spawn 完 pi、进到 provider 请求里，以「模型报错」的形式出现。

**只有图片、没有文字的消息是完整的一轮。** pi 无论如何都写 `[{ type: "text", text }, ...images]`，所以空字符串配一张截图合法；服务端把 `message` 从「必填」放宽成「message 或 images 至少一个」。客户端的乐观轮次用 `userContent()` 拼出**同一个形状**——不然那条消息会在重载后突然换个样子，而 fork 匹配（按 `textFromContent` 比对文本）也会跟着错位。

**缩略图点开是全屏查看，而查看器全项目只有一个。** `ImageLightbox` 挂在 App 层，因为能点开的图片来自三个地方：用户气泡、工具输出的 I/O 卡（`read` 读一张截图就是这种）、还没发出去的草稿。遮罩用 `--dsw-alias-bg-mask-photo`（dsh 专为看图准备的 88% 黑，不是对话框那档 32%），Esc 或点空白关闭，右上角 36px 圆钮与转录里「回到底部」那枚同一套尺寸。工具结果里原本会显示成 `[image]` 的占位文字一并去掉：图片下面就摆着图，再挂一个代表它的字符只是噪音。

**附件在气泡里是「先图后文」，气泡内边距随内容收窄。** 有图片时 `data-images` 把气泡的 `10/16` 内边距换成 `8`，图片贴着气泡圆角铺开（气泡仍 22px，图片自己 14px）；文字保留 8px 侧边距，所以第一行仍与消息边缘对齐而不是与图片对齐。工具行的图片则跨 I/O 卡的两列网格——它是答案本身，不是标签旁边的值。

**`image/svg+xml` 不在接受列表里。** 不是因为浏览器画不了，而是它是文档（也是脚本宿主），拿它当截图发给 provider 多数会直接报错；`png/jpeg/gif/webp` 是各家都解的四种。列表在两端各有一份（`ACCEPTED_IMAGE_MIME_TYPES` 与 `ACCEPTED_IMAGE_TYPES`），因为文件选择框的 `accept`、粘贴时的判断、以及服务端的上限必须给出同一个答案——三处只要有一处松，表现就是「点了没反应」。

**同一份草稿逻辑服务两个输入框：会话里的 Composer 与新会话页那张卡。** 两处必须是同一个行为（同样的上限、同样的三种进入方式、同样的拒绝文案），所以状态放在 `useImageDraft` 里，缩略图条与附件按钮放在 `AttachmentStrip` 里——两份拷贝就是「同一个」开始不成立的地方。新会话页的附件跟着首条消息过 `pendingPrompt`，等 draft 换成真实会话后再投递（`startDraftSession` 的第三个参数），所以「开一个新会话，第一句话就是一张截图」不需要会话先存在。

### 消息操作行 / fork

**每条消息下面有一行操作（复制、分支、用量、用时、时间），其中只有「复制」是纯前端的。** 其余三项都需要 pi 里真实存在的数据，而它们确实存在，只是藏得比较深：

**最新一段消息常驻，更早的行悬停（或键盘聚焦）才浮现。** 容器上的 `data-actions-reveal` 是 `always` 还是 `hover`，由消息自己的内容决定：最后一条用户消息常驻；最后一轮的回答只有在**这一轮真的收在一个回答上**时才常驻（`endsWithResponse`——最后一条是 assistant、往前跳过思考与空白占位，落在文本或图片上算收尾，落在工具调用上算还没答完），其余淡入淡出。**浮现的行不占位**：它离开文档流（两种状态都是 `absolute`，所以浮现时同样不重排，转录不会在指针下跳），挂在所属消息下方的间隙里，量的是转录自己的节奏 `--transcript-gap`——就是 `MessageList.module.css` 里 `.column` / `.turn` / `.turnTail` 共用的那个 14px，它借的这 14px 落在消息自己的底边（气泡或卡片的 padding）上，不碰文字；`always` 的行照旧留在流里，因为它本来就看得见，那条带子**就是**它自己，而把最新一条用户消息的行浮起来会盖住回答的第一行。这里与 dsh 有一处**有意的偏离**：dsh 只把它淡化（`opacity`），28px 的带子仍垫在每条更早的消息下面，加上转录自己的两道 14px，就是一块「没人在碰、却一直占着」的约 62px 空洞，几轮之后整段读起来是散开的。触屏设备不悬停，`@media (hover: hover)` 不成立时整行照旧常驻、也照旧留在原位。属性名与选择器逐条对齐 dsh，只有这条几何是刻意的差别。

**「用量」是可点开的按钮，不是一行静态数字。** 点开的 `StatPanel` 列出本轮命中的缓存比例与四个分桶（未缓存输入 / 缓存读取 / 缓存写入 / 输出），每个数都是这一轮自己的和——只累加 `totalTokens`、把四个分桶写成 0 的话，弹层一开就会显示「这一轮什么都没计费」。首屏那个数字仍然只是 `totalTokens` 之和，口径与下面这条一致。

- **用量**在每条 assistant message 自带的 `usage` 里（`{input, output, cacheRead, cacheWrite, totalTokens, cost}`）。一轮的用量是该轮所有 assistant message 的 `totalTokens` 之和——所以它是「本轮所有模型调用累加的 token 数，含缓存读取」，而不是可见答案的长度。一个 400 token 的回复坐在 30k 的上下文上会报 ~30k，这是对的。
- **用时**由时间戳算：本轮最后一条 message 的 `timestamp` 减去第一条的。**它是墙上时间，不是模型时间**——包含工具执行、排队、重试。别处没有更好的数据源；pi 的 TUI 有自己的计时器，但那是终端渲染层的东西，没有 RPC 能拿到。
- **分支**需要 `entryId`，而 `get_messages()` 返回的 message **不带 id**，只有 JSONL 里的 entry 带。

**时间戳只在自己是「今天」的时候省掉日期；说明文字是自绘气泡；复制成功的一秒。** 三处都照 dsh。时间戳是 `21:05`（今天）→ `9月17日 21:05`（同年另一天）→ `2025年9月17日 21:05`（跨年；英文写作 `9/17` 与 `2025-9-17`），日期部分走 i18n 的 `clock.md` / `clock.ymd`；判断用的「今天」来自 `useCalendarDay()`，不是渲染时现读的钟——转录可以开着跨过午夜，现读会把昨天的行一直显示成裸时刻。行里的说明文字不再用原生 `title`，换成 `components/Tooltip.tsx`：dsh 的气泡指标（13/20 字、`--dsw-alias-tooltip-bg`）、`role="tooltip"`、portal 到 `body`（转录区既是 `overflow-y: auto` 又声明了 `container-type: inline-size`，留在里面既会被裁掉、又会按容器而不是视口定位），位置交给 `tooltip-position.ts` 的纯算术：左右夹在边距内，上下只在首选侧放不下、另一侧放得下时翻面，两边都放不下就留在首选侧（叠住锚点还能读，推出屏幕不能）。复制后的对勾持续 **1 秒**（dsh 的值，这里原来是 2 秒），期间再点一次不排队——否则第二次确认会把自己的计时器续上，勾看起来像卡住了。

**entryId 是按位置配对、用文本二次校验的。** 一开始想用时间戳配对，实测发现不行：entry 的 `timestamp` 是**写入时刻**，message 的 `timestamp` 是**生成时刻**，同一条助手消息相差 4 秒（`toolResult` 两者相等，`user` 差 0.35 秒)。能依赖的是**顺序**：`buildContextEntries()`（pi 自己重建上下文用的函数）里筛出 `type === "message" && role === "user"`，其顺序与转录里的用户消息严格一致——在一个 13 轮会话上验过，**13/13 对齐、文本 0 处不符**。文本一并下发，客户端逐条比对，**不符就不显示分支按钮**：与其在错误的位罟分叉，不如不给这个按钮。

**pi 的 `fork` 是「从这条消息重新开始」，不是「截断当前会话」。** 实测（先备份、测完逐字节还原）：

```
原会话   210 行 → 211 行，且新增的那条是 plannotator 插件写的 custom entry
             0 个 entry 被移除，11 个用户消息 id 全部保留
新会话   另建一个 .jsonl（93 条 entry / 87 条 message / 2 条用户消息）
```

fork 到第 3 条用户消息时，新会话里只有 **2** 条用户消息——因为被点的那条是「要重新提的问题」，不在历史里。这一点和直觉相左，所以界面在分叉后**直接切到新会话**、刷新侧栏，并用一句通知说清楚原会话还在。（第一版把 `sessionPath` 当成新会话读回去，看上去像什么都没发生：`sessionPath` 始终是原路径，新分支在 `sessionFile` 里。）

**没有赞/踩。** 参考截图里助手消息下还有一对拇指，但 dsh 把反馈存在自己的 message 字段上，pi 没有对应字段也没有 RPC。那个按钮要么什么都不做，要么写到没人读的地方——**一个做不到事的控件比一个不存在的控件更糟**。

**曾经有一个话题树面板（已移除）。** 它把会话的 entry 树画出来、标出当前所在位置、在能分叉的节点上标「可分叉」。之所以没有「切过去」这个动作：pi 的 TUI `/tree` 能把叶子指针移到任意节点，但**没有任何 RPC 能移叶子**，分支相关的方法只有 `fork`，而它只接受用户消息。于是那个面板能提供的唯一动作，与消息操作行上的「分支」完全相同——而后者就在每一条用户消息下面，离要分叉的地方更近。保留一个只能看的浮层，只是把这个动作又包了一层。

**设置页的导航现在有四项。** dsh 的面板有模型 / 插件 / Agent 预设 等一节节，本项目做到了通用设置、模型、插件和 MCP，Agent 预设还没有。搜索框只在**插件**一节里有，而且是从 dsh 的插件列表照搬的：那一节列的是从磁盘和已安装包解析出来的清单，行数由用户的安装状况决定，不像通用设置那样固定四五行——一个能长出几十行的列表和一个永远四行的列表，要不要搜索框根本不是一个问题。MCP 那一节用两个筛选下拉代替搜索框，因为它列的是同一批配置在两种维度上的切片（作用域 × 状态），而条数通常是个位数。

### 模型配置为什么在改文件

**pi 的 RPC 覆盖的是「一个正在跑的会话」，不是它的配置。** `set_model` / `get_available_models` 这些操作的是进程状态，而 provider 定义和它们的凭据是**启动时读一次**——那时还没有任何会话。所以这一节直接编辑 `~/.pi/agent/models.json` 和 `auth.json`：

```
models.json  { providers: { <id>: { name, baseUrl, api, apiKey?, models: [...] } } }
auth.json    { <id>: { type: "api_key", key: "..." } }
```

两个文件都读，凭据**只写 `auth.json`**：pi 自己的登录流程就存在那里，而且把秘密集中在一个 0600 文件里，比散在一个用户很可能粘进聊天窗口的定义文件里好推理。pi 支持把 `apiKey` 内联写在 provider 里，这种情况也会被认出来（`keySource: "inline"`），但不由本页管理——编辑器看不到它的值，没法让用户决定要不要覆盖它。

**「自定义」徽章的判据是 pi 的 `KnownProvider`（41 个 id）。** id 不在那张表里，就是用户自己造的 provider，只有用户知道它的地址和协议。拿截图核对过：dsh 那边 `DeepSeek` 没有徽章（内置），`cz` 和 `CommandCode` 有（自建）——本项目里 `cz` 和 `commandcode` 同样带徽章，**判据一致**。那张表在 `models.ts` 里是字面量而不是 import 的，因为 `@earendil-works/pi-ai` 是 pi 启动器的传递依赖，pnpm 的严格布局不暴露它。代价是 pi 新增内置 provider 时它会被标成自定义——一个外观上的小误差，不是一次错误的写入。

**API 密钥是只写的。** 页面从服务端拿不到当前 key，所以没法显示或是回显；没动过输入框的保存**不发送 apiKey 字段**，服务端把「字段缺席」解释为「保持原值」，密钥因此活下来。占位文字就是 dsh 的那句「已配置——输入新值可替换」。这条不只是隐私：如果 key 能读回来，它就会出现在 DOM 里、出现在浏览器缓存里、出现在任何一次截图里。

**保存时按 id 合并模型条目，只覆盖编辑器渲染出来的字段。** 编辑器渲染每个模型的 `id`、`name`、`contextWindow`、`maxTokens`、`input`、`reasoning` 和 `thinkingLevelMap`，但一个模型条目还带着 `cost` / `compat` / `inputLimits`。**这里踩了一个真坑**：第一版把列表整个替换成渲染出来的两个字段，结果浏览器里改一个 provider 的名字，它下面所有模型都被削成 `{id, name}`——一个声明了 `contextWindow: 1000000` 的模型回来时上下文窗口为空，pi 会退回一个对那个端点而言错误的默认值。改成按 id 合并、渲染出来的字段各自覆盖之后，改名对其他字段是**逐字节无差**的（有测试守着）。**渲染出来的那几个字段是「缺席即清空」**：编辑器持有的是服务端读回来的那份值，所以空着的输入框是用户真的把它清掉了，此时字段从条目里删掉，让 pi 回到自己的目录或内置默认——留一个旧数字在文件里，等于让「清空」这个动作失效。删除仍然有效：编辑器列表里没有的 id 会被移除。**`reasoning` 与 `thinkingLevelMap` 是这一条规则的例外**：它们没有「空值」形态能表达「没动过」——不勾选就是 `false`（pi 读作「这个模型不思考」，本身就是一句声明），空 map 就是「没有额外档位」——所以合并时只有真的带了这两个字段才覆盖，缺席就保留文件里的原值。它们是唯一可能由人手写进去、而发现流程又不一定渲染的字段，把「没提到」当成「清空」会删掉用户自己写的声明。

**推理是一个行上的复选框，而不是 provider 级的设置。** 能力属于模型：同一个 provider 下面 `gpt-6.1-sol` 能思考、别的不能，放在 provider 上的控件只能提供一个有一部分模型会拒绝的值。而它**必须**是人来声明的——OpenAI 与 Anthropic 的 `/v1/models` 每条只有 `id` / `object` / `created` / `owned_by`（实测这个 `cz` 站点的 23 个模型全是这四个字段），pi 自己也不认识这个自定义 provider 下的模型，于是 `reasoning` 缺席就等于按「不推理」处理，那张卡片上写的是「思考强度不可用」。勾上它，`off` 到 `high` 五档立刻可用；`xhigh` 与 `max` 是提供方专属的档位名，按 pi 的规则只有 `thinkingLevelMap` 明确写了才有，所以它们是同一栏里另外两个复选框，且只在勾了推理之后可点。复选框只**增删这两个键**、不重建整张 map：手写的 `{"low": null}`（明确禁用某一档）或自定义 effort 名必须活过保存。

**两个容量字段在界面上是文本框，不是数字框。** `128000` 和 `128K` 说的是同一个容量，能写后者就不会有人愿意数零，所以 `model-capacity.ts` 负责两种拼写之间的翻译：`1M` 按 1000K 算（容量就是这么被引用的），能整除就缩写成 `K` / `M`、不能就原样写出来（`262144` 保持 `262144`）。打字期间的文本由行自己的缓冲持有，而不是每次按键都从数字重新格式化——那会把 `1000000` 在半途改写成 `1M`。读不懂的文本（`abc`）在行里存成 `NaN` 并且**拦住保存**：`JSON.stringify(NaN)` 会变成 `null`，而 `null` 会让 pi 拒绝读整个 `models.json`；拦下来的错误留在屏幕上，让用户看着那一行改。服务端也不信客户端，同样的拒绝在 `parseModelEntries` 里又做了一遍。

**输入类型至少留一个。** pi 的 `input` 是 `["text", "image"]` 的子集，而空数组不是「什么都不接受」、是「没说」——所以最后一个还勾着的复选框是禁用的，要取消它得先勾上另一个。没声明过 `input` 的模型显示为只勾「文本」，但保存时**不写入**这个字段（除非用户真的动过它）：屏幕上显示的是 pi 会替这个模型假定的值，不是我们替它做的声明。

**披露区默认收起。** 这三个字段是例外而不是常态：pi 自己认识的那些模型本来就带着窗口值，而写错一个上下文窗口比不写更糟。常开的五行控件会让最常做的那件事（改个名字）看起来必须先填完它们。

**状态点只说明配置文件里有没有凭据，措辞也跟着收敛。** 判断看 `auth.json` 的条目和 `models.json` 的内联 `apiKey` 两处，但**环境变量提供的密钥看不到**——所以 tooltip 写的是「配置文件里没有 API 密钥」，而不是「未配置」。用户用环境变量时这行不会误导他去重新输入一个已经生效的 key。

**写之前备份，写的时候原子替换。** 每个被改动的文件先落一份 `*.bak.pi-web-simple-<时间戳>`（沿用 pi 自己 `.bak.<后缀>` 的习惯），再用临时文件 + rename 落盘，权限 0600。改配置文件是一个崩溃就可能毁掉用户全部模型配置的操作，这两步都很便宜。

**改完关掉所有驻留的 pi 进程。** provider 列表是进程启动时读的，所以一个比这次编辑更早启动的进程会继续用它那份：刚加的 provider 在任何地方都看不见，刚删的还会应答。会话本体在磁盘上，所以代价只是下次切换付一次冷启动。

**「打开配置文件」在本项目里叫「复制配置路径」。** dsh 是桌面应用，能把路径交给操作系统去打开；浏览器不行。按钮名字改成它真正做的事，路径放在 `title` 里，点击即复制——一个承诺「打开」然后什么都不发生的按钮比一个范围更窄的按钮更糟。

**不列出未配置的内置 provider，虽然 dsh 会列。** 截图里 `DeepSeek` 带着红点出现在列表里，因为 dsh 知道它的端点与协议。pi 的 provider 必须在 `models.json` 里显式定义（含模型列表），所以我们不知道一个没配置的 provider 该长什么样——列出来点开也没有可填的东西。入口交给「添加提供方」：它从那 41 个 id 里选一个。

### 插件清单为什么交给 pi 自己解析

**「装了哪些扩展」这个问题，pi 的 RPC 答不了。** 一个正在跑的会话只知道它自己加载了什么，而设置页要回答的是「下次启动会加载什么」——那由磁盘上的 `settings.json`、`.pi/settings.json` 和已安装的包共同决定。所以这一节把解析交给 pi 自己的 `DefaultPackageManager.resolve()` 与 `SettingsManager`：两个都从本服务已经依赖的 `pi-coding-agent` 里导出。

**不自己走目录，是因为走不对。** 要复现的规则并不显眼：包的 `pi.extensions` manifest 与每包 filter 叠加、`extensions/` 下的自动发现与 `+` / `-` / `!` 覆盖模式合并、同一个包在项目设置里覆盖全局设置时的去重与 `autoload: false` 的增量语义。一个「看起来一样、实际不同」的清单比没有清单更糟——用户会拿它去判断 pi 为什么不加载某个文件。附带的好处是开关的编码：`pi config` 写的就是这些模式，这里照抄它的 `toggleTopLevelResource` 与 `togglePackageResource`。

**开关写的是带 `+` / `-` 前缀的相对路径，而不是删除条目。** 顶层扩展在所属作用域的 `extensions` 数组里追加 `-extensions/foo.ts`（相对 agent 目录，或相对 `<工作区>/.pi`），包内扩展写在包的对象形式里（`{ source, extensions: [...] }`）。这正是 pi 的匹配器拿来比较的对象（`relative(baseDir, path)`，`baseDir` 由解析器给出），所以写进去的模式一定会被读到。重复切换会替换同一条模式，而不是叠加——留一个 `-` 和一个 `+` 同时指着一个文件，下一次启动就变成掷硬币。

**写入走 `SettingsManager`，不是自己拼 JSON。** 它带着 pi 自己的字段记账、项目信任校验和写队列；在这里重新实现一遍那个格式，等于把 pi 拥有的东西复制一份，然后等它漂移。只有一点是我们自己做的：解析结果里对**本地包**的 `source` 是一个路径（本机是 `/var/folders/...` 那种临时目录名），所以包名从它的 `package.json` 里读——否则一行会叫 `probe-package-6Mwr5T`。

**没有「运行状态」，因为 pi 里没有这个东西。** dsh 的插件有 fiber 生命周期（加载中 / 等待依赖 / 运行中 / 卸载中），它的宿主能观察到；pi 的扩展是进程启动时同步加载进去的，诚实的答案会是「在 3 个打开的会话里的 2 个中运行着」——一个每渲染一次都可能变、而这一页没有便宜办法知道的数字。坏扩展的可见性在会话里，以 `extension_error` 事件出现在它真正发生的地方。

**没有「插件配置」标签页，因为 pi 侧没有那份 schema。** dsh 的第二个标签页给每个被宿主服务的 settings 命名空间渲染一张卡片；pi 的扩展不声明这种命名空间，它读什么写在扩展自己的代码里，所以没有东西可以据此生成表单。摆一个没有卡片的标签页比不摆更糟。同理没有运行时重载（`/reload`）按钮：那是终端里的动作，Web 侧没有对应命令。

**未信任的工作区照样列，只是不能改。** 清单是磁盘真相，信任状态（`ProjectTrustStore`）单独报出来，所以一个 `.pi` 里有扩展、但 pi 还没被信任的工作区会看到它们，并看到一行说明「不会被加载，也无法在这里改写」。开关置灰而不是隐藏——状态本身仍然是真信息。真的去写会被 pi 的 `SettingsManager` 拒绝，服务端把它翻译成一个 400。

**改完关掉所有驻留进程。** 扩展是启动时加载的，一个比这次编辑更早启动的进程会继续跑旧的那套。和模型写入一样：代价是下次切换付一次冷启动。本机实测这一页有 14 行（4 个自动发现的 `.ts` + 10 个包提供的入口）。

### 更新提示为什么分三条路，其中一条会代劳

**「pi 有没有新版」和「装的包有没有新版」是两个问题，答案来自两个地方。** pi 本身是这个服务的一个 npm 依赖（`@earendil-works/pi-coding-agent`），它的「最新版」由 pi 自己的发布端点回答 —— `https://pi.dev/api/latest-version`，也就是 CLI 启动时轮询的那一个。拿 npm registry 去比会报出 pi 从未公布过的版本（撤回的发布、预发布噪音），所以端点照用，只有版本比较是自己写的：`updates.ts` 里那份 semver 子集，发布版高于同版本预发布、数字段按数值比、无法解析的 tag 一律不当成更新。

**扩展的更新问题 pi 已经会答，所以不重写。** `DefaultPackageManager.checkForAvailableUpdates()` 正好做了要做的筛选：本地路径、钉死版本、没装到磁盘的包都不参与比较，`PI_OFFLINE` 也认。这份知识在 pi 里，复刻只会漂移。

**两条提示的「更新方式」不一样，因为后果不一样。** pi 是依赖，动它要改 lockfile 并重启这个服务，所以那一行只报版本、给一枚「复制更新命令」（`pnpm update @earendil-works/pi-coding-agent`），不做一枚假装能就地完成的按钮。包是运行时资产，pi 自己的包管理器就能换（`packages.update(source)`），所以插件页每一行直接带「更新」，更新完关掉所有驻留进程，下一条消息加载新副本 —— 与装一个新扩展是同一条路。

**项目自身是唯一一枚真会动手的按钮。** pi-web-simple 自己也在 npm 上，`latest` 标签就是它的「最新版」，所以这一行不另造发布端点 —— 和 pi 不同，这里没有一份比 registry 更权威的答案。差别在后果：它的发行形态（`npm install -g`、npx 缓存、`pi install`）都落在某个 `node_modules` 里，`npm install -g pi-web-simple@latest` 与 `pi update npm:pi-web-simple` 都是**原地换文件**，下次启动读到的就是新副本，所以这一行可以有一枚「立即更新」。选哪条命令不靠问，靠看代码自己在哪里（`PACKAGE_ROOT` 是否在 pi 的包目录下）。唯一不代劳的是桌面壳：它这份代码在 app bundle 里，上面两条命令更新的是另一个东西，所以壳启动服务时自报 `PI_WEB_SIMPLE_DESKTOP=1`，那一行于是只交出一枚「复制下载地址」（release 页），但**照样检查** —— 桌面版同样会落后，只是升级方式是重新下载安装包。

**更新成功不等于已经在跑新版本。** 服务端改的是磁盘上的副本，进程内存里是旧代码，这是唯一一个「做了什么」与「现在是什么」可以不一致的更新。所以成功后那一行说的是「已更新到 x.y.z，重启后生效」，而不是把状态翻成「已是最新」；服务端也不会顺手重启自己 —— 从正在作答的那个请求里重启，会先杀掉这条回答。另：版本号是**每次读 `package.json`** 而不是烘进产物（前端那份构建期常量只做兜底），否则更新完它还会接着报旧号。

**「检查失败」和「已是最新」分开报。** 网络不通时如果落回「已是最新」，那是在替用户下一个它并不知道的结论。所以 `error`、`skipped`、`available: false` 是三种状态，页面分别说「无法检查更新」「已跳过检查」「已是最新」；`PI_OFFLINE` / `PI_SKIP_VERSION_CHECK` 照 pi 自己的规则认。

**服务端缓存几分钟，是因为打开设置页不该等于发一次网络请求。** pi 自己每次启动最多查一次；这里缓存的粒度是「每个工作区一份」（项目级包可能落后而全局的没有），显式的「检查更新」按钮（`refresh=true`）绕过缓存。

**侧栏那枚圆点是用户作用域的答案。** 它回答的是「这个工具本身要不要动」，所以在 bootstrap 时用 user scope 查一次并常驻；三件事（pi、项目自身、被装的包）任一落后都点亮。设置页和插件页的行则解当前工作区的答案。两者按工作区 key 分开存（`updates: Record<string, UpdatesView>`，键是路径，`""` 是用户作用域），不会互相覆盖。

### MCP 管理为什么要自己解析这两份文件

**pi 内置了 MCP，配置就是两份 `mcp.json`。** 用户级是 `<agentDir>/mcp.json`，工作区级是 `<工作区>/.pi/mcp.json`；pi 启动时读它们、连上已经启用的服务器，`/mcp` 与 `pi mcp` 都围绕这两份文件。所以这一节没有可依赖的扩展，也不该有：一个「先装个扩展」的提示会误导——装 `pi-mcp-adapter` 反而会**替换掉** pi 内置的这套支持，`/mcp` 和实际连接的服务器都会换一个来源。

**所以解析由我们自己写，但语义照抄 pi。** 合并规则不复杂，但每一条都决定「页面显示的是不是 pi 真会连的东西」：工作区条目整条替换同名的用户级条目；工作区里没有 `command` / `url` / `type` 的条目只覆盖 `enabled` / `exposure` / `toolExposure`，其余字段（凭据在内）仍来自用户层；只在 `-` 与 `_` 上不同的两个名字共享工具命名空间，后者被拒；格式是严格 JSON——pi 的读取器也不接受注释，所以这里同样报错，而不是把注释隐去再重写一遍。一个文件读不了或某条非法不会让整页变空，也只是把那条记下来、在列表下面列出来。

pi 自己的 loader（`dist/extensions/mcp/config.js` 的 `loadMcpConfig` / `updateMcpServerConfig`）做的是同一件事，但没从包的 `exports` 里暴露出来。为一个能展示却是私有的路径而放弃「只依赖公开入口」这条线不值得，而复刻的代价是几十行可测的纯逻辑（`mcp.test.ts` 守着合并、命名冲突、覆盖语义和参数往返）。

**密钥值一步都不出服务端。** 视图里只有 `envKeys` / `headerKeys`（名字），没有值；编辑框里的值初始为空，**留空表示保持已存值，删掉整行才移除那个变量**——所以「没重打一遍」不会把密钥清掉，表单里的行集合就是最终的 key 集合。密钥值确实会进 JSON 文件（那本来就是 pi 自己的文件），这条规则只保证它不出这个进程；跨层编辑时，目标文件里没有的条目会回退到合并结果，免得因为写另一层而把已存密钥丢掉。

**参数是一行文本，但保存时只在它真的变了才拆分。** 编辑器把 `args` 数组连成一行显示，保存时如果逐字未变就原样写回原数组——否则 `--config=/a b/c.json` 这种含空格的参数会被拆成两个（有测试守着）；真改了就按空格拆分，与配置里那行命令的写法一致。

**「停用」是工作区级的，没有全局开关。** pi 自己的 `/mcp` 写的是 `<工作区>/.pi/mcp.json` 里一条只含 `enabled` 的覆盖项，所以 dsh 的「当前 profile」在这里对应工作区：没选工作区时那个按钮是禁用的，并给出原因，而不是假装它是全局的。反过来，如果工作区文件里已经承载了定义，`enabled` 就直接改在那一条上；一条完整定义被重新启用时，`enabled: true` 这个等于默认值的字段会被删掉，和 pi 写入时的做法一致。

**写回保留文件其余内容。** 保存、删除、启停走的都是同一条路：读 JSON、只改 `mcpServers` 里的一个 key、原子写回（临时文件 + rename，掉电不会截断）。顶层其它字段（例如 `autoEnableCodemode`）与用户手写、但表单里没有的字段（`exposure` / `timeout` / `oauth` …）都原样保留——一行行把表单字段拼成新对象，第一次编辑就会把没展示的配置抹掉。删除的两个语义细节：删的是**实际承载定义的那个文件**（工作区在前，用户级在后）；删掉一个只用来停用的覆盖项会把用户层那个定义重新暴露出来，这句话写在确认框里，而不是等删完才发现。

**「检查」是真的连一次。** 它做的是 pi 启动时同样的握手：`initialize`，然后 stdio 再发一次 `tools/list` 并把工具数报出来。只在点击时跑：一个 stdio 条目可以是任意命令，`npx -y something@latest` 冷启动可能要几十秒，所以超时给了 15 秒，状态也只挂在那一张卡片上。HTTP 只做 `initialize`——取工具列表要先拿 `Mcp-Session-Id` 再往返一次，收益不抵复杂度。pi 内置支持只认 stdio 与 streamable HTTP，所以没有第三种传输要处理。本机实测：`mobai` 2.0 秒握手成功，服务端公布 22 个工具。

**「重启」就是关掉所有驻留的 pi 进程。** dsh 重启的是它自己；这里能做的等价事情是让下一条消息重新 spawn 一个，于是一次性关掉全部（会话在磁盘上，代价是切回去时一次冷启动）。MCP 配置和扩展、模型、provider 一样，都是启动时读的。

**页面底部列出这一节读写的文件。** dsh 不列，因为它有自己的注册表；这里的配置就是 pi 自己读的那两份 `mcp.json`，卡片上的「停用」实际在写工作区那一份——把路径写出来，按钮才不是一个猜测。

### 获取可用模型

**「获取可用模型」这件事 pi 做不了。** `get_available_models` 报的是**已经配好**的模型，而 pi-ai 里的 `refreshModels` 是**每个 provider 自己的方法**（各 provider 自建 `models-store.json` 条目，比如 `opencode-go`），而且 `@earendil-works/pi-ai` 不在依赖树里。所以这个请求由服务端自己发。

**地址与认证头按协议选。** Anthropic 的列表端点在版本前缀下面（`https://api.anthropic.com/v1/models`），而它的消息端点是 `{baseUrl}/v1/messages`，所以 `anthropic-messages` 拼 `/v1/models`，其余拼 `/models`——**但如果用户已经写了 `/v1` 就不再接一次**。把 `https://host/v1` 拼成 `/v1/v1/models` 不是一个任何 provider 会服务的路径，而粘贴一个带 `/v1` 的 base URL 很常见。认证头同样分两种：Anthropic 用 `x-api-key` + `anthropic-version`，其余用 Bearer。

**响应形状宽容一点没代价。** OpenAI 和 Anthropic 都答 `{ data: [{ id, … }] }`（Anthropic 把显示名叫 `display_name`），而自建网关也常见 `{ models: [...] }` 和裸字符串数组。三种都收，代价是一个分支。

**网关肯说多少就顺手收多少。** 那两个官方端点每条只给一个 id，但前面带一层网关时通常还带着能力字段：OpenRouter 的 `architecture.input_modalities` / `supported_parameters` / `top_provider.context_length`、LiteLLM 的 `model_info.supports_reasoning`、vLLM 的 `max_model_len`。这些字段都被读进待加入的条目（窗口、输出上限、模态、推理），用户不必把一个提供方刚刚告诉我们的值手抄一遍。**只认肯定信号**：`reasoning: false` 不采纳，因为它在网关的语境里既可能是「这个模型不能推理」、也可能是「这个模型不返回思考文本」，而 pi 会把后者读成前者、把一个能思考的模型的滑轨藏掉——不写则留给 pi 自己的目录回答，方向是安全的（少给几档，绝不凭空造一档）。数字同样挑：整数或纯数字字符串，`0` 和负数当作占位符丢掉，因为 pi 会拒绝读一个装着它们的 provider。

**参数是「表单里当前的值」，不是已保存的 provider。** 这个功能最有用的时刻就是**建一个 provider 的时候**——那时还没有 id、也没有文件可读。所以接口收的是未保存的 `baseUrl` / `api` / `apiKey`，密钥未填时服务端回退到 `auth.json` 里存的那个（**回传的只有模型列表，密钥永远不回前端**）。没有任何写入，所以不会清掉驻留进程。

**已在目录中的模型默认不勾选，重加也不会覆盖已有条目。** 列出是因为一个用户找得到的模型在列表里看不到，读起来像拉取失败；默认不勾是因为这个对话框最常被打开的理由是「看看我漏了什么」，而已经在文件里的那些恰好是重加一次就会出问题的那批。它们仍然可勾——但合入时**已有的条目赢**，所以手工改过的 `contextWindow` / `cost` 不会被端点报回来的值替换掉。

**「全选」作用于筛选后的行，不是全部。** 搜索框里打着字的时候，「全选」如果连被你筛掉的也选上，这个意外会在保存之后才发现。

**这个功能真的有价值，不只是对齐截图。** 实测：用户的 `cz` 提供 **11 个**模型，而 `models.json` 里只配了 **5 个**——发现这个差别正是这一节存在的理由。

**删除的确认文案分两种，因为后果真的不同。** 凭据在 `auth.json` 里时，提示是「会移除其配置和存储的 API 密钥」；否则是「其使用的凭证（如有）由其他位置管理，将会保留」——环境变量给的 key 从来不是我们写的，删除 provider 也不该去碰它。两句都是 dsh 原文。

**这一节的样式和逻辑照 dsh 重做了一遍。** 行不再是 44px 的扁条，而是 dsh 的卡片（`settings-card-fill` / `settings-card-stroke` 这两个 token 也是这次补进主题的）；编辑器不再是弹窗，而是就地展开在那一行下面——**同一时刻只有一张卡**，点第二行的「编辑」会先把上一张和「添加」卡收起来。添加入口从两个按钮变成一个：卡片顶上是一个分段控件，在**第三方模型提供商**（从内置目录里选一个 pi 已认识的 id）和**自定义模型 API**（手写 id、地址、协议）之间切换；两块面板一旦访问过就留在 DOM 里只做 `hidden`，所以来回切不会丢掉任何一边填了一半的内容，切换本身在有一边正在写入或正在问端点时禁用。

**页面标题也改用了 dsh 的 `.title`（16/24）。** 最初这里写的是 20/28 的 `.heading`，理由是「dsh 的 `.title` 上面还有一层外壳的页面标题，这个应用的四节各自渲染 `<h1>`，字号该跟着角色走」——像素级对齐之后这个理由不再成立：同一个位置两边就该是同一个字号。连带的是标题行的高度：`.title` 的行盒是 24px，配置路径按钮也从 28px 收到 24px，否则它会把标题行撑高 4px，下面每一行都跟着往下挪。

**dsh 有三处在这里没有对应物，所以没有照搬。** 一是分区内的「已保存」提示：这个应用已经有一条全局通知栏，同一个事实写两遍只会有一条先过期；二是只读提示：pi 的 models 视图里没有 `writable` 这个概念，能读到就一定能写；三是首次运行时的「整节 setup 卡」——dsh 会把一个还没配密钥的 provider 直接渲染成它的设置卡，而 pi 不会列出一个没在 `models.json` 里定义过的内置 provider，没有行也就没有那种卡。

**模型目录那一块照 dsh 分了标题行和元信息行。** 标题行右边是「获取可用模型」（表单里的地址还没填时禁用，`title` 说明原因）和「恢复默认模型」；元信息行说这个 provider 的目录是**已自定义**还是**正在使用 pi 内置目录**。恢复默认只给 pi 认识的 id——自定义 id 在 pi 那里没有目录可回退，那个链接只会把用户自己写出来的列表删掉。

**分段控件是本地实现的。** 这个仓库没有 primitive 组件库，所以 dsh 的 `SegmentedControl` 被搬成 `SegmentedControl.tsx`，连同它的键盘行为（方向键在可用的段之间绕行、Home/End 到首尾、指示条靠 `--dsh-segment-count` / `--dsh-segment-index` 做一次 `translateX`），而不是换成两个 radio 或一个 `<select>`——`role="tablist"` 加 `aria-controls` 正好把两块面板的 `id` 定下来。

**样式表是整份抄过来的，不是照着重写的。** `ModelsSection.module.css` 就是 dsh 那一份（724 行），只在末尾追加了这个页面自己的外壳类（标题、说明、配置路径、加载态、对话框按钮），`ProviderEditor.module.css` 和 `FetchModelsDialog.module.css` 因此删掉了。这样两边的样式可以逐 token 对照；缺的三个 token（`--dsw-radius-xl`、`--dsw-alias-settings-card-fill`、`--dsw-alias-settings-card-stroke`）补进了 `design-platform.css`，后两个在 dsh 里本来就是 `bg-layer-2` 和 `border-l4` 的别名。

**像素级对齐先要对的是主题，不是样式表。** 用脚本把两边的主题树解析成浅色/深色两张表，再把这一节样式表引用到的 33 个 token 逐条解析 `var()` 链比一遍，只有 3 处对不上：`--dsw-alias-state-business-primary`（深色，真差异）、`--dsw-elevation-soft`（深色，是解析器的假阳性——dsh 深色块里有一条 `[data-menu-material]` 覆盖改写了描边色，两边实际都是 `border-l3`）、`--dsw-focus-ring-color`（这个应用根本没有，见下）。样式表本身既然是整份抄的，对不齐就只可能出在 token 上，这也是先查 token 的原因。

**深色下的 `--dsw-static-deepseek-400` 是唯一一处真正的颜色偏差。** 应用写的是 `rgb(103, 158, 254)`，dsh 是 `rgb(122, 170, 255)`；浅色走 `deepseek-500`，两边一致，所以只有深色偏。它经 `--dsw-alias-state-business-primary` 传到这一节的输入框聚焦边框和焦点环兜底色，也就是「深色下点进输入框，边框那一下蓝得不一样」。改成 dsh 的值即可，其他 token 不动。

**焦点环缺的是整个 `focus.css`。** dsh 的键盘环不是某条 `:focus` 规则，而是一套三件：`:root` 上的 `--dsw-focus-ring-width: 2px`；`:focus-visible` 读 `--dsw-focus-ring-color`（没有就退到 `business-primary`）；以及 `html[data-input-modality='pointer'] body :focus-visible:not(:read-write)` 把指针交互下的环涂成透明——鼠标点按钮不出环，键盘 Tab 才出。这个应用原来一条都没有，只能靠组件自带的 `box-shadow` 兜底（这一节的按钮就是），而输入框、复选框这类没自带环的地方就完全没有反馈。`focus.css` 整份搬过来；`input-modality.ts` 也搬，但改成显式调用（`main.tsx` 里 `watchInputModality()`），因为「模块加载即挂监听」的写法在这个仓库里没有先例。

**宽度对齐的是外壳的列，不是分区自己的 `max-width`。** dsh 的设置面板是 800px 浮层减 188px 导航栏 = 612px 内容列，里面再留 24px 内边距，所以那一节实际渲染 **564px**。这个应用原来是 748px——那是 dsh 的**对话正文**宽度，当初是类比来的，不是照抄；加上 24px 内边距后分区是 612px，比 dsh 宽 48px。改法有两条：把 `.inner` 收成 564px，或者给每个分区加 `max-width: 564px`。选前者：后者等于让抄过来的样式表多一条 dsh 没有的规则，而前者的 564 正是「列宽减内边距」，是 dsh 那两层的算术结果。

**dsh 的 Modal 指标搬进了这个应用的 Dialog 壳。** 两边弹窗的来源不同（dsh 是 primitive 的 `Modal`，这里是 40 行的 `Dialog`），但外壳指标可以照搬：遮罩 `z-index: 1000`、`bg-mask-1` 填充、2px 背景模糊；面板 `radius-panel`(28) + `bg-layer-2` + `elevation-prominent`、头部内边距 22/14/12/24、关闭按钮 28×28、描述 14/22 且左右 24px、底部内边距 24px、内容间距 20px。删除确认因此是 480px、模型选择器是 380px——`.fetchDialog` 那条 `max-width: 520px` 在 dsh 里也不起作用（`width` 已经是 `min(380px, 100%)`），它只是不让更长的标题把面板撑开，所以照抄不动。

**复选框和图标也回到 dsh 的 primitive 库。** 这个仓库没有 Checkbox 组件，所以原生 `<input type="checkbox">` 带上 `ui-primitives/Checkbox.module.css` 的指标：16px、`accent-color: brand-primary`、标签 14/20、禁用时整行 0.5 透明度。图标同理：dsh 的 `IconChevronDownOutline16` / `IconChevronRightOutline16` / `IconCloseOutline16` 是描边 1.5 的**方头**线段，而本仓库的 `Glyph` 默认 `stroke-linecap: round`，直接换成 outline 图标会圆头——所以 `Glyph` 加了按图标声明的 `strokeLinecap`，`trash` 也标成 `butt`（dsh 的垃圾桶同样是方头）。

**对齐是在真浏览器里量出来的。** 用 CDP 驱动本机 Chrome（1440×900，DPR 2 以便看清 0.5px 描边），浅色与深色各读一遍几何，与 dsh 的声明值逐项对照：分区 564px、标题 16/24/500 落在 y=32、说明 14/22 落在 y=68（= 24 + 12，与 dsh 同）、行列表 `gap: 8` + `margin-top: 12`、卡片内边距 12/14、圆角 20、描边 0.5px(`border-l4`)、填充 `settings-card-fill`、行内间距 12、标签 11/16、圆点 8px、行内按钮 28px/左右 10/圆角 8、添加按钮 44px 虚线/圆角 16、编辑器内边距 14/16/圆角 16/间距 14、密钥输入 32px/圆角 12、目录标题 12/18、模型行网格 `1.4fr 1fr 28px 28px`/间距 6、模型条目内边距 6/圆角 16、展开区两列 236px/间距 8、复选框 16px、分段控件 `grid`/间距 2/内边距 4/圆角 12（指示条 136×28、圆角 8、深色下描边是白色 20%）、以及上面那组弹窗指标——全部命中。深色下另测了 `deepseek-400` 的传播链：输入框聚焦边框实测 `rgb(122, 170, 255)`，与 dsh 一致。

**顺带看清了 dsh 的弹窗和选择器都来自 primitive 库。** `Modal`、`Checkbox`、`SegmentedControl`、`Button` 都在 `ui-primitives` 里，dsh 的 `ModelsSection.module.css` 只写布局不写控件——所以这份样式表能整份抄过来，前提是这些控件的**指标**也一起抄（上面三条），否则抄过来的只是骨架。这个仓库没有那一层，于是控件就落成原生元素加本地样式。

**图标从 dsh 的产物里取出来，逐字节相同。** 这一次新增了四个 glyph：侧栏齿轮、外观三个方块（`IconLightOutline16` / `IconDarkOutline16` / `IconFollowsystemOutline16`）。字号 stepper 的上下箭头共用一套 chevron，向上的那个是 `rotate(180deg)`，而不是第二份 path。插件那枚拼图和 MCP 那枚两端连线，是**两枚不是 dsh 原件的 glyph**：dsh 的插件分区和它的 MCP 面板都不声明导航图标（它的轨道按分区注册的内容画，而这两节注册的都是空的），所以形状是按同一套规则补的——16px viewBox、单条描边路径、1.25 线宽（和 `database` / `clock` 同一基线）——`dsh-icons.tsx` 的注释里也这么写着。刷新按钮直接复用了 `icons.tsx` 里的 `RefreshIcon`，没有为这一节再造一个圆箭头。

**图标是从 dsh 的产物里取出来的**。dsh 的工具图标表是 Figma 导出的（bash→终端方框、read→浏览、edit→铅笔、search→放大镜、其余→星芒），`dsh-icons.tsx` 里是逐字节相同的 path。它们是纯填充（`fill: currentColor`）而不是描边，所以没和 `icons.tsx` 那套描边图标混在一起。

**右侧导轨是会话的索引，不是会话的地图**。`TurnNavigator.tsx` 在每个轮次旁边放一条 12×2px 的圆角短线：悬停显示该轮的内容卡片，点击滚过去，键盘 Tab 也能逐个预览。轨道全长只有几条线，但每个标记承担的是「用户提的一个要求」而不是「一条消息」——分组在 `turn-rail.ts`，遇到 user 消息开新一轮，助手回复和它触发的所有工具往返都留在同一轮里。

**标记是等间距的**（10px 一档，`TURN_SPACING_PX`），这正是它能用一次除法反推指针落在哪个标记上的原因（`itemAtPointer`）；如果按内容高度摆放，它就不再是索引而是缩略图了。首尾各留 6px（`RAIL_INSET_PX`），整条轨道的高度就是 `(轮数-1) × 10 + 12`——实测 3 轮时 32px、标记中心整齐地落在 433/443/453。轮次多时封顶 420px 并在内部滚动，上下各用 `mask-image` 渐隐一段 24px 的带子，这样「被裁掉的轨道」和「就这么长的轨道」一眼能区分开。窄于 900px 时整个导轨隐藏（容器查询）——再窄它就要压在它本意要索引的文字上了。

**当前轮次是数出来的，不是猜出来的**：在滚动区顶部往下 `min(96px, 高度的 20%)` 处拉一条探针线，取最后一个起点在线上方的轮次（`turnAtLine`）。跳转用 `scrollTop += rowTop - 24` 而不是 `scrollIntoView`——后者没法在目标行上方留出固定空白，会把标题贴在面板边缘。跳转后若没落到底部就关掉自动跟随，否则下一个流式增量会把读者拽回去。

**三处与 dsh 的偏离，都是因为它有分页而我没有**：dsh 的轨道由「已加载窗口 + 未加载的 outline 投影」拼接而成，所以有 `markUnloaded`（8px、60% 透明）、「加载并跳转到第 N 轮」文案，以及点击后等待 `loadThrough(seq)` 的忙态；pi 一次读回整个转录，每个标记都是已加载的，这些状态没有对应物。另外 dsh 用 `100dvh - composer-height (152px)` 估算轨道所在带子的高度，我改成用 `ResizeObserver` 量滚动容器的实际高度——顶部多一条横幅或错误条时不会失准。

**「回到最新」是第二条通往底部的路，但它和自动跟随共用同一个判断**。dsh 在右下角浮一个 36px 圆钮，往上翻过 80px 就出现，点一下滑回底部；这里照做，只是把「是不是贴底」这一个答案同时给了两个消费方——是否继续跟随新输出仍然只看 `STICK_THRESHOLD_PX`，而按钮在不在场必须能触发重渲染，所以同一个值也存进 state，`applyPinned` 是唯一的写入口，ref 和 state 不可能各说各话。圆盘用零高度 sticky 槽位浮在滚动区底部（和上面那条导轨同一个技巧），而不是给滚动区套一层 `position: relative` 的外壳：外壳会把导轨重新挂到另一个父节点上，而导轨的算术是对着滚动区本身写的。

**平滑滚动期间要假装什么都没发生**。动画会经过沿途每一个偏移量，若照单全收，按钮会在半空中重现、自动跟随也会被解开——读者要的是「到底」，不是「停在半路」。所以跳转一开始就置上 `jumpingRef`，滚动处理在这期间只记账不判底，直到三种信号之一出现：`scrollend`（浏览器说滚动结束了，包括被滚轮打断、以及因为底部在动画期间被流式输出推远而追不上）、到达底部、或者 `scrollTop` 开始变小（读者接管）。三种都留的原因是它们各自都有盖不住的情况：`scrollend` 最权威但不保证存在，偏移量序列永远不会告诉你「动画放弃了」，而只看向上滚动则会在「内容长到追不上」时永远卡住。跳转被打断时，解除抑制的那一次滚动事件必须顺手判一次底，否则「滚一下就走」的读者会看到按钮再也不出现。

**一个真 bug 值得记下**。`syncActiveTurn` 用 `requestAnimationFrame` 节流，标志位是 `frameRef`；cleanup 里 `cancelAnimationFrame` 了却没把这个 ref 复位。于是 StrictMode 的双挂载在**第一次渲染**就踩中：effect 排队一帧 → 卸载时被取消 → ref 仍是非空 → 之后每次调度都认为「已经有一帧在排队」而直接返回，轨道永远停在初始状态（安安静静，不报错）。修复是 cleanup 里无条件把 ref 置回 `null`。

**底部不只是「消息变了」才需要重贴**。上面那条自动跟随挂在 `view.messages` 和 `view.partial` 上——流式输出会碰它们，但转录的**高度**还会被很多别的东西改：点开某个已完成轮次的过程组（这一组就可能是几千像素）、展开一个工具行、附件里的图片加载完成、设置里改正文号、todo 或提问卡片把输入栈撑高、窗口被拖小。这些都不经过消息，所以不会触发那一次重贴，而**也没有别的东西会把读者带回去**：带用量/用时的消息操作行被推到折叠线以下，`pinned` 却还是 true，于是「回到最新」的圆盘也不出现——看上去就是那一行「偶尔」跑到窗口底部之外，而且没有回去的路。实测两个：窗口从 900 压到 700，`scrollTop` 停在 962、`ch` 由 643 掉到 443，行落在可视区外 192px 且按钮不在场；展开最后一轮的过程组，内容从 1605px 长到 7960px，行掉到折叠线以下 6347px。修法是一个 `ResizeObserver` 同时看滚动区和消息列：跟随时 `scrollTop = scrollHeight`，不跟随时只重读一次距离（与滚动处理、与上面那个 layout effect 的第二个分支同一个判断，所以按钮不会和跟随状态各说各话）。dsh 拆的是同一件事——`ChatViewport.attach` 观察消息列、滚动区和 composer，`resize` 事件的全部内容就是「跟随时就再跟一次」（`use-chat-scroll` → `ChatReading.onResize`）。观察消息列而不只是滚动区是必须的：折叠和平铺展开改的是列自己的高度，滚动区毫不知情。

**「发出去」是第三条回到底部的路，而它不需要点。** 输入框始终钉在窗口底部，所以一个上翻去重读旧答案、又忽然想说点什么的人，其实是在说「我想看接下来发生什么」——这条消息本身就该把转录带回末尾。信号是 `ConversationView.sentAt`：这个浏览器自己发的每一句（prompt / steer / follow-up、命令、重试、回答待答问题）都经过 `useConversation` 的 `send` / `runCommand`，所以一处打点就够，不必让每个调用点自己记得说一声。它**故意不是**「出现了新的 user 消息」：pi 从终端记下的消息、或者刷新后才出现的行同样会让 `messages` 变长，而正在读的人不该被别人的消息拽下去。转录只认**变化**一次（一个 ref 记住上次认过的值）：先 `applyPinned(true)`——跟着走，答案的每个增量都留在最底下、圆盘也不会再出现——然后在**同一个 commit 里**落到底（layout effect 里的 `scrollTop = scrollHeight`），所以读者自己那句话不会被画在折叠线以下。落底是瞬时的，不走圆盘那条平滑：他要的是答案，不是再逛一遍刚离开的转录。这个值在切会话时**不复位**：跨会话它没有意义，而一旦复位，切换本身就会被读成一次发送、把下一个会话的读者按住不放。

**转录短于一屏时列是顶对齐的，这一点与 dsh 一致，这里不动**。消息列没有 `min-height`，也不会把内容推向底部（dsh 的 `.column` 同样如此），所以只有一两轮的会话里，那条操作行会浮在离底边很远的地方——实测把内容压到 58px 时它离底边 631px。它**稳定**地待在内容末尾，「偶尔」跳动的从来不是它；要改的是「内容不够一屏时贴着输入框」，那是另一种版式（聊天软件多数如此，dsh 不是），需要单独决定。

**卡片预算是 50 / 120 字符**（`PROMPT_PREVIEW_LIMIT` / `RESPONSE_PREVIEW_LIMIT`），对应卡片的一行标题加最多三行摘要，连同 `preview()` 里那个 `limit * 2` 的预读上限一起照搬 dsh——不设上限的话，轨道的工作量会随每一个回答的长度增长。截断是**按字符**切的（`word word w…`），不向词边界回退：卡片宽度已经由 CSS 的行数钳制决定，从这里再回退一次只会让它和真实文本差得更远。

**没有的东西是有意没有的**。dsh 的编辑行还带 `+18 -18` 的 diff 统计、把路径做成虚线下划线可点开的文件链接，并有一个悬停才出现的「查看」药丸。pi 的结果只给 `Successfully replaced 2 block(s)`，没有行级 diff；文件也打不开。这三样因此都没做——用参数行数近似出来的 `+N -M` 会是个看起来精确、实际错误的数字。

### 每轮末尾的改动文件卡片

**卡片是转录的投影，不是工作区快照。** dsh 在每一轮末尾也放这样一张卡（`ChangedFiles.tsx`），但它的数据来自**轮次边界的工作区快照对比**：所以它知道 `+6 -1`，也知道那条用 `bash` 追加了一行的 `notes.txt`。这里用的是同一批消息里的 `write`/`edit` 工具调用（`turn-files.ts`），于是得到的是它的另一半——**归属确切的那一半**：每一次调用都明说了自己写的是哪个文件。代价说清楚：`bash` 改的文件不在卡里（一条 `echo x > a.ts` 没有任何可以归属的路径，猜一个出来就是在把猜测当事实讲）。要连 `bash` 一起覆盖就得有真快照，这一轮没有做。

**`+N -M` 用的是 pi 自己那份 patch。** 一度这里是「不显示行数」，理由是转录里没有权威依据；依据其实一直在工具结果里——`edit` 的 `toolResult.details.patch` 就是 pi 生成的标准 unified diff（`details.diff` 那份带行号的文本是给人看的那一份），`parseUnifiedDiff` 解析它得到的 `additions`/`deletions` 与右侧栏变更面板上的数字出自同一个解析器，于是行尾那个数字与悬停画出来的每一行永远一致。`write` 没有 patch（pi 只回一句 `Successfully wrote N bytes`，`details` 是 `undefined`），那一侧是**由 `content` 合成的一整段新增**：覆盖一个已有文件时只能记 `+N -0`，因为转录从来没读过那份被覆盖的内容，写一个 `-M` 出来就是编的。`content` 缺失（参数被输出上限截断）或超过 200 KB 时不猜，照 dsh 的 `oversized` 显示「过大」。`edit` 的结果不在这一轮里时（从被裁剪的日志读回来的会话），退回 `edits[]` 两侧各自的行数——有数字、没 patch，悬停时浮层只写一句「这次调用没有可显示的改动」（`oversized` 的那一档写「文件过大」）。**一行看起来能悬停、实际什么都不发生，比一句说明更让人以为是自己没停够久**，所以「没有 patch」不再是「不开浮层」的理由。

**版式照 dsh 的 `ChangedFiles.module.css`。** 单文件只画 header，标题就是文件名（再列一行是同义的重复），多文件才带列表，折叠阈值 4 行（dsh 的 `COLLAPSED_ROWS`，原来是 3）；右侧是 `+N -M`，千分位用 dsh 的 `Intl.NumberFormat('en-US')`。**行尾不再有 `编辑 ×3` 那类调用次数**，投影里也不再留那两个字段——没人读的东西不留。**悬停 500 ms 出对比**（dsh `HoverCard` 的 `openDelayMs`），画的是这次调用自己的 patch：同一文件改了三处就是三段 patch，dsh 那边是快照对比出来的**一份合并 diff**——合成的代价是先后两处改动不会互相化简，那需要一份两侧文件都没有的中间态。**浮层 portal 到 `document.body`，坐标是视口坐标**（`preview-position.ts` 那支纯函数照搬 dsh HoverCard 的算法：宽度 = 卡片宽 − 24×2 且不越视口，左边 = 卡片左 + 24 再夹回视口内，先量上下各剩多少空间再决定朝上还是朝下，最多 420px 高，与锚点留 8px 缝）。旧版把浮层留在卡片外面那个 `position: relative` 壳里：绝对定位的包含块因此落在转录的滚动框内，被它的 `overflow-y: auto` 沿着框边剪掉——那条边正是输入框区的上沿，所以看上去就是「被输入框盖住」（实测把同一张浮层按旧写法放回去，它的盒子被算到卡片坐标系里，连自己该在的位置都到不了）。现在两件事一起换掉：`position: fixed` 让盒子脱离那个滚动框，portal 到 body 让它在根层叠上下文里——这一条也是 dsh 的 HoverCard 与本站 Tooltip 走的路，任何祖先将来变成包含块（`transform`、`filter`、containment）都影响不到它。`z-index: 100` 取 dsh HoverCard 的那一层：高于本应用自己画的全部东西（通知 20、侧栏 40、右栏 50、图片遮罩 70），低于两枚等人回答的遮罩（对话框 1000、tooltip 1100）。顶部让出的那条带读 `--dsh-frame-top-clearance`（本应用只在 `html[data-platform="darwin"]` 下给 48px，浏览器里没有这个属性就回落到 8px 视口边距——和 dsh 读到 NaN 的回落是同一个答案）。滚动（捕获）、缩放、以及浮层/卡片/行的尺寸变化都触发重算，第一遍量到的高度是 0 不影响落位：`positioned` 进 effect 依赖，第二遍才写坐标。**进场出场都是 100ms 透明度**（`@starting-style` 与 `data-closing`），指针进到浮层上会取消这次淡出——`usePointerGrace` 那 200ms 宽限本身就是「取消」这件事；Escape 关掉它。

**diff 只有一份版式，三处都用它。** 曾经行样式放在 `ChangesTab.module.css` 里（flex 行、34px 号位、hunk 之间 2px、用状态色代替 diff 自己的三色），后果是悬停出来的那张对比、变更面板、第 N 轮改动看着像三种东西——同一个应用里同一段 patch 有两种观感，比「两处行号可能不一致」更显眼。现在 `FileDiff.module.css`（`ui-deliverables/src/client/FileDiff.module.css` 的移植，与 `DiffHunk.tsx` 一起放在 `rightbar/`）是**唯一一份**：同一套网格 `3.5em 3.5em 1.2em minmax(0, 1fr)`、同样的 22px 行盒与 `--dsw-font-markdown-code-block` 字面、同样的 `--dsw-alias-file-diff-*`（行底、号位槽、标记三色，本次一并补进 `design-platform.css` 的明暗两块）、行号右对齐且不可选中、每行第一枚号位用 3px 内阴影画出侧标记、context 行正文降到 `label-secondary`、正文右侧留 16px；body 用 `minmax(max-content, 100%)` 单列网格，所以长行是**横向滚动**而不是在卡里换行；hunk 之间 8px，路径行 38px（下缘 0.5px `border-l3`，路径本身横向滚动而不是省略号）。行的渲染仍然只有一处（`DiffLines`），它不再收样式表，也不收换行开关：**换行是 body 的属性**（`data-review-wrap`），面板与第 N 轮改动带着它（它们的 patch 随栏滚动，长行必须换行才读得全），浮层不带（它按量出来的宽度摆放，长行横向滚动）。于是「同一段 patch 不会有两种行号」与「三处版式相同」同时成立，差别只剩表面那一层。**超过 5000 行就不再往下画**（dsh 的 `MAX_RENDERED_LINES`，在越界那个 hunk 内部截断），末尾补一句「只显示前 5,000 行」；一份被写出来的生成文件不该因为悬停一下就排上万行。画不出对比时用的也是参考那一档：`oversized`（过大）走 `.status`（16px 内边距、13px、`label-secondary`，`role="status"`），「这次调用没有可显示的改动」走 `.note`（13px `label-tertiary`，带 `data-diff-note="empty"`）。刻意保留的两处不同：hunk header 不画（面板里那行是折起/展开的按钮，浮层没有这个动作），路径写工作区相对形式（`file.display`）而不是 dsh 解析出的绝对路径——浮层只要让人认出是哪个文件，完整路径留在 `title` 里。还有一处**没有**对齐：本应用的 diff 行至今不做语法着色（转录里的代码块有），参考实现的浮层有——那要按 hunk 两侧各做一次高亮，并且变更面板与 review tab 也得一起改，否则同一个应用里会出现两种代码观感，所以留作单独一件事。

**浮层自己是一个指针目标**。离开行或浮层后不是立即关闭，而是留 **200 ms** 宽限（dsh `usePointerGrace` 的同一个数）：指针从行跨过那几像素进到浮层上就取消关闭，于是里面的滚动条、可选中可复制的文字才真的可用——没有这道宽限，`overflow: auto` 写了也永远没人能用上。宽限同样管住另一头：指针已经在往外走时，那半秒的悬停计时一并取消，不会在它离开的那一行上还开一张浮层。

**一行一个文件，按首次出现的顺序**。去重键是**项目内相对路径**，所以 `./a.ts`、`a.ts` 和 `/proj/a.ts` 会折成同一行；行尾是该文件自己的 `+N -M`，表头那一对是整轮求和。项目外的路径（比如写到 `~/.pi/settings.json`）**照样列出但不做成按钮**：右侧栏预览走的是项目内相对路径，给它一个只能失败的可点行，比不给更糟。

**位置在答案与操作行之间**（`MessageList` 的轮次末尾），和 dsh 的 turn tail 一致：卡片属于造成它的那一轮，不属于整个转录。每个轮次的文件在 `useMemo` 里一次性算好（键是已经缓存过的 `railItems`），所以流式增量不会重新扫全量消息。点击走的是变更面板同一个入口 `rightbarActions.openPreviewTab`——面板若收起会自己打开，点了一定看得见。

**卡片等到那一轮结束才出现**（`liveTurn`）。一轮里的每个 assistant 消息在 `message_end` 时就会连同它的 `write`/`edit` 调用落进转录，而这一轮可能还要再跑好几轮工具往返，所以只看「这个轮次有文件吗」的话，卡片会在生成过程中就亮出来——第一次工具往返先亮出一行，之后每写一个文件再长一行，抖动的正好是读者盯着的那块地方。dsh 也是轮次结束才落卡，于是 `isStreaming` 命中的那一轮不画卡（它本来就在等一张会变的表，而不是一份结论），已经结束的轮次照常立刻显示。

**排队里还没轮到的发言不算新一轮。** 「这一轮结束了吗」是靠「哪一轮是最后一轮」回答的，而转录的最后一条用户消息可能是一条 pi 还没去读的 steer / follow-up：输入框在流式期间按一下 Enter 就把它乐观地放进转录（用户必须看得见自己发了什么），但 pi 还没开始它那一轮。`groupTurns` 于是把它留在正在跑的那一轮里，等 `message_start`——pi 把它从队列里取出来的那一刻——才让它开新一轮；不这么分的话，排队的那条消息会凭空多出一轮，正在跑的轮次立刻不再是最后一轮，卡片就在文件还在被写的时候亮出来，而它下面那份列表还要接着长几行。判断「pi 收到了没有」用的是计数而不是比对文本：pi 在排队前就会展开 skill 命令，回显并不等于用户敲进去的那句话。`useConversation` 因此只数两个东西——转录里有几条用户消息、pi 已经取走几条（`deliveredUsersRef`）——差值就是 `undeliveredPrompts`。prompt 一发出就算取走（pi 只会把它当 prompt 跑，这样新的一轮开始时上一轮的卡片不会闪一下再回来），steer / follow-up 则要等到 `message_start`；从磁盘读回来的转录里每一条都是取走过的，所以 `load()` 直接把它设成文件里的用户消息数。

**路径做了一次缩短**：摘要若是工作区内的绝对路径就先转相对，再对 home 下的路径显示成 `~/…`（`shortenPath`，照 dsh 的 `relativizeToCwd` + `abbreviateHomePath`）。两者都只在整个字符串以根开头时才生效，所以 `cd /long/path && …` 这样的命令不会被改写。本机 5716 次文件类调用里 95% 是 home 下的绝对路径。

### 右侧栏的「本轮改动」面板

**它读的不是工作区，而是转录。** dsh 的 review tab（`ReviewTab.tsx`）按 sessionId 与事件序号向 Host 要一份 summary 和一份 comparison——那能成立，是因为 dsh 在轮次边界留了工作区快照。这里没有快照，一轮的改动只存在于转录里，而转录在对话面板手上、右侧栏够不着。于是多了一条通路：`MessageList` 算出每一轮的文件后，由 `ConversationPane` 发布进 `turn-changes-store`（一个独立的小 store，不是 `appStore`——后者被外壳整棵订阅，写它会让整页重渲染，而这份数据每结束一轮就要写一次），面板按 `sessionPath + turn` 读回来。等价的重算不写：投影是从消息列表重算出来的，流式期间每次往返都会得到一份内容相同的新数组，不比较就会把每个打开着的 review tab 都叫醒一次（`turn-changes-store` 里那份逐文件比较就是为此）。

**地址是 `<turn>#<index>`。** turn 是这个 tab 的身份——dsh 用的是「宣布 summary 的那个事件序号」，这里没有那么一个东西，卡片自己标的轮次号就是同一个键；index 是当前选中的文件，跟着地址走，所以从表头（index 0）和从某一行（该行下标）进同一轮，落到的是同一个 tab、只是把它的选择移过去（dsh 的 `navigation.params.index` 同样是每次导航应用一次）。保存的布局里一个解析不出来的地址会被丢掉（`readTab`）：那指向一个这个版本画不出来的轮次，dsh 的 `canOpen` 也拒绝这样的资源。

**面板本身是 dsh 的骨架**：38px 的头、左边文件选择器（列表带 `+N -M`）、右边「在右侧栏打开整个文件」，下面是带双行号的统一 diff。**两处有意不同**：没有左右对比视图（这个项目的变更面板也没有，`known-limitations` 里记着），也没有换行开关——变更面板的 patch 本来就随面板滚动、长行必须换行才读得全，一个永远开着的开关比不给更糟。diff 行来自 `DiffHunk.tsx`，与变更面板共用同一份解析（`diff-parse.ts`）和同一套行样式（卡片那张的悬停预览画的也是这批行），所以三处不可能对同一段 patch 给出不同的行号或不同的增删数。

**卡片不再直接开文件预览**：表头与每一行都打开这个面板并定位到那个文件——这是 dsh 的行为（`openReview(index)`）。项目外的文件现在也能点了：它的 patch 和别的文件一样在转录里，只有「打开整个文件」那枚按钮需要项目内相对路径（没有就不画）。

**一处健忘是设计而不是缺陷**：这份投影只活在当前页面。刷新后右栏的布局会从存储里回来，但数据要等对话面板把会话重新载入并再次发布；会话没打开（或那一轮的转录已不在）时，面板说的是「这轮改动的内容已不可用」——dsh 的 `changes.missing` 是同一种回答，只是它那边是 Host 不再持有那份快照。

**目录选择器**：`/api/fs/list` 只返回子目录（符号链接指向目录时也会返回），以 `.` 开头的目录排在最后而不是隐藏（`~/.config` 这类目标依然可选）；路径经 `fs.realpath` 规范化，因此软链会被解析到真实位置。

### 桌面端的通知与红点

**通知和红点是同一件事的两半，都归主进程。** 浏览器版的完成通知就是一次 Web Notification（`notifications.ts` 一个模块包着，别处不碰 `Notification` API），桌面版复用同一份前端产物，但 `new Notification()` 在那里的点击只在页面里生效——窗口被最小化、或者已经被关掉（macOS 关窗不退出）时，用户点那条通知什么也不会发生。所以桌面版把这件事交给主进程：`notify` 弹通知、`setBadge` 写红点、`onNotificationClick` 把点击送回页面。页面的分派点只有一个（`showNotification` 里看桥在不在），浏览器那条路径一个字没改。

**preload 从此不再是纯数据的。** 这条桥原本的自我约束是「只传数据，外加一个 `getPathForFile` 字符串查询，绝不出现 channel」，因为页面根本不需要 `ipcRenderer`。通知打破的是最后半句：通知的宿主是操作系统，只有主进程能弹、能设 Dock 徽标、能在用户点它的时候把窗口拉回来——渲染进程就算能自己弹一条，也没有「把窗口还原」这个动作可调。于是桥多了三个函数，`ipcRenderer` 仍然留在 preload 里，页面拿到的还是几个函数而不是一个 renderer 句柄。参数在 preload 侧先做一遍类型检查再转发：它跨的是一次隔离世界的拷贝，主进程不该替页面兜住一个畸形对象。

**红点数是算出来的，不是记出来的。** 它等于 `sessionActivity` 里 `done` 的条数，订阅里按引用变化重算，`setNotificationBadge` 再去掉没变的数字——否则 store 的每一次写入都会变成一次 IPC。这跟「已完成但还没打开」这个语义天然对齐：打开会话（`selectSession`）会清掉 `done`，删除会话、进程退出同样会清，所以红点不需要另一套账本，也就不可能和侧栏的状态点对不上。

**Windows 只能画。** `app.setBadgeCount` 覆盖 macOS 与 Linux（Dock / Unity 启动器），Windows 走的是 `BrowserWindow.setOverlayIcon`，要的是一张位图。与其随包带几张预生成的图（还要管尺寸、深色任务栏下的对比度），不如按需画：`badge-overlay.cts` 用一个 5×7 点阵把数字拼出来，`nativeImage.createFromBitmap` 直接吃裸 BGRA，既没有图片编码器也没有资源文件；两个字符在这个尺寸下放不下，所以超过 9 就显示「9+」——那也正是红点这个记号的语义上限。这个模块单独成文件的原因很实际：`win32` 分支在开发机（macOS）上永远跑不到，抽出来才能用一段 Electron 脚本把几个数字渲染成 PNG 看一眼。

**窗口生命周期补了一处。** 关掉窗口后 `window` 变量原来一直指着那个已销毁的 `BrowserWindow`（macOS 关窗不退出，所以这不是死代码），于是 `activate` 里的 `window === null` 永远不成立、点 Dock 图标不会重建窗口。现在统一走 `mainWindow()`：已销毁就当没有，没有就重建，并记下 `closed` 事件。通知点击用的是同一个入口——用户关掉窗口之后点通知，窗口会重新出现并带上那个会话。

**签名是 macOS 通知的隐藏前提。** Electron 42 起 macOS 的通知走 `UNNotification`，而它拒绝只有链接器签名的二进制——`node_modules` 里那份 `Electron.app` 正是这一种。失败还是静默的：`isSupported()` 返回 `true`，`show()` 只是不投递，只有在事件里挂一个 `failed` 监听器才看得见，所以第一版实现「跑起来一切正常、通知就是不出现」。开发脚本因此会先做一次 ad-hoc 重签（`sign-dev-electron.mjs`），打包时 `afterPack` 对成品做同一件事（`mac.identity: null` 是「不找证书」，不是「不签名」），主进程也把 `failed` 写进 stderr。代价是 ad-hoc 的指纹每次构建都变，升级后系统会把通知授权当成一个新应用再问一次；要消掉这一点得有真的开发者证书，那是另一件事。

### 计划模式为什么落在日志上

`/plan` 不是一个新的界面状态，而是**会话日志里的一条 entry**（`pi-web-simple:plan-mode`，载荷 `{ active }`，整体替换），`extensions/plan-mode.ts` 每次读都从当前分支折叠最新的一条。这是 dsh 的 `plan/mode`（log-only、whole-value replace）用 pi 的 `pi.appendEntry()` 复现：resume、fork、compaction 之后状态自然是对的，不需要任何内存镜像，也不需要谁去同步它。服务端读的是同一个文件（`server/src/session-plan.ts`，走 `session-open.ts` 已有的解析缓存），随 composer 读一起把 `planMode` 返回给前端，头部那枚徽章因此说的是文件里的事实，不是点击的预测。

**指引只加一段、不换工具。** `before_agent_start` 往 `systemPromptOptions.sections` 里放一段 `plan-mode`：进入和离开都只改这一段文本，工具清单一个字不动——dsh 让 `exit_plan_mode` 常驻注册是同一条道理，工具表一变，provider 的缓存前缀就作废。它的限制因此是**软的**：全部写在提示词里，不拦任何工具；要真正限制，配 sandbox 与审批策略（这也是 dsh 的立场）。选 `sections` 而不是 `promptGuidelines`，是因为 pi 把 section 当作可独立替换的片段记进转录，这一段的状态变化在会话里看得见。

**"下一次请求生效"是 pi 的形状，不是偷懒。** pi 的 system prompt 在一个 turn 组装时就固定了，而扩展命令不在 turn 里（pi 直接消费掉，不产生用户消息），所以 bare `/plan` 只记状态、等下一条消息；`/plan <message>` 用 `pi.sendUserMessage()` 把那条消息立刻发出去，它触发的那一轮就带着指引。`exit_plan_mode` 的批准同样只是往日志里写一条：当前这一批工具调用仍按 plan 模式跑完（它们的 prompt 早就组装好了），下一批自然读到关闭——这正是 dsh 的 silent pending exit，只是这里不需要一个 pre-step 去落地它。

**审批复用问答那条通道，窗口按 dsh 重排。** `exit_plan_mode` 通过 `ctx.executeTool("ask_user_question", …)` 提一个带 `intent: { kind: "plan-review" }` 的单题批次，于是计划落在 Web 自己的审批卡上（`PlanReviewPanel`），没有第二条审批 UI——但它**整卡接管**而不是往问答卡里塞一块：`QuestionComposer` 命中 `plan-review` intent 时直接返回它（dsh 那边是同一个分叉：`review === undefined ? QuestionFlow : PlanReviewPanel`），把卡头、页码「第 x/y 题」、Skip 与提交都留在门外，标题与摘要也从计划本身取（首行作标题、首段作摘要，`plan-review-text.ts`），不再把 `header` 里的问句重复成正文。intent 里多带的一个 `callId`（`exec.callId`，dsh 的 `PlanReview.callId`）不是装饰：它是"这份计划由哪个调用提交"，审批卡、轮次尾部的计划卡片、右栏的标签页都靠它认出同一份文档，所以评审关掉之后还能读回来，刷新之后也能从转录重放出来。它刻意不带 `timeout`（dsh 的评审没有截止时间，而一张读到一半就过期的卡会把"我还在看"变成"没人回答"）。批准回 `{ approved: true }` 并写一条 inactive，退回把用户的反馈放进错误结果，模型据此重写；plan 模式外调用这个工具直接失败。**卡片本身不再展开计划正文**：上一版把它折在卡里，是因为当时没有别的地方读它；现在"查看全文"在卡片顶部警示条右侧（dsh 的 `reviewLink`），正文进右栏的 `plan` 标签页（文档排版用 `Markdown` 新增的 `document` 变体，即 dsh `MarkdownText` 的间距，而不是转录那套紧凑的）——标签页按 `callId` 寻址，内容从转录投影发布（`plan-store.ts` 与 `turn-changes-store.ts` 是同一套桥），所以会话一打开、刷新之后它自己就活了；评审一到还会**自动打开一次**（dsh 的 `PlanReviewOpen`），手动关掉不会被再次打开。没有 `callId` 的评审（别的扩展直接提问）把文档留在内存里，刷新后显示 dsh 那句"临时计划预览已失效"——它没有可重放的调用，这是唯一诚实的说法。

**计划状态的权威来源有三层，因为 pi 的落盘是懒的。** 进程（`get_entries`）是权威：`/plan` 写的是 pi 的内存，而会话文件要到第一条真实消息才存在，所以切换端点与只读端点都从进程折叠（`server/src/session-plan.ts` 里的同一套折叠，文件只作兜底——进程在命令与读之间死掉时才用）。文件是第二层：会话一旦说过话，磁盘就是持久的答案，`sessionOnDisk` 让前端能区分"模式是关的"和"还没有东西可读"。本地值是第三层，只用于"刚按下、还没人到场确认"的那一小段：dsh 的 chip 读 host 折叠的 pending 选择（`pending ? !active : active`），也是在显示一个尚未落到日志的意向；这里没有 host 投影，于是由浏览器记着，直到进程或文件给出答案。由此还带出两处细节：新会话页那条输入框里的 `/plan` 走的也是扩展命令那条路（`planCommandOf` 认文本，排队时带上 `command` 标记），否则它会被画成一条 pi 从未写过的用户气泡；以及开关本身不发通知——chip 出现或消失就是反馈，而通知在本项目里不会自动消失，一条 "Plan mode on" 会一直压在 chip 上。

**模式 chip 的位置和显示条件也是 dsh 的规则。** dsh 的 `PlanChip` 长在输入区的控制行里，**只在模式开启时才渲染**（`pending ? !active : active`），职责只有一件：点它执行 `/plan off`。所以这里也把徽章从会话头部搬进 `Composer` 的控制行（`PlanChip`，附件按钮旁），并且只在 `planMode` 为真时才画——进入靠 `/plan`，`/` 菜单里就列着它，与 dsh 一样。悬停/聚焦时图标从计划文档换成划掉的圆，是"按下就是关掉"这件事的说明；退出失败在 chip 旁说一句，而不是弹一条通知。**转录侧多了 dsh 的两种呈现**：一轮结束后的计划卡片（`PlanCard`，照 `PlanCards` 的形状：图标块 + 标题 + "计划 · Markdown" + 打开），与被退回的计划一起保留——卡片记录的是"提交过一份计划"，不是"批准过"；以及侧栏会话行的第三种状态：有待审批的计划时状态点变 warning、无障碍文案是「计划待审批」，时间戳的位置换成「计划审批」（dsh 的 `Plan awaiting review` / `Plan review`）。判定用服务端那张待答表（`pendingUiRequests`）而不是转录，因为"谁被打断了"是服务端唯一确知的事（见 `question-model.ts`）。

**扩展命令不再画用户气泡。** pi 对扩展命令只记录命令自己写下的消息（`/plan <message>` 记的是那条需求，bare `/plan` 什么都不记），而输入框原来把用户敲的那一行原样乐观插进转录——两行对不上；`/todos` 这类不提交消息的命令更糟，留下一行永远等不到对应记录的幽灵气泡，只有刷新才能消掉。现在 `extensionCommandName()` 认出这一类文本，改走 `runCommand()`：不画乐观行，等 pi 在流里记下它自己那条再采纳。普通消息照旧乐观插入，技能与模板命令也照旧——它们本来就是 pi 展开后按普通消息记录的。

### 预览里的「打开方式」与「显示文件位置」

**一个文件一次查询，两个地方画它。** 预览头最右边（自动刷新与重新载入之后）是本机打开的分体按钮：主按钮「用 X 打开」，箭头列出这台机器上注册为这个文件类型的应用，最后一行固定是「显示文件位置」。同一个文件的「不能预览」空态画的是同一个控件的放大形态（36px、带「打开」两个字）。两处共用一次 `useOpenWith(projectId, path)`——同一个文件只有一份答案，问两遍既慢又可能给出两个不一样的列表；dsh 把「同一个文件 + 同一个查询函数」做成一份共享状态也是这个原因。查询失败时控件照画：主按钮退回「用默认应用打开」的措辞，菜单里多一行禁用的「无法获取应用列表」——一个问不到的列表不该让「打开」本身消失。

**应用列表是主机的答案，不是前端编的。** `GET /api/projects/:id/file/applications?path=` 回 `{ desktop, applications }`：`desktop: false` 表示这台主机没有可用的桌面（SSH，或 Linux 没有 `DISPLAY`/`WAYLAND_DISPLAY`），前端据此**什么也不画**——这正是 dsh 的 `canOpenWorkspacePath` 语义。列表在 macOS 上由一段 JXA 脚本（`osascript -l JavaScript`，`NSWorkspace` 的 `URLsForApplicationsToOpenURL`）枚举，带 `default` 标记与 32px PNG 图标（`data:image/png;base64,…`）；同名同 bundle 的副本（自更新留下的 staging、多版本安装）合并成系统默认那一个，否则留版本最高的——dsh 用同一套规则。应用目录只查 `/Applications` 与 `~/Applications`（和 dsh 一样不去问 Launch Services 的全量注册表），所以装在别处的 app 不会出现在菜单里，新装的要刷新页面。

**路径先过项目这道闸。** 前端只会发它已经拿到的工作区相对路径；服务端用读文件那条同一道检查解析它（`resolveWorkspaceFile` → `resolveInsideProject` 的 realpath + 前缀判定），所以 `path=../../../etc/passwd` 在任何系统调用之前就被 403 挡掉（实测过）。`action` 是个闭集（`open` | `reveal`），`application` 只对 `open` 有效，`reveal` 带上它会被拒绝——路由转发的是一个已经验证过的意图，不是一条命令。

**动作是尽力而为，拒绝也是一句话。** `open` 走文件的默认应用，`.html`/`.svg` 会先试着交给默认浏览器（macOS 读 LaunchServices 里 `https` 那个 handler）；`reveal` 是 `open -R` / `explorer.exe /select,` / `xdg-open` 父目录；explorer 的退出码 1 算「已交给桌面进程」，不是失败。主机拒绝（`{"ok":false,"error":"…"}`）与超时都不变成 HTTP 错误，而是头部下面那一行字——「没有可用的桌面」是一个答案，不是一次故障。这一行自带「关闭」，因为本项目没有 toast 层，而一句会自己消失的话不适合表达「桌面拒绝了」。

**和 dsh 有意不同的一处：主按钮永远是「打开」。** dsh 在没有任何关联应用时把主按钮变成「显示文件位置」并去掉箭头，因为它的主机在三个平台上都答得出关联查询。这里只有 macOS 能（见[已知限制](./known-limitations.md)），照搬会让 Windows/Linux 的默认打开方式彻底没有入口；所以菜单最后一行固定是「显示文件位置」，主按钮固定是「打开」（没有列表时用「用默认应用打开」的措辞）。其余几何与文案都对齐 dsh：24px 分体按钮、0.5px 边框、11px 字、菜单行 28px 高、应用图标 14px、默认应用标「（默认）」、最后一行前一条分隔线；列表还在读的时候按钮显示 13px 的灰块并禁用，指针与键盘手势共用同一个 in-flight 锁，所以连点不会打开两次。

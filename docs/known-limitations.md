# 已知限制

这份清单记录 pi-web-simple 目前**做不到**什么，以及那些行为背后的取舍。装之前值得先扫一遍。

- 只在浏览器本地单机单人使用，没有账号体系；兜底的 Host/Origin 校验只挡浏览器发起的跨源请求，**不要把它暴露到公网**。
- 目录选择器浏览的是**服务端所在机器**的文件系统（本工具里就是本机）。
- **拖文件夹进输入框只在桌面版可用**：浏览器不会告诉页面一个被拖入的文件夹在哪里（与目录选择器同一道墙），所以网页版会抬一条提示而不是静默无视；桌面版通过 preload 的 `getPathForFile`（`webUtils`）拿到绝对路径，引用**只显示目录名**（`alpha/`）、发送的是完整路径（相对当前工作区，工作区外则绝对），并是**静止态的 chip**：能看、能当普通文字编辑，但不能悬停或点开；手改过的引用不再展开，按用户看到的样子发出去；草稿里的引用自带一个不可见的**图标槽**（一个 em 空格）用来画文件夹图标，**复制草稿时它会一起被复制**（发送前会被清掉，不进消息）。理由见[设计说明](./design-notes.md)。
- **工作区的分组与排序可以在侧栏里改，但有两条界限**：侧栏分组头右侧那枚滑块按钮给出 dsh 的三种分组（按工作区 / 按工作区树 / 单列表）和两种排序（手动排序 / 最近更新），选择缓存在浏览器本地。① **手动排序只作用于已经加载进侧栏的那些行**：每个工作区默认只持有一页（5 条）会话，没展开的既不在拖拽范围里、也不在保存的顺序里，它们按「最近更新」接在已排列的行之后（展开「其余 N 个会话」后可以继续拖）；「单列表」没有工作区行、也就没有「展开更多」，所以选它会先把每个工作区的整份列表拉下来。② **工作区只能和同级换位**：树模式下 `/a` 不能拖进 `/b` 的子树（那改的是路径模型而不是顺序，所以直接拒绝，跨父级的落点连插入线都不画）。还有一点与 dsh 不同：这里的**分组默认是「按工作区树」**（dsh 默认平铺），理由见[设计说明](./design-notes.md)。工作区的顺序存在服务端（`PUT /api/projects/order`），会话的手动顺序只存在这个浏览器。
- **PDF 预览用的是浏览器自己的查看器**，所以缩放、翻页、打印都由那个查看器提供，界面里没有一套自己的控件，样式也不跟应用主题走。这是刻意的：手写一个 PDF 渲染器要拖进几百 kB（dsh 走的就是自带渲染器那条路）。文件超过 64 MB 直接拒绝。
- **HTML 预览永远不跑脚本，也没有打开它的开关**：框是 `sandbox=""` 加一条写在文档里的 CSP，脚本、表单、跳转全关，图片/字体/媒体只认 `data:`。所以一份引用同目录图片或外部样式的页面会缺那部分——预览的是这一份文件的静态样子，不是一个能用的网页（要看能跑的页面用「浏览器」标签页，那里默认是开的沙箱）。dsh 在开启开发者工具时会把本地资源内联进去让页面真的跑，这里没有那条路。
- **超长文本要手动翻页**：一页 2000 行 / 256 KB，底部一个「读取更多」，**没有「一次读完」也没有跳到指定行**。不自动加载是故意的——一个几百 MB 的日志不该因为滚到底就把浏览器吃掉。翻页的正文是纯文本，不带语法高亮。
- **预览的自动刷新只认工作区里、且不在 `node_modules` 下的文件**：它跟着工作树监听走，而那个监听把依赖目录的抖动静音了（见[设计说明](./design-notes.md)），所以打开依赖里的文件时不会自动跟随，只能手点「重新载入」。这个开关本身也是内存态：切走这个标签页再回来，它恢复为开启。
- 右侧栏有**文件树、预览、变更面板、本轮改动、终端与内嵌浏览器**（轮次导轨是浮在对话流旁的一条窄轨，不算第三栏）。停靠区**最多分成左右两格**：按 `⌘\` 分当前格，或者把标签拖到某一格的两侧边缘；**没有上下分屏，也没有第三格**——dsh 那套布局树能递归，这里是一份扁平数组，理由见[设计说明](./design-notes.md)。两格都还放得下 150px 时才允许分，放不下时「分栏」按钮置灰并写明原因。**被拖空的窗格会自己合并掉**，所以不存在空着的停靠窗格，也不会为了占位补种一个「文件」页。
- **标签可以拖出成浮动面板**：拖到标签条和窗格之外松手，标签就变成一个浮窗，可以拖动、从右下角缩放、按头部那枚按钮停靠回栏内；位置随会话保存，刷新后还在原处。浮窗**只装一个标签页**（它没有标签条，也就没有东西可切），**把它拖回窗格并不会停靠**——只有那枚按钮能收回去。
- **终端标签页需要一个可选的 `node-pty`**：它是原生模块，按平台分发预编译二进制（Linux 没有，要本机编译）。装不上时「+」菜单里的「终端」与空面板的引导卡都置灰，鼠标悬停写明原因，其余功能不受影响；`pnpm-lock.yaml` 里已声明为 `optionalDependencies`。
- **终端一次最多 8 个**（`MAX_TERMINALS`），启动失败与已退出的也算，到上限后新建返回 409 并提示先关一个。**关掉标签页会立刻从界面消失，同时在后台杀掉那个 shell**：杀失败不会把标签变回来，而是在面板底部留一条可重试的提示。只有折叠右栏、切会话、刷新这种「卸载」才只断开、不杀进程，所以后台跑着的构建不会被收起侧栏掐断；页面关闭时会尽力 detach。没有附件的 shell 空闲 2 小时后由服务端回收，附件 90 秒没有心跳会被判定为已离开并让出输入权。
- **同一时刻只有一个窗口能输入一个终端**：最后 attach 的那个附件拥有键盘与 resize，其他窗口看到只读屏幕和一枚「接管」按钮。屏幕由服务端用 headless xterm 维护，刷新或重连拿到的是同一进程的快照加单调序号，不是回放字符流，所以不会花屏；序号断档时标签会自己重新拉一次快照。服务端重启后，标签记住的 id 已经不存在，会明说「进程已经不在了」并给一个「新建终端」，不会偷偷拿新 shell 顶替。
- **shell 可选，默认跟主机走**：空面板的引导卡与「+ → 终端」会列出 `/etc/shells` 和本机常见 shell（zsh / bash / fish / pwsh …），默认是登录 shell（`$SHELL`，macOS 上通常是 zsh），Windows 落在 `ComSpec`。列表由主机给，装不上 `node-pty` 时整块入口置灰。**已经开着的 shell 不能换成另一个程序** —— 那是重启一个进程；退出后点「新建终端」会先释放旧的再开一个。标签名由服务端拥有（`TerminalInfo.title`，默认是实际启动的程序名），**双击标签就地改名**，右键菜单里也有同一项；名字随终端一起消失，布局只保存指向它的 id。
- **终端只给人用，没有给 agent 的工具**：dsh 的 `terminal_open` / `terminal_send` / `terminal_read` / `terminal_signal` / `terminal_close` / `terminal_list` 六个模型工具没有接；agent 仍然走 `bash` 工具，两者不共享会话。
- **快捷键是固定的，改不了也查不到全表**：绑定写在代码里（`features/rightbar/shortcuts.ts`），没有重绑定界面，设置页里也没有一页列出全部快捷键——想查只能看按钮的悬停提示，或者这份文档。目前只覆盖右栏那六个动作（收起/展开、全屏、打开文件、新开终端、新开浏览器、分栏）；dsh 那边还有「关闭标签页 / 刷新会话」这类命令，这里没接——**关标签没有键**，只有标签的右键菜单和标签上的 ✕。浏览器里 `⌘P` / `⌘T` / `⌘⇧B` 换成了 `⌥⌘P` / `⌥⌘T` / `⌥⌘B`，因为前三个已经归浏览器；`⌘\`（分栏）两边一样，因为没有浏览器占着它。
- 变更面板**自动跟随工作区文件变化**（服务端递归监听工作树，`node_modules` 除外），不再需要手动刷新；但**不做提交详情、任意两个 revision 的对比、建分支/合并/rebase，也没有并排（side-by-side）diff 视图**。右侧栏的「本轮改动」面板同样是统一视图。
- **「本轮改动」面板的数据只活在当前页面**：它读的是转录投影（`turn-changes-store`），不是工作区快照——dsh 的同一面板靠轮次边界的工作区快照做后端，这里没有快照，所以刷新后要等会话重新载入、面板才会再次有内容；会话没打开、或那一轮的转录已不在时，面板写「这轮改动的内容已不可用」。它也没有换行开关：patch 本来就随面板滚动、长行必须换行才读得全。
- **`write`/`edit` 的工具卡画的是「打算改什么」的 diff，不是「改成了什么」**：diff 从调用参数本地推导（`edit` 用 `oldText`/`newText`，`write` 是整段新内容），不读 pi 回包里的 patch——那是给改动文件卡片算行数用的另一条路。参数还没到齐的调用不画 diff，回落成通用卡；调用失败也不画。两者的差别只在编辑结果与参数不一致的罕见场合（文件在工具执行间隙被改过），这时卡上画的与磁盘上的会差一口气。
- **每轮末尾的改动文件卡片只认 `write`/`edit`**：`bash` 改的文件不在卡里（它没有可以归属的路径，见 [每轮末尾的改动文件卡片](./design-notes.md#每轮末尾的改动文件卡片)）。行数取自 pi 自己的 patch：`edit` 用 `details.patch` 解析出来的真 diff，`write` 用 `content` 合成的一整段新增——**覆盖已有文件时只算新增**，因为转录里没有那份被覆盖的内容；`content` 缺失或超过 200 KB 时显示「过大」而不是猜一个数字。dsh 的同一张卡靠轮次边界的工作区快照，因此还能报出 `bash` 改过的文件。
- **任务清单面板只显示最近完成的 3 条**完成项（其余折成 `+N 项已完成`），展开后的高度上限是 180px——长清单要靠滚动。转录里那次调用的展开体显示完整快照（不裁），但也有 260px 的滚动上限。
- **计划模式靠提示词，不拦工具；chip 只在它开启时出现，计划正文也不在卡里展开**：进入 plan 模式只是往系统提示里多加一段指引（只加这一段，不动工具清单，见[设计说明](./design-notes.md)），所以模型照样有 `edit`/`write`/`bash` 可用——要真正拦住得另配 sandbox 与审批策略，这是 dsh 的立场。**进入只有 `/plan` 一条路**（`/` 菜单里列着它），而输入框里那枚 chip 是"出去"的按钮，因此它只在模式开启时才画（dsh 的规则）；退出失败在 chip 旁说一句。审批卡上「查看全文」打开的是右栏的计划标签页，而标签页要能寻址才能读：会话还没落盘（第一条真实消息之前）时卡片仍在、两个裁决仍可点，只是没有那条链接。开关是会话日志里的一条 entry，而 pi 在第一条真实消息之前不创建会话文件：这种时候状态只在进程里，界面上那枚 chip 因此先由本地值顶着，等能问到权威答案（进程）再落定——所以刚开完模式时 chip 可能比磁盘早一步，不会因"文件里还没有"而闪掉。bare `/plan` 也不会自己发出一条请求：指引从你的下一条消息开始生效，而 `/plan <消息>` 用那条消息立刻开始一轮。极简组成里没有计划模式（它和问答、任务清单都走同一个 `--extension` 名单）。
- **fork 创建的是新会话**，不是把当前会话截断；原会话一个 entry 都不会丢（已实测）。分叉后会自动切到新会话。
- 助手消息下的「赞/踩」**没有做**：pi 没有对应字段，也没有 RPC，做了也写不进任何会被读的地方。
- **失败后只能「把这条 prompt 再发一次」，没有真正的重试**：pi 的重试循环只在 turn 内部跑，RPC 里没有 continue/retry，而 `abort` 又会连自动重试一起停掉。失败行右边那枚按钮发的是同一条 prompt（含原图），所以转录里会多出第二份用户气泡。另外**从磁盘读出来的失败行不带重试次数**（session 文件里没有这个数字），刷新之后那行就只写「模型请求失败」。
- 「用时」是墙上时间（含工具执行），不是模型生成时间——pi 没有暴露后者。
- **压缩前的轮次只在这一屏里看得见**：一次 compaction 之后，pi 的上下文不再包含切点之前的轮次。看着压缩发生的那一屏上，它们还在（上面那条「上下文已压缩」把它们与之后的部分分开）；但**刷新、切走再回来，转录就是 pi 重放的那份**——只剩摘要与切点之后的那一段，折叠掉的轮次读不到了（它们仍在会话文件里，pi 从文件重建时同样只读切点之后的部分）。那一行也**不报折了多少条、压缩后剩下多少**：前者只有 session entry 里有（`compactionSummary` 消息只带摘要、`tokensBefore` 与时间），后者（`estimatedTokensAfter`）pi 只在压缩那一刻算过、没落盘——服务端在 `/compact` 的回包里给过一次，但这个界面不再显示它（同一件事该只在一个地方说，那条 toast 已经去掉）。
- **新会话页可以选模型，但没有上下文环**：hero 上的 picker 选的是「这个即将创建的会话第一轮用哪个模型」，随首条消息交给 `POST /api/sessions`（服务端用 pi 的 `set_model` 应用它）；上下文环要的是会话的用量，没有会话就没有可显示的东西，所以 hero 上不画。
- **上下文环的数字依赖 `models.json` 里写了 `contextWindow`**：pi 内置 provider 的默认窗口不在依赖树里拿不到，所以没写这个字段的模型只显示空环加一个「未知」读数（面板也写「未知」），而不是去猜一个窗口。要补上它，模型目录里那一行点开「模型选项」就能填——包括 `256K` 这种写法。
- **上下文环在每轮结束后刷新**，不在流式过程中逐 token 更新——这个数字本来就只在模型回复完成后才有（它来自最后一条回复的 usage）。因此环不会因为一次超长回复而提前预警。
- **模型切换会启动会话进程**（如果它还没驻留）：切模型是 pi 的会话级状态，没有进程就没有对象可切。实测一次 1.7s。
- **思考强度的可选档位偶尔要等一次 live 读取**：档位由模型的 `reasoning`/`thinkingLevelMap` 推出，`models.json` 里描述过的模型磁盘上就能答；只有 `models.json` 不认识的模型（pi 内置 provider 的模型）才需要在打开卡片时付一次冷启动——与模型列表同一道限制。切换本身也需要进程（与会话级状态同一条）。
- **`@` 补全搜不到被 `.gitignore` 忽略的文件**：索引就是 `git ls-files --cached --others --exclude-standard`，和 agent 自己用的那套过滤一致（`.env`、`dist/`、`node_modules/` 都不在菜单里）。要引用它们，在输入框里手打路径即可——手打的 `@路径` 原样进句子（不 chip 化，也不展开）。
- **`@` 补全在非 git 工作区只看到前两万条、八层深**：没有 git 时索引退化成一次有上限的遍历（跳过 `node_modules` / `dist` 这类目录），超出上限的部分不会出现在菜单里，菜单也不会说少了什么。
- **自动命名只认两种线上协议**（`openai-completions` 与 `anthropic-messages`）。其它协议（`google-generative-ai`、`amazon-bedrock`、`openai-responses` …）会在调用时直接拒绝——按另一种 API 拼一份请求只会换来一条看不懂的 provider 报错，而这个调用没有地方能把那条报错讲清楚。要自动命名，就先挑一个 OpenAI 兼容或 Anthropic 的端点。
- 设置页有「通用设置」「模型」「插件」和「MCP」四节；Agent 预设还没有。
- **MCP 用的是 pi 自己内置的支持**：配置就是 pi 读的那两份 `mcp.json`（用户级 `<agentDir>/mcp.json`，工作区级 `<工作区>/.pi/mcp.json`），不需要任何扩展。格式是严格 JSON（pi 的读取器同样不接受注释），写坏或写错条目的文件不会静默消失——那一节会把跳过的条目列出来。
- **MCP 的「停用」是工作区级别的**，与 pi 自己的 `/mcp` 一致：没有用户级开关，没选工作区时那个按钮是禁用的。启用/停用写 `<工作区>/.pi/mcp.json` 里那条只含 `enabled` 的覆盖项。
- **MCP 的「删除」写的是定义它的那个文件**。如果同名条目在另一层还有定义（典型的是一个只用来停用的覆盖项），删掉上层之后那个定义会重新生效，删除对话框里会先说明这一点。
- **MCP 的「检查」会真的启动配置里那个命令**（stdio）或请求那个地址（http），超时 15 秒；HTTP 只做 `initialize`，不报工具数。pi 内置支持只认 stdio 和 streamable HTTP，旧版 SSE 与 rmcp-mux socket 这类扩展传输不在其中。
- 模型一节不列举未配置的内置 provider（pi 需要显式的模型列表，列出来也没有可填的东西），但可以**向提供方询问它有哪些模型**。这需要 provider 有一个 API 地址：内置 provider 的默认地址不归我们管，新建的 known provider 又还没保存，所以这两种情况下要先填上地址。dsh 的限制完全一样（`fetchNeedsBaseUrl: "请先填写 API 地址，再获取。"`）。
- 模型写入只对真实 pi 做过**读**的验证；写入用临时栈验证过（包括中途发现并修掉的字段丢失），但用户全局 `~/.pi/agent/*.json` 的写入每次都会先备份再原子替换。
- 模型状态点只反映两个配置文件，**环境变量提供的密钥看不到**（`@earendil-works/pi-ai` 不在依赖树里，拿不到它的 `findEnvKeys`）。措辞已经收敛成「配置文件里没有 API 密钥」，不会断言成「未配置」使环境变量用户去做多余操作。
- 没有「权限」和「语言」两项：前者在 pi 侧没有对应概念（`trust` 管的是项目动态配置的信任，不是工具执行级别），后者在单语言项目里只有一个选项。
- 设置页的下拉用原生 `<select>`：外壳是自绘的，展开的菜单是系统的。换取的是键盘、读屏、首字跳转全部由平台提供，不必重新发明一遍。
- 代码高亮和 dsh 一样是按行续接的增量路径（见[设计说明](./design-notes.md)中关于代码高亮的段落），但**第一次**渲染一个栅栏仍要走一次全量 tokenize，所以超过 2 万字符的栅栏在没有任何可续接前缀时（刚加载完的历史消息、缓存被挤掉的块）直接显示为纯文本；流式增长的长块不受这个上限影响。单行超过 2 000 字符的一律不着色——那是压缩产物或数据倾倒，而且 JS 正则引擎在这种行上会真的卡死，不是慢一点的问题。
- **图片以 base64 进会话文件**：`data` 不落盘到别处，所以一张 5MB 的截图会把那条消息撑大 6.7MB 左右，而这个会话之后的每次磁盘读取都要带上它（`buildSessionContext()` 不裁剪内容块，只按 compaction 走树）。磁盘上仍然如此，但**读给前端时工具结果的图会换成 URL**（见[设计说明](./design-notes.md)的「输入框里的图片」），所以切会话的响应只带序号、不带整条会话的截图；文件本身没有变小，图仍按需从文件里取。读取时会在浏览器里缩放（长边 ≤ 1568px）并重新编码，截图和照片通常因此小一个数量级；上限仍是 8 张/条、5MB/张（按压缩前的文件算），没有对整条消息的总量再设一道闸。
- **图片只认 `png/jpeg/gif/webp`**，`svg` 会被明确拒绝（它是文档而不是图片）。压缩只做缩放 + 重编码：**GIF 不压缩**（重绘会只剩第一帧），已经在 1568px 以内且小于 512KB 的图也原样放行；解码失败、画布不可用、或重编码反而更大时一律回退原文件，不会因为压缩丢图。
- `web/src/features/dev/TokenPreview.tsx` 是设计系统的自检页，不在路由里；需要时把 `App.tsx` 临时指向它即可。
- **「打开方式」只在 macOS 上列得出应用**：应用列表来自 LaunchServices（一段 JXA 脚本），所以只有 macOS 能回答「这台机器上哪些应用打开过这种文件」并读出它们的图标。Windows/Linux 只提供「打开」与「显示文件位置」两个动作，菜单里没有列表——dsh 在那两个平台用的是注册表和 GIO，这段实现本机验证不到，与其带一份测不了的清单，不如只留能验证的动作（见[设计说明](./design-notes.md)里那段有意不同的说明）。主机判断按 dsh 的规则：`SSH_CONNECTION`/`SSH_TTY` 非空，或 Linux 没有 `DISPLAY`/`WAYLAND_DISPLAY` 时，一个控件也不画。
- **应用只在已知的两个目录里找**：`/Applications` 与 `~/Applications`（和 dsh 一样不去问 Launch Services 的全量注册表），装在别处的 app 不会出现在菜单里；列表每次请求都重查，但页面只在一个文件被预览时查一次，所以新装的应用要刷新页面才出现。
- **图标是现画的 32px 位图**：`NSWorkspace` 缩出来的 32×32 PNG，不是 `.icns` 原图，所以菜单里的小图标比 Dock 里糊一点也不奇怪；没有图标的条目留一个空格子而不是借用别的图形。
- **选中某个应用不会改系统默认**：这是与 dsh 相同的约定（它只在这一次调用里把「用哪个应用打开」告诉系统）。另外 dsh 在没有关联应用时把主按钮变成「显示文件位置」，这里没照搬——本仓库在 Windows/Linux 没有关联查询，那会让默认打开方式没有入口，所以主按钮永远是「打开」，菜单最后一行永远是「显示文件位置」。

## 桌面版

- **没有代码签名与自动更新**：首次打开要手动放行，升级靠重新下载安装包。
- **安装包只能在目标平台上构建**（自带运行时是宿主平台的，Intel 版 macOS 包要在 Intel runner 上打）。
- **Windows 上退出时不会回收 pi 子进程**：Windows 没有 SIGTERM，服务端是被直接终止的，来不及停会话；dsh 用 job object 解决，这里没做。macOS/Linux 正常。
- 装完约 490 MB（dmg 约 180 MB），其中自带 Node 运行时占解压后约 108 MB。
- 细节与取舍见[桌面版](./desktop.md)。
